# Input Signature Validation

Agent Actions automatically validates that field references in agent prompts match the actual fields available in the LLM context. This prevents runtime errors by catching invalid references during config loading.

## Overview

When you reference fields from dependencies in your prompts using `{agent.field}` syntax, Agent Actions validates that:
- The referenced agent is declared in `depends_on`
- The field exists in the agent's output (schema or observe)
- The field hasn't been removed with `drops`

**Example:**
```yaml
agents:
  - name: extractor
    output_schema:
      properties:
        summary: {type: string}
        metrics: {type: object}
   observe: [document_id]

  - name: analyzer
    prompt: |
      Document: {extractor.document_id}
      Summary: {extractor.summary}
      Metrics: {extractor.metrics}
    depends_on: ["extractor"]
    # ✅ All references validated at config load
```

## LLM Context Formula

The fields available to an agent's LLM are computed using this formula:

```
llm_context = (schema fields + observe fields) - drops
```

### Formula Breakdown

**Schema Fields**: Fields defined in `output_schema.properties` that the LLM generates

**Observe Fields**: Input fields passed through to output (not generated by LLM)

**Drops**: Fields explicitly removed from output

### Examples

#### Example 1: Basic Schema
```yaml
extractor:
  output_schema:
    properties:
      summary: {type: string}
      metrics: {type: object}
```
**LLM Context for next agent:** `{summary, metrics}`

#### Example 2: With Observe
```yaml
extractor:
  output_schema:
    properties:
      summary: {type: string}
  observe: [document_id, timestamp, source_url]
```
**LLM Context for next agent:** `{summary, document_id, timestamp, source_url}`

**Why?** Observe fields are added to output and ARE available to next agent's LLM

#### Example 3: With Drops
```yaml
extractor:
  output_schema:
    properties:
      summary: {type: string}
      metrics: {type: object}
      temp_data: {type: string}
  drops: [temp_data]
```
**LLM Context for next agent:** `{summary, metrics}`

**Why?** Dropped fields are completely removed from output

#### Example 4: All Directives Combined
```yaml
extractor:
  output_schema:
    properties:
      summary: {type: string}
      metrics: {type: object}
      internal_id: {type: string}
  observe: [document_id, author]
  drops: [internal_id]
```
**LLM Context for next agent:** `{summary, metrics, document_id, author}`

**Why?**
- Schema provides: summary, metrics, internal_id
- Observe adds: document_id, author
- Drops removes: internal_id
- Final: (summary + metrics + internal_id + document_id + author) - internal_id

## Validation Errors

### Error 1: Missing Field

**Cause:** Field doesn't exist in dependency's output schema or observe list

```yaml
agents:
  - name: extractor
    output_schema:
      properties:
        summary: {type: string}

  - name: analyzer
    prompt: "Use {extractor.nonexistent}"  # ❌ ERROR
    depends_on: ["extractor"]
```

**Error Message:**
```
❌ {extractor.nonexistent}
   Field 'nonexistent' not available in 'extractor' output
   → Available fields: ['summary']
```

**How to Fix:**
- Use a field that exists in the schema: `{extractor.summary}`
- Or add to observe list if it's an input field

### Error 2: Dropped Field Reference

**Cause:** Field exists in schema but is in the `drops` list

```yaml
agents:
  - name: extractor
    output_schema:
      properties:
        summary: {type: string}
        temp_data: {type: string}
    drops: [temp_data]

  - name: analyzer
    prompt: "Use {extractor.temp_data}"  # ❌ ERROR
    depends_on: ["extractor"]
```

**Error Message:**
```
❌ {extractor.temp_data}
   Field 'temp_data' not available in 'extractor' output
   → Available fields: ['summary']
```

**How to Fix:**
- Remove `temp_data` from `drops` list
- Or don't reference the field in the prompt

### Error 3: Undeclared Dependency

**Cause:** Referenced agent is not listed in `depends_on`

```yaml
agents:
  - name: extractor
    output_schema:
      properties:
        summary: {type: string}

  - name: analyzer
    prompt: "Use {extractor.summary}"  # ❌ ERROR
    depends_on: []  # Missing extractor!
```

**Error Message:**
```
❌ {extractor.summary}
   Agent 'extractor' not in dependencies
   → Add 'extractor' to dependencies list. Available: []
```

**How to Fix:**
- Add `extractor` to `depends_on`: `depends_on: ["extractor"]`

### Error 4: Missing Dependency Config

**Cause:** Referenced agent doesn't exist in workflow

```yaml
agents:
  - name: analyzer
    prompt: "Use {unknown_agent.field}"  # ❌ ERROR
    depends_on: ["unknown_agent"]
```

**Error Message:**
```
❌ {unknown_agent.field}
   Configuration not found for dependency 'unknown_agent'
   → Ensure dependency config is provided
```

**How to Fix:**
- Check agent name spelling
- Ensure the agent is defined in the workflow

## Validation Timing

Validation runs **at config load time**, before any workflow execution:

```bash
$ agent-actions run workflow.yml

# ❌ Fails immediately if validation errors found:
================================================================================
INPUT SIGNATURE VALIDATION ERRORS
================================================================================

Agent: 'analyzer'
--------------------------------------------------------------------------------

  ❌ {extractor.missing_field}
     Field 'missing_field' not available in 'extractor' output
     → Available fields: ['summary', 'metrics']

  ❌ {unknown.field}
     Agent 'unknown' not in dependencies
     → Add 'unknown' to dependencies list

================================================================================
Fix these errors in your agent configurations before running the workflow.
================================================================================
```

**Benefits:**
- ✅ **Fail fast** - Errors caught before execution starts
- ✅ **All errors shown** - See all issues at once, not one at a time
- ✅ **No wasted compute** - Don't run expensive workflows that will fail
- ✅ **Clear guidance** - Errors show available fields and how to fix

## Special References

Some references are always valid and skip dependency checks:

### Source References
```yaml
prompt: "Process {source.page_content}"
# ✅ Always valid - no dependency required
```

### Loop References
```yaml
prompt: "Processing item {loop.index} of {loop.total}: {loop.item.text}"
# ✅ Always valid within loop agents
```

### Workflow References
```yaml
prompt: "Workflow: {workflow.name} v{workflow.version}"
# ✅ Always valid - workflow metadata
```

## Best Practices

### 1. Keep Schemas Clean

**Good:**
```yaml
output_schema:
  properties:
    summary: {type: string}
    metrics: {type: object}
# Only fields you need
```

**Avoid:**
```yaml
output_schema:
  properties:
    summary: {type: string}
    metrics: {type: object}
    temp1: {type: string}
    temp2: {type: string}
    temp3: {type: string}
drops: [temp1, temp2, temp3]
# Why add fields just to drop them?
```

### 2. Use Observe for Pass-Through

**Good:**
```yaml
extractor:
  output_schema:
    properties:
      summary: {type: string}
  observe: [document_id, source_url]
  # Input fields passed through
```

**Avoid:**
```yaml
output_schema:
  properties:
    summary: {type: string}
    document_id: {type: string}  # ❌ LLM shouldn't generate this
    source_url: {type: string}   # ❌ This is input data
```

### 3. Declare Only What You Use

**Good:**
```yaml
analyzer:
  prompt: "Analyze {extractor.summary}"
  depends_on: ["extractor"]
  # Only declares extractor (used in prompt)
```

**Avoid:**
```yaml
analyzer:
  prompt: "Analyze {extractor.summary}"
  depends_on: ["extractor", "classifier", "preprocessor"]
  # Too many - only extractor is used!
```

### 4. Reference Fields Explicitly

**Good:**
```yaml
prompt: |
  Analyze {extractor.summary}
  Metrics: {extractor.metrics}
  Document: {extractor.document_id}
```

**Avoid:**
```yaml
prompt: |
  Analyze {summary}      # ❌ Unclear source
  Metrics: {metrics}     # ❌ Which agent?
  Document: {doc_id}     # ❌ Ambiguous
```

## Debugging Validation Errors

### Check Available Fields

When you get a validation error, the error message shows available fields:

```
❌ {extractor.wrong_field}
   Field 'wrong_field' not available in 'extractor' output
   → Available fields: ['summary', 'metrics', 'document_id']
```

Use this list to:
- Find the correct field name
- Discover what fields are available
- Understand your data contract

### Verify LLM Context

Calculate what fields will be available:

```yaml
agent:
  output_schema:
    properties: {summary: {}, metrics: {}, internal_id: {}}
  observe: [document_id, author]
  drops: [internal_id]

# LLM Context = (summary + metrics + internal_id + document_id + author) - internal_id
#             = summary + metrics + document_id + author
```

### Check Dependency Chain

Ensure agents are in correct order:

```yaml
agents:
  - name: extractor    # Runs first
  - name: classifier   # Can reference extractor
    depends_on: ["extractor"]
  - name: aggregator   # Can reference both
    depends_on: ["extractor", "classifier"]
```

## Return Collection

When using `return_collection: true`, an additional `input_data` field is added to LLM context:

```yaml
loop_agent:
  loop:
    mode: sequential
    items_from: "{source.reviews}"
  return_collection: true
  output_schema:
    properties:
      analysis: {type: array}

# LLM Context for next agent: {analysis, input_data}
```

**Next agent can reference:**
```yaml
next_agent:
  prompt: |
    Analyze these results:
    {loop_agent.analysis}

    Original data:
    {loop_agent.input_data}
  depends_on: ["loop_agent"]
```
