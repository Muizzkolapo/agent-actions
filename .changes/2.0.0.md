## 2.0.0 - 2026-10-24
### Breaking Change
* AGAC_MAX_RECORDS is renamed AGAC_RECORD_LIMIT, so one record limit now has one name across the workflow config, the CLI and the environment. The retired name is rejected with an error naming its replacement rather than ignored: a run that believes it is capped and is not spends against a provider with no limit at all. A completed action now stores the limit that applied rather than the one its config asked for, which only new runs benefit from: an action completed by an earlier version under AGAC_MAX_RECORDS, or under --max-records with no configured limit, stored a value that cannot be told apart from a full run and is still skipped as complete. Re-run those once with --fresh.
* A `defaults:` block now declares every key it accepts and refuses the rest, where it used to drop an unrecognised key and log a warning. A typo such as `temperture:` silently did nothing where anyone would read it; the refusal now names the declared key a stray one resembles and lists the keys the block takes. Every other mistake is covered too, where before only a table of remembered spellings was. `reprompt:` and `on_schema_mismatch:` are now answered by name again, with the `expect:` block that replaces them — see that entry — but the general rule stays the floor beneath every key that has no entry of its own. The migration is in the expectations reference. `frequency_penalty` and `presence_penalty` are now declared and inherited, so writing either under `defaults:` reaches the OpenAI client and Groq's JSON path; previously both were discarded before any client saw them. `temperature` and `top_p` now carry the ranges the configuration reference already documented for them (0.0-2.0 and 0.0-1.0), matching the vendor config models, so a value outside them is refused at load instead of travelling to the API. Individual providers differ inside those ranges, and a local Ollama model that accepted a temperature above 2.0 no longer can. Any workflow whose `defaults:` block carries a key the framework does not read now fails at load and must drop the key.
* A workflow file now declares every top-level key it accepts and refuses the rest, the same rule `defaults:` already follows applied to the surface holding it. A misspelled `defaults:` used to be dropped in silence, taking every setting in the block with it: each action fell back to hardcoded defaults, the run completed, and nothing said a configuration section had been discarded. The refusal names the declared key a stray one resembles and lists the keys a workflow takes. Any workflow carrying a top-level key the framework does not read now fails at load and must drop the key. Two keys the framework does read are now declared rather than tolerated by accident: `tool_path`, which takes precedence over the default config and over `tool_path` in `agent_actions.yml`, and `storage`, whose `prompt_trace_retention_runs` and `source_data_ttl_days` are validated for the first time. That block is strict about its values because the code that consumes it reads the raw file rather than the validated model: `prompt_trace_retention_runs: "10"` used to validate as a number and hand the backend the string, failing the run after every action had succeeded, and `true` became a one-day retention without saying so. Both are refused now, as is a `storage:` block written with no value under it. `0` remains accepted and still means never prune. The retired top-level `plan:` key, which nothing has read for some time, is refused along with everything else undeclared.
* A JSON input row that is not an object is refused at staging, naming the file, the row it stopped on and what it found there. An array holding a bare value previously staged a record with no identity in batch mode, or raised a bare TypeError from the envelope, or passed through online to die at the source save with an AttributeError — which of the three depended on the mode and the shape. Give each record its own object naming its fields.
* A staging JSON file must hold a list of records. A file whose top level is a lone object was wrapped into a one-row list before the rule that refuses one could see it, so the same payload staged identically whether it was written as an object or as an array. It is now refused, and the refusal names the fix. To migrate, wrap the object in an array: a file holding `{...}` becomes `[{...}]`, which stages exactly the record it staged before, with the same identity. The refusal already named what it found; it now names what to do about it as well, on every input that reaches it. A staged document whose rows are not records, and one that is not rows at all, are reported as the shapes they are rather than as a missing field in the prompt that could not be built from them.
* `observe:` and `drops:` are no longer keys of a `defaults:` block or of an action. Both were declared on the schema and read by nothing: a workflow setting either passed validation, reached no agent, and ran as though the fields had never been named — one real workflow has been passing three field names to nothing. The mechanism that works is `context_scope:`, which is declared, inherited from `defaults:` to each action, and read. Writing any of `observe`, `passthrough`, `drop` or `drops` beside `context_scope:` instead of under it is now refused at load, on an action, in `defaults:`, in a legacy top-level `agents:` block, and in the `default_agent_config:` block of `agent_actions.yml` that every agent merges over, with a message naming the action and showing the nesting; the same slip previously reached a runtime error on one of those surfaces and nothing at all on the rest. Move the key under `context_scope:` — and note that entries there are `action.field` selectors, so a bare field name is not a reference the framework can resolve. `drops` is no longer a `context_scope` directive either: every reader takes `context_scope.drop`, so a value written under `drops` dropped nothing, and it is now refused with the valid directives named.
* The framework no longer writes `agent_io/source/`. The files there were written for version-merge actions and read by nothing: their rows are four framework keys — `source_guid`, `id`, `lineage`, `node_id` — carrying none of the record's payload, and every source read in the framework goes to the store instead. The artefact was not well defined either, because its path dropped the action directory: two version-merge actions whose target files share a name wrote to the same file, and the later one replaced the earlier. Lineage is unaffected — a consuming action chains from the merged records themselves, which carry the full merged lineage. `agac clean` is unchanged and still removes the directory, so a project carrying one from an earlier version can clear it; on a project that has never had one, a plain `agac clean` now reports nothing to clean. A project reading these files from a script outside the framework must read the store instead. Removed with them: `FileWriter.write_source`, `SourceDataLoader.save_source_data` (and the `ISourceDataLoader` methods declaring it), and `BatchSourceHandler`, none of which had a caller.
* `chunk_config` now takes exactly four keys — `chunk_size`, `chunk_overlap`, `tokenizer_model` and `split_method` — and refuses the rest at load, naming the field a stray one resembles. The key it refuses in practice is `overlap`, which is what the chunker's own parameter is called and what the shipped examples and the reference docs all used: the block was a free-form dict, so `overlap` was read and `chunk_overlap` ignored, while the expander wrote `chunk_overlap` and nothing read it. An action or `defaults:` asking for a chunk overlap therefore got the hardcoded 10, whatever it configured, and `chunk_size` alongside it worked — which is what kept it hidden. Rename `overlap:` to `chunk_overlap:` inside any `chunk_config` block; every example in this repo has been migrated. `tokenizer_model` and `split_method` were declared on `defaults:` and inherited onto the action, but only ever read out of `chunk_config`, which they never entered, so those two never reached a split either; each of the four can now be written as a key of its own on an action or in `defaults:`. Chunk settings merge by name rather than by block, so a narrower block no longer drops the names it omits and a block written further out no longer overrules the action: the order, outermost first, is the project file's block, then the workflow's key, the workflow's block, the action's key and the action's block. A `chunk_overlap: 0` written as a loose key used to be read as unset and became 10; it now reaches the split as the no-overlap it asks for. A loose `chunk_size: 0` was read as unset the same way and is now refused at load, as is any size at or below the overlap it would be split with — a pair that merging by name newly makes reachable across levels, and that the splitter used to reject partway into a run. Note that a completed action is not re-chunked on upgrade: its stored output was written under the old boundaries, and the resume check does not hash chunk settings, so re-run with `--fresh` where the new overlap matters.
* `interceptors:` is no longer accepted anywhere. The interceptor system it configured — the response-processing factory, the validation interceptor and the realtime interceptor service — was deleted some time ago, but its config surface was not: the key stayed declared on the action schema and the expander kept copying it onto the runtime agent, where no stage ever read it. A workflow writing an `interceptors:` block therefore passed validation, carried the value all the way onto the agent config, and ran as though the block were not there. That the value *reached* the agent is what kept it hidden — anything dumping or inspecting the agent config showed the interceptors present and apparently applied. Three surfaces could carry it and each now refuses it at load: an action, a legacy top-level `agents:` entry, and the `default_agent_config:` block of `agent_actions.yml` that every agent merges over. The last two validate against models that allow extra keys, so removing the declaration refuses nothing there and they are refused by an explicit check instead — without it, moving the block up a level to escape the new error would have put it back on every agent at once, unread, which is the original bug rather than a migration. A `defaults:` block never declared the key and so already refused it, but with a message listing the valid keys, which invites exactly that relocation; all four surfaces now say the key configures nothing and should be removed, and each names the block it was written in — a `default_agent_config:` block lives in a different file from the workflow, so an error omitting it sends the reader to the wrong one. There is no replacement key, because there is no longer anything to configure: delete the block. The same deletion's other half, `reprompt:`, was retired earlier. Nothing in this repo's examples, fixtures or sample project used the key.
* An input a FILE tool consumed without producing a row of its own is recorded as `reason=consumed_into_output`, replacing `collapsed_into_output`, and is no longer reprocessed on every run. The reason names neither direction because the write site cannot tell one: the flag there compares batch lengths, so a result where one input split and the rest mapped 1:1 reports an expansion for all of them, and a 3-in/3-out result where one input really split reports none. An input that was split is not collapsed, so the old name was wrong for half its uses. If you query or filter disposition rows on `collapsed_into_output`, update the string; nothing in the framework branches on it. Two shapes were reprocessed. A tool returning more rows than it received is an expansion, and lineage enrichment mints a fresh identity for every output row of one, so no row carried the input's identity and the input got no disposition row at all — `agac dispositions` showed rows only for identities the run had just invented. A tool returning as many rows as it received while splitting one of them got its row, from the contributor sweep, but no row carried its identity either. In both cases carry-forward reads prior output by `source_guid` and found nothing, so the input was re-queued at the end of the work list and split again into a fresh set of identities on every run, leaving the previous set's disposition rows behind and reordering an input that FILE mode maps by position. Rows now name, as `producer_source_guids`, every input they consumed whose identity they do not themselves carry, and carry-forward resolves such an input through the rows it produced, so the work is done once and the identities hold. It is a list, because a many-to-one output has several producers. These are the immediate producers, not `parent_source_guid`, which is deliberately the original pool-resolvable ancestor and names the grandparent once an input has itself been expanded; it is a per-stage field, so it does not reach the next action, where it would name records that action never received. The record-mode expansion paths (online and batch) mint in the same enricher and were reprocessed the same way; they are fixed by the same change. An input an expanding tool consumed but did not name is still claimed neither way, and an input a tool genuinely dropped still gets its `tool_missing_record` tombstone.
* An action that reads at FILE granularity must now declare `dependencies`, and preflight refuses one that does not — where before the config validated and the run failed on `Object of type FileUDFResult is not JSON serializable`, pointing at the output writer rather than at the configuration. FILE granularity means an action receives a whole file of an upstream action's records at once, and the first action of a workflow has no upstream: it reads the staged input, and that is driven by a different pipeline, which selects its strategy by neither granularity nor kind. So a first action declaring FILE granularity was processed one record at a time regardless — silently, when its tool happened to return plain records, and with an unserializable-object error when the tool returned `FileUDFResult` as FILE tools are meant to. The refusal names the action, says a first action is always processed per record, and points at the fix: put a RECORD action in front and depend on it, which is what every FILE tool in the shipped examples already does. It applies to `hitl` actions as well as `tool` ones, because HITL reaches FILE mode without declaring it and hits the same missing dispatch, and it resolves granularity through the workflow's `defaults` block the way the config expander does, so an action that inherits FILE granularity is refused on the same terms. Nothing that ran correctly stops running: the shape this refuses either crashed or ignored the granularity it declared. One test fixture did rely on the silent form and now adds its FILE action downstream instead.
* `versions.mode` and `version_mode` are no longer config keys, and a `versions:` block is now validated. Version fan-out turns each version into its own action in the dependency graph, and versions of one action share their dependencies by construction, so they land in the same execution level and nothing in the block could change that. Neither key was ever read: `mode` was dropped at the render step that expands the block, and `version_mode` reached every expanded agent carrying the literal string `parallel` whatever the workflow asked for. A workflow writing `mode: sequential` validated, loaded, showed `parallel` on every agent, and ran in parallel. Both spellings are refused now, on every surface that carries agent settings. `mode: parallel` is refused too — it agreed with the behaviour but configured nothing, and deleting the line is the whole migration, done here for the 14 blocks in this repo's examples, fixtures and sample project. `version_number`, written onto every expanded agent and read by nothing, is removed as well; the same value is in `_version_context` under `i`, which is what consumers read. `versions.items_from`, a reference the static analyser looked for in a key the block never declared and no workflow writes, is removed with them, and the editor integration no longer offers `mode`, `source` or `pattern` as keys of the block — it completes what the block actually declares.

There is no per-action way to order versions, and the documentation no longer implies otherwise. The reference guide presented `dependencies: ["<action>_${i-1}"]` as sequential refinement, and it does not work: on the first version `${i-1}` resolves to nothing, leaving a dependency on a bare `<action>_` that the workflow refuses, and referencing the previous version through `context_scope` instead reports a cyclic dependency, because every version of an action is one node to the graph. That section now says so and points at pooling, which is the pattern for work that must see earlier work; `--execution-mode sequential` still serialises a whole run and `--concurrency-limit` caps how many actions run at once. The refusal message names those rather than a pattern that cannot be written.

The block is validated at the render step because that is the last point on the load path that holds it: it is stripped from the action before the workflow model validates, so `mode: banana` and a misspelt `param` both reached the runtime accepted, the misspelling silently replaced by the default `i`. The validated block is now what the expansion reads, so a value pydantic coerces can no longer be validated in one form and used in another. Validation names the action and the key at fault. Four shapes that used to pass are refused: a `range` of two non-integers, which is read as an inclusive `[start, end]` and failed arithmetic at expansion; an empty `range`; a descending pair — both of which expand to no versions, which removes the action from the workflow and surfaced only as a dangling-dependency error against whatever depended on it; and an empty `versions:` block in either spelling, which declares no versions and fans out nothing. A `range` of three or more values still expands over those values, names included, and a block naming only `param` still expands to one version. Values that are not integers become the version suffixes directly and cannot be collected by `version_consumption`, which groups versions by a numeric suffix; the reference now says so. Both expansions validate the block through the same check: the config loader always renders first, but a caller handing an unstripped block to the action expander used to get no validation at all, so one block meant two things depending on which expansion ran.
* `agac retry` now exits 1 when the workflow it re-ran finished with a failed action, and names the failed and skipped actions instead of printing `Retry complete.`. It previously exited 0 in that case. A script, CI job or loop that treats a non-zero retry as an error will now see one where it saw success before; nothing that succeeds changes. Retry already classified the finished workflow exactly as `run` does — complete, terminal with a failed action, or paused — and recorded that status against the run, but then returned success whatever the answer was, so a repair that fixed nothing was indistinguishable from one that worked to every caller except a human reading stdout. Retry is the command most likely to run unattended, which is where the missing signal cost the most. What counts as failure is unchanged and is the same as `run`: a record that failed inside an action that still completed leaves the action `completed_with_failures`, which both commands call success; a failed action is the non-zero case. One divergence in the classification is closed at the same time. Retry called a workflow with actions still pending and no batch in flight FAILED, where `run` calls it PAUSED; that was invisible while retry ignored its own answer, and would have become an exit-code difference between the two commands the moment it stopped. Both now decide the three outcomes identically.
* A removed field spelling is now refused in the `default_agent_config:` block of `agent_actions.yml`, not only on an agent. The check already ran on each legacy `agents:` entry, so `depends_on:` or `skip_if:` written there failed at load naming its replacement — but the same key one level up, in the block merged into every agent, was accepted. That made the block an escape hatch from the refusal rather than a gap in it: the natural move after hitting the per-agent error is to hoist the key so it applies everywhere, which made the error disappear and the setting stop working across every agent at once. `depends_on` was the worse of the two. The canonical `dependencies` stayed empty, so the action read as having no upstream and DAG ordering changed silently instead of merely losing a setting; `skip_if` left `skip_condition` unset, so nothing was ever skipped. Both keys reached the runtime agent config and were visible to anything that dumped it, read by nothing. Migrate as on an agent: `depends_on` becomes `dependencies`, `skip_if` becomes `skip_condition`. No project config in this repository, its examples, or its test corpus carried either spelling in that block, so the refusal should reach no existing workflow.
* `reprompt:` and `on_schema_mismatch:` are now refused on every block that carries agent settings, and each refusal names the `expect:` block that replaces it. Both keys were retired with the runtime that read them, and the two strict surfaces — an action and `defaults:` — already refused them, but as keys the schema does not declare: on an action the message was `Extra inputs are not permitted`, which does not even name the key, and on `defaults:` it listed the valid keys, which invites moving the block somewhere else. The other two surfaces are validated by models that allow extra keys, where leaving a field undeclared refuses nothing, so that relocation succeeded: a `reprompt:` block written in a top-level `agents:` entry, or in the `default_agent_config:` of `agent_actions.yml`, loaded clean and rode onto every agent at once, where no stage read it. Anything dumping or inspecting an agent config showed the setting present and apparently applied, which is what kept it hidden — a project asking for schema repair got none and had no signal saying so.

The refusal carries the migration rather than telling the reader to delete the block, because unlike a key whose feature was deleted, the behaviour these two asked for is still available. A `reprompt:` block that only checked the schema becomes `expect: {repair: auto}`, and one naming a `validation:` function becomes a rule list. For `on_schema_mismatch:`, `reprompt` mode becomes `expect: {repair: auto}` and `reject` — halt rather than regenerate — becomes `expect: {max_iterations: 1, on_exhausted: raise}`; a refusal offering only the first would turn a deliberate halt into a retry loop. No source config in this repo, its examples or the sample project writes either key, so nothing the loader reads is affected. Generated workflow artefacts under `artefact/rendered_workflows/` do still carry pre-retirement `reprompt:` blocks; those are build output that the config loader never reads, and the surfaces the blocks sit in refused the key before this change too.
* A guard's verdict at File granularity can change, in both directions, because the guard now reads the record as stored rather than the view `context_scope` shaped for the prompt. Two spellings are affected and both used to depend on the granularity that read them.
A clause on a field the same action `drop`s used to be answered as if the field were absent, so `on_false: filter` discarded the record; it is now answered from the stored value and the record is judged on its merits. A clause naming an `observe`d field by its **bare** name (`n` rather than `a1.n`) used to resolve, because the observe pass flattens observed fields to top-level keys for the prompt; it no longer resolves anywhere, so `on_false` applies to every record. The failure is classified semantic rather than counted as an unmatched condition, which is why `passthrough_on_error` does not rescue it and why a warning names the spelling. With a wildcard `observe` the dead spelling is every field of the namespace, not one.
Record granularity answered both cases the new way already, so nothing changes there. Of the 13 File-granularity guards in the sample project — `examples/` has none — exactly one declares a `drop` on the same action, and it is the regression probe added alongside this change (`ql_dropguard_probe`), which exists to exercise the new behaviour. No pre-existing workflow is affected, and none of the 13 names a field without dotting it. A bare-name clause is not silent about it either — the name has a dotted form, so the guard logs a warning naming the supported spelling ("use dotted paths, e.g. `action_name.field`") and classifies the failure semantic, which bypasses `passthrough_on_error`. The editor's guard diagnostic suggests the dotted form in place.
To check a workflow before upgrading: for each File-granularity action carrying a `guard`, confirm every field its clause names is written `action.field`, and be aware that a clause reading a field the action drops will now admit records it previously discarded.
* `idempotency_key` is refused rather than accepted. It was declared on `ActionConfig`, documented in the configuration reference, and echoed into generated docs by the docs parser — with no runtime consumer anywhere, so a project writing it validated, saw the key in its own documentation, and got nothing. Unlike the keys retired in #1066 nothing had been removed: it never worked. It joins `_RETIRED_CONFIG_KEYS` with no replacement hint, since there is no behaviour to redirect a reader to, which refuses it on all four blocks that carry agent settings with a message naming the key rather than a generic unknown-field error. The declaration, the reference row and the docs echo are all removed. Measured before the change: no shipped project, example or fixture writes it.
* `ephemeral` is refused rather than silently accepted. `8bf148d59` removed its declaration from `ActionConfig` and `AgentConfig` as "never acted upon at runtime", but both models that carry agent settings are `extra="allow"` — so removing a declaration refuses nothing there. The key kept loading, kept riding onto every agent, and kept doing nothing: measured, it reached all 33 agents of a sample workflow as `False`. It joins `_RETIRED_CONFIG_KEYS` with no replacement hint, since nothing replaced it, which refuses it by name on all four blocks that carry agent settings instead of leaving the strict surfaces to say only that the key is unknown. Every config this repository controls is migrated in the same change — both integration fixtures, two inline test configs, and the shared `sample-project/`. A clone whose copy of the sample project predates this needs `bin/setup-smoke-projects.sh` before its smoke ring will load.
* A workflow file now fails to load where a tag needs a name that has no value at load, instead of rendering it as nothing or as false. Outside a prompt, a name nothing defines, used other than through `is defined` or `default(...)`, fails the load naming it: `{{ workflow_name }}`, `{% if enable_validation %}` with no `{% set enable_validation %}`, or `{{ cfg.missing }}` for a field a variable lacks; guarded uses such as `{% if debug is defined and debug %}` or `{{ model | default('gpt-4o-mini') }}` load as before, and so does the top level of a `templates/` file, which runs once as the folder loads. An inline prompt whose names the load all knows renders at load as before, and one using a name nothing supplies (`Write about {{ topic }}.`) fails the load, or each record when it also reads a record's names, instead of sending "Write about .". A name a record or a version supplies (`source`, an action of the workflow, `version`, `i`) read anywhere the load renders also fails the load: in a value other than a prompt, in a `{% set %}` block, macro or `caller()` body that a prompt uses, or tested with `is defined`, which used to be decided false for every record; wrap such a tag in `{% raw %}` to hand it to the prompt as text. A prompt that reads a record's names is sent as the same prompt in the prompt store is, under that render's `trim_blocks` and `lstrip_blocks` whitespace rules; it can use a macro, `load_prompt` or an imported template only in a `{{ }}` tag of its own outside its `{% %}` blocks, and cannot `{% include %}` anything, or the load fails naming it. A versioned action's other values that read a version variable render once per version, and fail the load on an action without versions unless guarded. The templates page listed `workflow_name`, `env` and `now` as built-in variables of a workflow file; none existed, and the page now says which names the load supplies.
* A `BETWEEN` or `NOT BETWEEN` whose range is not two numbers or two strings is now refused when the condition is parsed, so pre-flight stops the run. A range written as one value, as a list that is not two values, with `NULL` or a boolean for an end, with ends of two types, or as a parenthesised clause (`x BETWEEN 50`, `x BETWEEN [1, 2, 3]`, `x BETWEEN [50, NULL]`, `x BETWEEN ["a", 5]`, `x BETWEEN (50 AND 100)`) used to be accepted in a guard and in an `expression` expectation, and never tested a range: it gave every record the same answer, or an answer decided by the types of its ends. In an `expression` expectation, an `a AND b` range whose ends are fields (`score BETWEEN low AND high`) was accepted and false for every record as well; it is now refused, and is written `score >= low AND score <= high`. A guard already refused a field on the right of a comparison. Because `x BETWEEN a AND b` is now read whole, an expression that follows a range held in a field with another condition, `score BETWEEN range AND y == 1`, is read as a range from `range` to `y` and refused: put the other condition first, `y == 1 AND score BETWEEN range`. A range written straight after `IS NULL` or `IS NOT NULL`, `x IS NULL BETWEEN 0 AND 1`, is refused too, where its list form was accepted and false for every record.
* `reduce_key:` on an action is refused at load, and the refusal names `granularity: File` as where grouping several records into one call still lives. It grouped nothing. The troubleshooting guide documented it as the aggregation pattern — an action with several dependencies got their outputs "merged and grouped by key", and the groups decided how many times it ran — and two layers stopped that happening. The action expander copies only the fields it knows, and this was not one, so a key written on an action never reached the runtime config: the merge was handed no key, and the run behaved exactly as if the key were absent. Delivered either of the two ways that do reach the merge — under `default_agent_config:` in `agent_actions.yml`, or in an `agents:`-format block, both of which validate against models allowing extra keys and so carry an undeclared one onto the agent — the lookup then searched the record top level and the top of `content`, and every user field sits a level lower, under `content["<action>"]`. No stored record was ever keyed, so each one fell back to its own `source_guid` and formed a group of one. Online and batch behaved the same, both exited 0, and the stored output matched the same workflow without the key. Had a record been keyed, the group merge updated `content` namespace by namespace and kept one member's value per namespace, so a group of two rows returned one row's data under the other row's `source_guid`. If you wrote `reduce_key`, the run you were getting was the ungrouped one: remove the key for identical behaviour, or move the grouping into a `kind: tool` action with `granularity: File`, which is handed every record of a file in one call and may return as many rows as the grouping produces. `examples/map_reduce_fanin_check` shows that shape. `merge_records_by_key()` and `merge_json_files()` lose their `reduce_key` parameter; same-source fan-in and version-merge correlation are unchanged. A `reduce_key` written under a workflow's `defaults:` was already refused, as an unknown key, and is now refused by name.
* `policy:` on an action, in a `defaults:` block, in an `agents:` block or under `default_agent_config:` is refused at load, naming the key. It was declared on the action schema as an untyped string, echoed into generated docs and listed in the configuration reference as "Execution policy", but no runtime module read it, so any value validated and changed nothing. Remove the key: a workflow that wrote it behaved exactly as it does without it.
* `primary_dependency` is no longer a key an action takes. It was declared on the action and checked at load to name an action of the workflow, but a value written on an action never reached the running action, and the one thing it could have changed, which dependency of a fan-in is called the input and which the context, is read as one list by everything that runs: every dependency's records reach the action whichever is listed first. An action that sets it is now refused at load like any other unknown key and must drop it. Written under `default_agent_config:` in `agent_actions.yml`, which takes any key, it did reach every action: there it relabelled the input and context of each fan-in in `agac inspect`, could change which of two actions at the same level ran first, and failed the load of every fan-in when it named something that was not one of its dependencies. It is now read nowhere, so the key there does nothing.
* `retry.max_attempts` now counts every attempt under batch, the original batch included, as it does online. Under batch it counted only the retry batches sent after the first, so `max_attempts: N` asked a record the provider never answered N+1 times and stored it `exhausted_after_N+1_attempts`, while online made N calls. A batch action with `max_attempts: 1` now sends no retry batch, and one with `max_attempts: N` sends at most N-1, so an existing workflow sends one fewer paid retry batch per missing record. Raise `max_attempts` by one to keep the old count. The schema description and `retry.md` and `batch-recovery.md` now say what the number counts. (#1368)
* A workflow whose RECORD tool sets a required output field only inside a branch is now refused at pre-flight when the tool's output dict starts as `out: T = {...}` or `out = dict(key=...)`, as it already was for `out = {...}`. Such a workflow used to run and fail each record that did not take the branch. The refusal names the field and the line; make the field optional in the schema, or set it on every path in the tool. (#1491)
* Pre-flight now refuses more RECORD tools that return a record without a required output field. A tool returning its dict as `[out]` is read like one returning `out`; a key removed with `del out["key"]`, `out.pop("key")` or `out.clear()` no longer counts as returned; and a dict bound twice, `out = {...}` then `out = {...}`, holds only the second literal's keys. Each of these used to pass pre-flight and then fail at run time the records that lacked the field. The refusal names the field and the line that sets it in a branch, removes it or re-binds the dict without it. Make the field optional in the schema, or set it on every path in the tool. (#1510)
* A guard that reads through `action`, `prompt` or `schema`, such as `action.producer.severity == 'high'`, is now refused by pre-flight. It used to pass, filter every record and report success. Write the upstream action's name without the prefix: `producer.severity == 'high'` (#1512).
* Pre-flight now refuses a guard that names an action not in the workflow, or a field its upstream action's schema does not list. This includes a field the upstream only observes or passes through, and a version action's base name, such as `vote.vote` where the records carry `vote_1` and `vote_2`. Such a guard used to pass, filter every record (or keep every one under `IS NULL`), and report success. Correct the action or field name the refusal points to. Read an observed field from the action that produced it. For a version action, name the branch to read, such as `vote_1.vote` (#1516).
* A fan-in now fails when one branch holds a row a `granularity: File` tool returned with `source_index: None` (an aggregate) and another branch does not read it. It used to run the aggregate with the other branches' fields empty, and any record the tool consumed into it with the tool branch's fields empty, and report success. The error names the branches and the tool's action. Read the aggregate in an action that depends on its branch alone, or have every branch of the fan-in read it. Such rows now carry `aggregated_by`, the action's name, a framework field excluded from what an action reads; rows stored before this release lack it until the tool runs again (#1517).
* A record tool with an early `return` of a mapping that leaves out a field its output schema requires is now refused by pre-flight, even when the branch never runs in practice. It used to pass and fail each record that took that return. Return every required field from that return too, or mark the field optional in the schema (#1519).
* `agac retry --from <action>` is refused, and exits 1, when a retry stopped before it finished started above that action. Resume the stopped retry with `agac retry` first, then retry from the action if anything is still failed there (#1524).
* Pre-flight now refuses a prompt reference, `observe` or `passthrough` entry that reads a field under an action which only observes or passes that field through, such as `summarize.url` after `summarize` passed through `source.url`. The field is stored under the namespace it came from, so such a prompt failed every record and such an `observe` handed the model a null. Read the field from the action that produced it, such as `source.url` (#1526).
* `agac run` exits 1 when, online, the store refuses to record a record's failure: the action reads `failed` with the store error, and the actions that read it are skipped. It exited 0 with the action `completed` and the failure lost. Fix the store, then run `agac retry` (#1534).
* Pre-flight now refuses a first action's guard that names a staged column without the `source.` prefix, such as `page_content == 'two'`. The first action's record holds the staged row under `source`, so the bare name resolved against nothing: the guard filtered every record and the run exited 0 with empty output. The refusal names the spelling that works, `source.page_content`. `agac inspect` and the editor diagnostic report it too (#1535).
* `agent_io/logs/events.json` now holds one workflow run. When `agac run` or `agac retry` starts, the previous run moves to `events.1.json`, the one before to `events.2.json`, and so on; the last 5 runs are kept (`AGENT_ACTIONS_LOG_RETAIN_RUNS`). `errors.json` rotates the same way. Other commands, such as `agac batch`, append to the current run's file. Past 50 MB (`AGENT_ACTIONS_LOG_MAX_BYTES`, 0 for no cap) a run file stops taking DEBUG events and says so once with `LogFileCapReachedEvent` (FIO008); INFO and above are always written. `LLMResponseEvent` and `CacheMissEvent` are now INFO, so the docs site reports the current run's tokens instead of a sum over every run in the file. `--fresh` now clears the workflow's own log directory, rotations included; before, it cleared a project-root path the run never wrote to. Readers that relied on the file accumulating should read `events*.json`. Event permalinks on the docs site change when a run rotates out. (#1543)
* Prompt traces are stored compressed. `compiled_prompt`, `llm_context` and `response_text` in `prompt_trace` are zlib blobs, each compressed against a dictionary made from the first value its action wrote, so `sqlite3` shows them as blobs. Read them with the new `agac traces -w <workflow> -a <action>` (`--record <target_id>`, `--json`). Rows written before this stay as text and read back as before; the other columns are unchanged, so metadata queries still work. (#1544)
* The store's payload columns are compressed, as prompt traces are: `target_data.data`, `source_data.data`, `checkpoint_output.record_data` and `record_disposition.input_snapshot` are zlib blobs, each compressed against a dictionary made from the first value its action wrote, so `sqlite3` shows them as blobs and `json_each`/`json_extract` over them no longer work. Read them with the new `agac records -w <workflow>` (`-a <action>`, `--source-guid`, `--file`, `--field <path>`; `--snapshots` for the input each failed record was processed with). Rows written before this stay as text and read back as before; `action_name`, `relative_path`, `record_count`, `disposition` and `reason` are unchanged, so metadata queries still work. A row that cannot be decoded stops the resume or retry that reads it with an error naming the table, action and row, rather than reading as empty; a walk that meets one counts the file as lost, as it did a corrupt text row. The storage format version is now 3: an older agent-actions refuses to read a store this version has written to, with a message to upgrade, rather than misreading it. (#1546)
### Enhancement or New Feature
* agac expect list shows the expectation rules each action would run, resolved through the same loader the runner uses
* agac expect report aggregates the expectation verdicts a run stored, ordering each action's rules by how often they failed
* agac expect report --fail-under exits non-zero when an action's expectation pass rate falls short, making expectations a CI gate rather than an annotation
* The per-action record limit resolver accepts a cap carried on the action config, reporting which source capped the run

Previously only `fail` was caught by name and every other wrong level fell through to a generic type error. The refusal no longer says which spelling replaced which; the expectations reference carries the migration.
* agac run --file-limit walks at most N input files per action regardless of the workflow config, taking precedence over AGAC_FILE_LIMIT. The file axis now has the same run-level doors the record axis has, so a project can be shrunk from outside along both rather than only by staging fewer files. A value that cannot bound anything fails the run before any action starts, the limit in force is stored with a completed action so lifting it re-runs what it held back, and the walk names the flag or variable that stopped it. Neither the flag nor the variable holds back agac retry: a repair walks every file holding a record it named, which also fixes a configured file_limit stranding a named record at actions reading their input from the store.
* `agac status` shows why an action failed: when a failed action's status holds an `error_message`, an Error column gives its first line (cut to 200 characters). Only `.agent_status.json` held it before. (#1519)
* An `openai` action with `base_url` sends its requests to that URL, so one run can mix a local OpenAI-compatible server such as llamafile with OpenAI. Each action keeps its own URL; a `base_url` in the workflow `defaults:` block is inherited like every other model field. Batch mode with `base_url` is refused at preflight, because the Batch API is served only by OpenAI, and `--verify-keys` probes a `base_url` action at its own server. (#1554)
* `model_vendor: llamafile` reaches a local llamafile server at `http://localhost:8080/v1` with no API key, through the OpenAI client. A runtime is one measured row in a profile table (`llm/config/runtime_profiles.py`), so the next OpenAI-compatible runtime costs a row, not a client. Preflight refuses batch mode on a runtime that has none and warns on a JSON action with no schema on a runtime that does not enforce `json_object`. The batch refusal for every vendor without batch now reads "Action 'X': vendor 'V' does not support run_mode: batch." with the hint "Set run_mode: online." (#1555)
* `agac retry --filter <action>:<record_id> --reason "..."` keeps a record that fails the same way on every attempt out of the workflow without retrying it. It marks the record `filtered` at that action with the reason given, as a guard's `on_false: filter` does, so no retry selects it again, and removes what its failure cascaded into the actions below, which then hold nothing for it. It runs nothing and calls no LLM, validates every target before writing any (an unknown action or record, or one not failed or exhausted there, is refused with where to find the right id), and changes a live `_retry_manifest.json` to match, so resuming an interrupted retry keeps the filter instead of putting the failure back. Repeatable; `--dry-run` lists what it would filter. (#1548)

### Bug Fix
* A JSON input file holding a single object rather than a list is now staged like every other first-stage record: the payload is namespaced under content.source and the record carries an identity, its ancestry and its node. Such a record was previously built by hand with none of those, so the source save dropped it before the store's own identity check could refuse it. The input row never entered the store, nothing keyed on identity could reach it — a record limit deciding which stored rows to spare, a named retry, carry-forward — and for a document holding a bare value the submitted prompt's source namespace carried the batch's own identifiers in place of the user's content. Batch and online now derive the same identity for the same payload.
* Staging now persists the records it staged. Whether a run's input was stored at all was previously decided by comparing the field count of the first staged record against the first record of a file staging does not write: the version correlator owns that file and its rows are four framework keys, so any input payload of four fields or fewer lost the comparison and was silently never stored, leaving a run that reported success with nothing in the store and nothing for a record limit, a named retry or carry-forward to match. Repeat writes are settled by the store's deduplication, which matches on identity rather than on how many fields a row carries. The same comparison ran the correlator against its own output, which always tied, so a version-merge correlation file was written once and never refreshed; it now follows its target.
* Source data is saved to the store, and the framework no longer reports it as a file. Four surfaces named `agent_io/source/<relative_path>.json` — a debug log, the line that says a save completed, the error raised when no storage backend is configured, and both source-data events — for a path no version of the framework ever wrote, and whose directory was removed outright when the correlation artefact went. Anyone following it found nothing. All four now carry the relative path the store keys those items by. The two events rename their payload field from `file_path` to `relative_path` and say "under" rather than "to", so a reader of `events.json` is not handed a filename that never existed; nothing in the framework consumed that field as a path. The error also offered `tinydb` as a backend to configure, which does not exist — the backend is `sqlite`.
* A row a FILE tool invented — declared with `source_index: None`, because no single input produced it — no longer ends up naming its own previous identity as its producer. Such a row is minted a `source_guid` where it is built, and carries no `parent_source_guid` on purpose. When the same tool call also returned more rows than it received, the whole result is treated as a 1→N expansion, and lineage enrichment then re-minted every row and recorded the guid it had replaced as that row's `parent_source_guid`. For the invented row the guid it replaced was the one just minted for it, so the row was stored claiming a producer that exists in no source pool and matches no record anywhere — against the contract stated in `agent_actions/record/envelope.py`, where `parent_source_guid` is the original source-pool identity and a row with no single producer adds none of its own. Such a row now keeps the identity it was minted and goes on claiming no producer. Nothing else about an expansion changes: a row that did name an input is still re-minted and still attributed to the input's pool identity, which is what keeps two children of one input off a single identity, and a row arriving with no identity at all is still minted here. No consumer behaved differently before this fix — every reader of `parent_source_guid` treats a guid that resolves nowhere the same as an absent one — so the correction is to what the store records about where a row came from, not to how a run behaves.
* A FILE tool that declares an output's provenance as an empty list — `source_index: []` — is now refused with a message naming the output and both valid forms, instead of raising `IndexError` from inside the framework. `source_index` says which input produced a row: an integer, a list of integers for a many-to-one output, or `None` when no single input produced it. `FileUDFResult` checked that the key was present and of an allowed type, but not that a list held anything, so an empty one passed validation and reached the reconciliation step, which resolves the first contributor by indexing the list directly. A tool that computes its contributor list — filtering, deduping, dropping records that failed a check — and lands on empty for one output therefore got a stack trace from framework internals rather than either a result or an error it could act on. The refusal is at the point the outputs are constructed, where the other output validation already lives and where the message can name the offending output index; the empty list is refused rather than read as `None`, because a contributor list that came out empty is as likely to be a filter that dropped everything as a row the tool meant to invent, and `None` already exists to say the latter. No working behaviour changes: the same input failed before, only less legibly.
* A FILE tool's `source_index` is now checked, element by element, where the tool declares it. `source_index` says which input produced an output row: a position in the input list, a list of positions for a many-to-one output, or `None` when no single input produced it. Only the type of the whole value was checked, never the elements, and six parts of the framework then read them under three different rules — reconciliation took the first element as the row's parent, disposition accounting bounded both ends of every element, lineage bounded only the upper end. So one index could be a contributor to lineage and absent from the accounting that decides whether a record was dropped, for the same row. A bool passed every one of those checks, because `True` is an integer to each of them, and resolved to input 1: a real row, the wrong one, with no error. A `None` inside the list or a string reached lineage's comparison and raised `TypeError`; a float passed the comparison and raised on the indexing a line later. Either way it is caught further out, leaving the row with no provenance at all and its upstream namespaces gone. Each of those is now refused with a message naming the output, the element and what a position may be. A position must be a non-negative built-in `int`, so an integral value from numpy or pandas needs `int()` around it — previously such a value was counted by lineage and not by the accounting, producing exactly the split provenance this change removes. An index past the end of the input list is still accepted at the boundary, because a tool cannot always know how many records the guard left it, but what happens next depends on where it sits: a later element is a contributor and is dropped with a diagnostic, while the first element selects the row's parent, and a parent that does not resolve fails the action rather than being invented. What counts as a position now lives in one predicate all six readers share, so that much cannot drift apart again; what each does with an index past the end still differs by role, deliberately, as above.
* A RECORD-granularity action now resolves a record's `source` namespace by identity before reading the namespace the record carries, which is the order the FILE-mode resolver already used. A record can carry a `source` namespace in its own content and also have an entry in the source pool under its `source_guid`, and the two resolvers disagreed about which one wins: the same record therefore resolved to a different source document depending on the granularity of whichever action read it, with nothing in the config saying so. The pool is the run's current source set, while the namespace a record carries is a copy taken when the record was written, so identity is the authoritative answer where it resolves — the reading the FILE-mode resolver already took, and the one consistent with a record whose `source_guid` misses a multi-record pool being skipped rather than given another record's document. A record the pool cannot place is unaffected: own `source_guid`, then the carried `parent_source_guid`, then the namespace the record carries, which is all such a record has. This governs what the prompt and the observe/passthrough output fields see. It reaches a guard condition too, by way of two companion fixes in this release: the evaluator no longer promotes a carried framework namespace over the resolved one, and the FILE-mode prefilter evaluates the guard against the stored record rather than the `context_scope`-shaped copy. Both granularities therefore read the resolved namespace, and the split this entry originally recorded as surviving is closed. Two kinds of record change what they observe. One is a record that carries a `source` namespace and also resolves in the pool, where the two hold different values; it now observes the pool's. Measured across the eleven stores of this repo's sample project, no stored record meeting both conditions holds a namespace differing from its pool entry, so the case is reached mainly on a resumed run whose staging data changed underneath it — note that those stores have at most one staged path each and none uses a FILE-mode `drop` on a `source` field, so they do not exercise every way the two can diverge. The other is a record whose `source` key holds something that is not a namespace — a scalar, `None` or a list. Such a record was returned as its own source document on the strength of the key alone, and the namespace builder then fell through to exposing that record's other content, its upstream actions' output, under `source.*`, where a prompt asking for `source.<field>` could be answered from the record's own earlier output. It now resolves by identity, or to nothing when identity cannot place it either. No record in those eleven stores holds a non-dict under `content.source`, and the only two writers of that key both write an already-resolved dict, so the shape is hard to produce deliberately. An empty `source` namespace still satisfies the type check and still answers for the record at the resolver, though the namespace builder drops an empty namespace, so none reaches the prompt either way. One consequence is worth stating on its own, because it moves in the direction of disclosure rather than away from it. A `drop` on a `source` field rewrites the namespace on the record the action passes forward, and the pool it was resolved from keeps the field. Reading identity first means a later resolution of that same record returns the pool's copy, so a dropped `source` field that the record no longer carries comes back. FILE mode already behaved this way, which is why the change is a widening of an existing gap rather than a new one, and the gap itself is that a drop does not survive re-resolution at all — see the issue filed for it. A workflow relying on `drop` to keep a `source` field out of a later action's context should not, on any granularity, until that is fixed. Also, where one `source_guid` appears twice in the source pool — which a repair can produce, because it concatenates every staged path while the store's uniqueness holds only per path — both resolvers now take the first row. The FILE-mode index kept the last while the RECORD-mode scan took the first. Stored values are unaffected either way: a `source_guid` is a content hash of the payload, so two pool rows sharing one hold the same payload; the change removes a divergence between the two readers rather than altering what either returns today. What still differs between the granularities is confined to cases where neither resolves a namespace and to the shape of the pool row. Where nothing resolves, FILE mode skips the record and writes a disposition while RECORD mode proceeds with no `source` namespace and writes none, because that reason string has only ever been written on the FILE-mode path. And for a flat pool row with no `content` envelope, which legacy and foreign stores hold and which this repo's sample project has one of, the FILE-mode path strips the record-keeping keys and the RECORD-mode path offers them as document fields; reading identity first newly routes a namespace-carrying record onto that path in RECORD mode, so the difference now reaches records it did not before. Aligning it is not safe in passing, because the exclusion list holds names a user's own document can use — a staged row with a `metadata` field is in this repo's own parity fixture — so aligning it discards user fields. Both are filed rather than fixed here. Counted across every combination of carried shape (a namespace, a scalar, `None`, a list, an empty namespace, or no key at all) and pool state (a hit on the record's own guid, a hit through its parent, a miss, an empty pool, and the pool being the input set), holding the pool row enveloped, the two granularities disagreed on 25 of 30 combinations before this change and 14 after; the eleven closed are every case where a namespace resolves at all, plus the empty-pool case where the record carries `None`. No combination disagrees now that agreed before.

* A staged file the filesystem would not describe was dropped from the walk with no exception, no error record and no log line, so the action completed as though the file had never been staged. `Path.is_file()` answers `False` for `ENOENT`, `ENOTDIR`, `EBADF` and `ELOOP`, which made a dangling symlink indistinguishable from a directory; it re-raises the rest, so a permission failure was never silent but escaped from the middle of a walk with no file attached. Both filesystem walks now ask through one predicate that lets the error out: the deliberate exclusions are answered first, so a dotfile or a filtered suffix is still skipped silently, and only a file that would have been processed is reported — named, with its errno, with the action's record count taken out of service, and counted as *found*, so a walk that lost every entry fails loudly instead of completing green and empty. * The docs site's Drops panel renders again. It reads a catalog key that nothing had emitted since the bare `drops:` action key was removed, so every action shipped without it and the panel stayed empty whatever the workflow declared. * A FILE-granularity `kind: tool` action no longer fails outright when its `context_scope` cannot resolve one record. FILE mode carries the pre-observe records beside the scoped ones so the guard can restore fields the scope removed, and `prefilter_by_guard` pairs the two lists by position. The scope drops any record whose observed field it cannot resolve, and the pipeline handed the guard the list from before those drops — so one unresolvable record left the two a different length and killed the whole action, every other record in the file with it (`prefilter_by_guard received 18 original_data for 12 input records`). The scope now names the input position of each record it drops and the pipeline slices the pre-observe list to match; position rather than `source_guid`, since a record need not carry one and a concatenated multi-dependency input can repeat one. #1033 reports it with two dependencies, which is the easy way to make some records resolve and others not, but one dependency and one incomplete record was enough.
* A staging directory the walk cannot open no longer loses every file beneath it in silence. `Path.rglob` swallows the `OSError` that `scandir` raises for such a directory: the directory entry comes back, so the per-entry regular-file check answers correctly and the existing loss path never fires, while every file under it is dropped with no exception, no log line and no error row. Since #1021/#1027 a completed action stamps how many records it processed and a later record limit at or above that count is read as one that could not have changed the record set, so files lost this way were never counted while the count still read as known - the action was skipped on the next run and its short output vouched for. Permission is normally set on a directory rather than on each file, so this is the common shape of the loss. Both filesystem walks now enumerate with `os.walk`, which reports the failure with the directory that caused it. Such a directory is counted as one file found and never as one processed, is named in the action's error list and logged, and takes the action's record count out of service: an action left with nothing else readable now fails with a `DependencyError` naming the directory instead of completing as though its input were empty, and one that read the rest reports and gives up its count rather than vouching for a run short by an unknown amount. One directory is deliberately not charged: a `batch` directory, whose files are skipped whether or not it opens. A repair is deliberately not exempt either, though it walks only the files holding the records it named: the store resolves those ids with a set union, so an id resolving to no source row leaves no trace and its staging file may be the one behind the lock. Separately, the tool scanner carried a comment claiming `rglob` raises here and a handler that could therefore never fire; it now uses the same walk and warns when a tool directory cannot be listed, keeping the tools it could read where the old handler would have abandoned the whole directory. That catalog feeds schema inference and the docs. The runtime UDF registry enumerates separately in `input/loaders/udf.py` and still drops an unreadable tool subtree silently; it is the more consequential of the two and is filed rather than fixed here, since `input/loaders/` is a smoke surface.
* A first action no longer offers the framework's own record-keeping keys to the model as fields of the user's document. The source namespace for such an action was taken from the whole record: correct for a record that carries its payload under `content.source`, wrong for one whose user fields sit at the top level beside `source_guid`, `node_id` and `lineage`, because the namespace builder then published the record itself as the document. An `observe` list that names fields hid this, since such a list never names a framework key; a wildcard `observe: [source.*]` sent all three to the model. The first-stage path now resolves through the same normalizer the rest of the framework uses, so `RECORD_FRAMEWORK_FIELDS` draws the boundary that a record without an envelope does not carry, and a user field that happens to share a framework name still reaches the prompt when it sits inside the document, where the envelope distinguishes the two. The guard path is aligned the same way: it had resolved a first-stage record from the inner content dict rather than the record envelope and so produced a source namespace one level too deep. No guard outcome changes as a result — the guard evaluator merges the record after the context, so the record's own namespaces already won — and no behaviour changes for the enveloped records the staging pipeline writes, which are the only shape it produces. Separately noted, not fixed: on the file-granularity path a flat row's user field named `metadata` or `lineage` is still discarded by the prompt exclusion list, which overlaps names a document may legitimately use, and narrowing that list is a decision rather than a fix; the same un-normalized derivation exists in the file-mode enrichment pass, where the first-stage case does not arise; and `agent_io/store` holds no flat source rows in the first place, so none of this is reachable from a workflow today.
* Batch carry-forward decided which stored rows to hand back to a rewrite by subtracting the batch's record identities from the stored ones, so a row the batch had just replaced read as one it never answered for. An expansion mints a fresh identity per child, so the rows a re-run produces for an input carry none of the identities its previous rows did, and the output file was written holding both generations side by side. Reachable without an interrupted write: a prompt, schema, guard, model or limit change clears the action's dispositions and re-runs the action with its previous rows still stored, which is why the duplication showed up on an ordinary edit-and-re-run rather than only after a crash. Carry-forward is now told which inputs the batch carried — `finalize_batch_output` already held that, in the context map it writes filtered dispositions from — instead of inferring it from the results. A stored row is handed back unless this run replaced everything it holds: under its own identity while holding nothing else, or through the producers that minted it. A row naming a producer the run left alone keeps both, and an input the batch carried is never read as a minted identity, so a row held for one the results did not answer for is kept rather than inferred away. Resolving such a row through `producer_source_guids` alone is not sufficient and not safe: that field is the consumed set minus the row's own guid, so a row that kept an input's identity does not name it, and a many-to-one row would have been dropped whenever its other inputs were reprocessed.
* A guard condition now reads the `source` namespace the resolver picked, not the copy the record carries. The guard's context already held the resolved answer, and the evaluator merged the record's own content over it, so a record whose guid resolves to a pool row was judged against a snapshot taken when the record was written. The visible symptom was a granularity split — the same clause kept a record at FILE granularity and filtered it at RECORD granularity — but the split was a side effect: a FILE-mode `context_scope` pass writes the resolved namespace onto the record before the guard runs, and a FILE action declaring no `context_scope` read the stale copy exactly like a RECORD one. A guard's answer no longer depends on which granularity reads the record or on whether an unrelated `context_scope` happened to materialise the namespace.
A namespace displaces a namespace and nothing else. `source`, `version`, `workflow` and `seed` are reserved *action* names, which does not make a plain field spelled that way the framework's: a first-stage record's content is the user's own staging row, a version-merge tool spreads its output flat rather than under its action name so `version` or `source` can be that tool's output field, and a dependency's `output_field` is promoted into the context by name so presence there does not mean a resolver produced it. Both sides must be a namespace before the resolved one wins, so a field spelled that way is left alone — taking the key away would leave the clause reading a missing field, which counts as *not matched* and would silently filter the record.
Two consequences. `context_scope.drop` no longer hides a `source` field from a guard clause, because the resolved namespace is the source document and `drop` never touched it; this closes a second divergence rather than opening one, since FILE mode used to hide such a field and RECORD mode never did, and the two now agree on RECORD's answer. A dropped *dependency* field behaved the other way round until the companion fix in this release made a guard read the stored record on every granularity. And while no namespace key is removed, a *field* only the carried copy had becomes unreadable once the resolved document replaces it — inherent to resolving against the pool rather than against the snapshot.
* Batch carry-forward no longer deletes a minting action's stored answers when a run does not settle. The rule that stops an expansion's stale rows being merged back beside their replacements resolves each stored row to the inputs behind it, and read the run's whole output as evidence of what it answered for. A row the provider failed is keyed on its input and holds no answer, and a row can be stamped failed or exhausted after enrichment has already named its producers - so a refused run counted as having answered for those inputs, and every stored row behind them was dropped. Measured against a real store: two stored answers gone, replaced by an error row holding no content. The same for exhaustion, for a cascade skip, and for a guard skip, whose state is terminal and whose disposition is a passthrough. Only a row settled as `processed` now answers for an input. Two further gaps closed. How many rows an input yields is decided per run from what the provider returned, so the same input mints several rows one run and keeps its own identity the next; each direction is a replacement, and reading one side alone left four rows where one and three were right. And a row the run rewrote under a stored row's own identity now replaces it before anything else is asked, since carried rows are appended to the run's own output and an identity in both lists is written twice. The `submitted_guids` parameter is gone, the shape it guarded - a stored row that names inputs while carrying another's identity - now being kept by the rule itself: a stored row naming one input is inferred away, naming several never. That reads one producer as a mint, which holds where this runs, because a batch row naming producers has been re-keyed. It is not true of every writer, and the limit is recorded in the code: a FILE-mode merge of two inputs keeps one identity and names one producer, and `build_carry_forward` holds the stricter reading such rows need. Reachability is narrower than the issue describes. A batch record-mode expansion writes one disposition under the *input's* identity, so a cleanly completed action is narrowed away and never reaches the merge; and `--fresh` deletes the stored output before anything re-runs, so the merge finds nothing to carry. What reaches it is a clearing that leaves rows behind: `agac retry`, which clears the records it names, or a reset of a failed, interrupted or config-changed action, which clears failed, exhausted and deferred records while `success` stands. Two limits remain. An input that is itself an expansion child carries a minted identity, so if its producer re-runs and re-mints, the rows behind it stop matching and the accumulation can recur - the nested-expansion gap #1022 tracks. And a run that mints rows and then stamps them unsettled leaves them for a later `processed` run to clear, since nothing names a mint but the run that made it; no path in the batch code produces that shape today.
* A `context_scope.drop` aimed at an upstream field no longer removes a field of that name from the declaring action's own output. `drop` hides a field from one action's prompt and leaves it on the record bus, and the runtime pops it per namespace (`prompt_context[ns][field]`), but the static analyzer recorded the bare field name with the namespace discarded — so `drop: [OptionsCombiner.answer_reasoning]` on an action that also declares `answer_reasoning` itself cancelled its own output field. `agac validate` then rejected a downstream `{{ action.field }}` with "Field 'answer_reasoning' has been dropped from action ... output" for a reference the runtime serves, `agac inspect`, `agac schema` and the docs catalog omitted the field from Outputs, and an `expect:` block naming it refused the whole run with `PreFlightValidationError` because preflight reads the same flag. Forwarding and drop directives now keep their namespace, so a forwarded name is withheld only when every namespace supplying it drops it, a produced name never is, and `ns.*` withholds the namespace it names. Each directive parses through the runtime's own `parse_field_reference`, so a spelling the runtime skips is no longer modelled as forwarded — with the one asymmetry that `drop` alone rejects a nested path, since its pop is flat while `observe` and `passthrough` resolve a path. `prompt/ARCHITECTURE.md` and `llm/ARCHITECTURE.md` described `drop` as a redaction that removes a field from the output and used PII as the worked example; the second wrote the refs without namespaces, a spelling the runtime refuses outright. Both now describe the per-action scoping the other docs and the shipped examples already did.
* Batch carry-forward no longer writes both generations of an expansion whose own input is an expansion child — the nested-expansion gap the previous entry named as remaining. `producer_source_guids` names the immediate inputs a row consumed, and where the action above is itself an expansion those inputs are its minted children, re-minted every run. The stored rows named producers that no longer existed anywhere, this run's rows named the current ones, the two sets never intersected, and nothing marked the stored generation as replaced. Measured against a real store: two runs of `A(expand) → B(expand)` over one staged record with nothing changed between them wrote eight rows where four were right, and each further run added four more. What separates a producer that is gone from one this run did not answer for is whether it still stands in the action's input, so a batch now records the identities it took as input and the merge reads them back.
The recorded input is the action's input above *every* narrowing, which is the part that decides whether this deletes data. Several narrowings sit between the two: the action's `record_limit`, the records a repair names, the disposition gate, and above the pipeline entirely the runner's drop of records an upstream guard filtered. A record dropped by any of them still holds stored rows the rewrite must carry, so the batch path is now handed the same pre-narrowing list the online path already receives, rather than the narrowed one reaching the submission. Recorded below any of those, `agac retry` naming one record would have deleted every other record's rows, and an ordinary incremental run would have deleted the rows of everything already done. A repair that reaches the submission without that list is refused rather than narrowed, matching the refusal the online path already makes; a whole-file read, which nothing narrows above, is its own recording.
Because the inference deletes, it is made only on whole evidence. The run must have settled *every* input it recorded, and *no* stored producer may still be an input. The first stops a run that failed or returned nothing from reading its own stored answers as replaced and deleting them — measured before it was added, a failed re-run deleted four stored answers and an empty one emptied the file. The second makes the decision generational rather than per row, so a single record leaving the input keeps its rows instead of reading as a stale generation. Only a row already read as a mint is ever inferred away; one naming several producers holds content of its own. An unrecorded input infers nothing, so a batch submitted by an earlier version carries its rows exactly as it did, and a recording that cannot be read or is not a list of identities degrades to the same, with a warning, rather than abandoning results the provider has already returned. `clear_batch_state` clears the recording alongside the context map it is scoped with, so `--fresh` and `agac retry` no longer leave one behind to answer for a run that has none.
One case stays open, recorded as a strict xfail rather than left implicit. An action that mints no identity of its own carries its input's and names no producer — a 1:1 action, and an expansion on any input it answered with a single row, since `is_expansion` is `len(structured_items) > 1`. Below an expansion its stored rows carry the previous run's upstream child identity, match nothing, and still accumulate. Closing it means reading an identity absent from the input as a gone generation, which is what carry-forward deliberately refuses: an input that is merely absent keeps its rows. It wants its own change and its own review.
Reachability is narrower than the issue describes. It claimed every run, by way of an upstream defect in how an expansion's dispositions are keyed; that issue was closed as invalid, because the function it rests on (`write_record_dispositions`) has no production caller and a completed batch expansion is in fact narrowed away on the next run. What reaches this is the same window the previous fix addressed — a clearing that leaves stored rows behind: `agac retry`, or a reset of a failed, interrupted or config-changed action.
* A guard condition now reads the record as the pipeline stored it, on every granularity. FILE mode applies `context_scope` before the guard runs, so the record reaching the guard had `drop` applied and its observed fields flattened to bare top-level keys, and the guard was gating on that prompt-shaped view. Three clause shapes answered differently depending on granularity as a result: a clause on a dropped dependency field filtered the record at FILE granularity and kept it at RECORD granularity, while a clause naming an observed field by its bare name (`n` rather than `a1.n`) did the opposite — it resolved only at FILE granularity, because only there had the scope pass flattened it. A guard gates the action before the action receives anything, so `drop` describes what the action is then handed; it is not a redaction the framework may not gate on.
`prefilter_by_guard` already received the pre-scope records, index-aligned and length-checked, and already handed them back for tombstones and the enricher — its own contract describes them as preserving "upstream fields that observe filtering may have stripped". The guard read the other list. It now reads the stored one, and the scope pass keeps shaping what the action receives: a passing record still reaches the tool with its dropped fields gone. Where no originals are supplied, which is every RECORD-mode route into the same function, the two lists are the same object and nothing changes.
The framework already drew this distinction elsewhere: `run_dynamic_agent` takes the original data and the `context_scope.drop`-applied data as separate arguments, and sends the applied one to the model wherever it is present. The FILE prefilter was collapsing the two for the guard.
What this changes for an existing File-granularity workflow is recorded as a breaking change of its own, since a guard's verdict can move in either direction: a clause on a dropped field now admits records it discarded, and a clause naming an observed field by its bare name stops resolving. No bundled or sample workflow is affected.
A guard's verdict is the limit of the guarantee: the scope pass can still remove a record before any guard runs, when it cannot resolve the record's `source` or a field an `observe` names is missing. Record granularity runs the same pass after the guard rather than before, and raises on such a record instead of skipping it — so which records a guard judges, and what becomes of the rest, still depends on granularity. Filed as a separate decision rather than folded in here.
* A source-pool row with no `content` envelope is refused rather than read, because reading one means guessing which of its keys belong to the user's document and which to the framework — and the two granularities guessed differently. Given the same row, a FILE-granularity action subtracted `_RECORD_METADATA_KEYS` and silently deleted a document field named `metadata`, `lineage`, `chunk_info`, `node_id` or `target_id`; a RECORD-granularity action subtracted nothing and offered `source_guid` to the model as a field of that document. Neither is recoverable from, and the boundary is information the row does not carry. #584 met the same question deriving record identity, where subtracting framework field names collapsed two rows whose user column was called `node_id`, and answered it by deleting the subtraction and putting the payload under `content.source`; the read path now follows, so a row without that envelope raises `DataValidationError` naming the row and the action. Nothing the framework writes produces such a row — every staging branch, batch and online, envelopes through one authority — so this surfaces a store written before that rule instead of losing data against it. Only the row actually read is checked, so an unreadable row elsewhere in the pool does not fail the records that resolve past it, and an enveloped row is unaffected whatever its fields are named.
* A version-merge tool's output field no longer replaces a record content namespace without saying so, and can no longer be declared with a framework namespace's name. A FILE-granularity action that is a tool — by `kind: tool` or by `model_vendor: tool` — and declares `version_consumption` has its output spread flat over record content instead of nested under its own name, which is what lets a fan-in publish its merged fields beside the versions it consumed. Those field names are therefore content's own top-level keys, shared with the framework's namespaces (`source`, `version`, `workflow`, `seed`) and with every upstream action's, and a field whose name matched a key already there replaced it with no warning and no error. Where that key was `source` the cost was not one field: content's `source` is what the source resolver falls back to when neither the record's own `source_guid` nor its carried `parent_source_guid` resolves against the run's source pool, and it is accepted only as a dict — so a record whose `source` had been overwritten with a scalar resolved to no source namespace at all from that point on, and one overwritten with the tool's own dict published that output as the source document. A record the pool could still place by identity was unaffected, because identity is read first. Every replacement is now reported, naming the action and the key and saying when the key is a framework namespace. The output still wins at runtime: such a field is the tool's own data and a guard clause reading it has to keep finding it, since a clause that reads a missing field counts as *not matched* and filters the record silently — trading a lost namespace for a lost record. Instead the name is refused where it is declared: a FILE-granularity version-merge tool whose output schema names a framework namespace is rejected when the workflow config is expanded, while renaming the field still costs nothing, and whichever way the schema was written — shorthand, compiled, JSON Schema, a root-level array, or a separate schema file, which rendering inlines first. A record-granularity action nests its output under its own name, so a field sharing a namespace's name collides with nothing there and is left alone. The flat merge was written out separately at three places, only one of them reachable in a run — the FILE path, since a tool action cannot run in batch mode at all; all three now share one function, so the rule cannot drift between them.
* `output_storage` is gone from the configuration reference and from the six shipped examples that wrote it, and a project file still carrying it now says so at load. It was documented as a top-level key of `agent_actions.yml` — `backend` and a `db_path` described as the database file location — but no reader ever took it: the top-level keys read are `default_agent_config`, `tool_path`, `schema_path`, `seed_data_path`, `required_by_default` and `project_name`. So a project setting `db_path` got no error and no effect, and the store went where it would have gone anyway. The documented value pointed somewhere the framework never writes: `./agent_io/outputs.db`, against the `agent_io/store/<workflow>.db` that a run actually creates and that the data reference already documents — so the one key claiming to control the location was also the one place contradicting the location. Neither half of it was wired to anything a project could set: the store path is derived inside the storage factory, which takes no path and is called from eight places that each rebuild the same convention, and `sqlite` is the only backend registered. Removing the key is therefore what closes it, rather than honouring a location the readers cannot agree on. Because a project that copied the key from the docs keeps it after an upgrade, the key is also reported by name at load — once per workflow, naming the path a run writes instead — rather than going quiet for everyone who already believed the reference. The report covers a fixed list of keys known to have no reader, not undeclared keys in general: the project file still has no model, and giving it one stays the separate decision it was, so a misspelled key is still dropped in silence.
* An action's inferred dependency list no longer depends on the hash seed. `context_sources` was built by iterating `potential_context_sources`, a set, so Python's per-process string hash randomisation leaked into the order — and through `tooling/docs/parser.py`, which builds each action's `dependencies` as `input_sources + context_sources`, into `catalog.json`. Generating the catalog twice from identical code produced a different order for 42 of 515 actions, with `dependencies` the only key that differed. The edge set was always right, so the rendered DAG was never wrong, but any diff of two catalogs was noisy and anything content-addressing one saw churn. The auto-inferred tail is now sorted; declaration order is not recoverable at that seam, because the names arrive from a set several calls earlier. The explicit `dependencies:` half is untouched — it is a list, keeps declaration order, and still comes first.
* The documentation catalog now reports the `context_scope` the runtime applies, and expands a version range the way the runtime does. `WorkflowParser` copied each action's own `context_scope` block and nothing else, so two directives a run honours were invisible: a `defaults.context_scope`, which `deep_merge_context_scope` union-merges into every action — an action declaring no scope of its own reported no drop while the runtime dropped a field on it — and a reference naming a version base, which `normalize_context_scope` rewrites into one ref per variant. Both now go through the same two functions the runtime uses, in the runtime's order: normalisation precedes dependency inference, as `config/manager.py` states, so the dependency graph and the scope panel no longer disagree about which upstreams an action names. The version map is built from a rendered workflow's `_version_context` as well as a source workflow's `versions:` block, because the scanner prefers the rendered file once a project has run and the renderer strips that key — a map built from `versions:` alone is empty for every project that has ever run. A directive the normaliser does not know, such as a retired spelling, is passed through per directive rather than abandoning normalisation for the whole block, which had cost version expansion in every workflow carrying one. Separately, the parser's own version expansion read a two-element `range` literally where the runtime reads it as an inclusive start and end: `range: [2, 5]` documented two actions for a run of four. All four sites that derive a variant name now agree on one definition, pinned by test.
* A workflow's execution order no longer varies between runs. `topological_sort` collected its nodes into a set, so the initial queue — and therefore the tie-break between actions at the same dependency level — came from Python's per-process string hash randomisation. Six independent actions produced five different orders across five hash seeds, and the sample project's `ql_code_debug` produced two distinct orders across eight. `determine_execution_order` hands this graph straight to the executor, so the order actions ran in could differ run to run with no config or code change. Nodes are now collected in the order the caller declared them, which is what an ordered mapping already carried; dependencies still decide the order wherever they constrain it, and the tie-break is all that changes.
* The editor's guard diagnostic now runs on real configs, and reports only what a workflow file can prove. It had never run on an idiomatic one: the indexer captured a condition with the quotes YAML uses to hold the scalar still attached and then blanked quoted literals before extracting variables, and it only recognised the block form of `guard:` — so of the 90 guards in the sample project it saw 3, and extracted variables from none. Values now come from the parsed document rather than from the lines, which also fixes a trailing `# comment` being read as field names, a quoted `output_field`, quoted `context_scope` list items, and `>-` block scalars. A clause is reported in two cases: a bare name that no promotion can resolve — a dependency's `output_field`, a version key, a record field such as `source_guid`, or a first-stage action's staging columns, which are unknowable and therefore left alone — and a dotted reference whose namespace no action in the workflow writes, which is how a misspelt action name is caught. Which FIELDS a namespace holds is never judged: the record carries every namespace the run accumulated rather than only this action's declared dependencies, and the framework attaches `expect` while refusing any schema that declares it, so reporting fields produced 19 warnings against the sample project, every one on a clause the runtime answers and one of them impossible to silence. A versioned action is stored per variant (`score_1`, `score_fast`) and never under its own name, so a clause naming the base is reported with the variants it should have used. The guard language's own words — `CONTAINS`, `LIKE`, `BETWEEN`, `LENGTH` — and `udf:` conditions are no longer read as field references.
* A record whose guard skipped it no longer ends up with two stored rows under one `source_guid`. The guard runs above the per-record disposition gate, so a skipped record reaches no carry set at all while still writing a tombstone of its own. A stored many-to-one row keyed on that record, naming a *carried* input as its producer, satisfied carry-forward's producer test and came back beside the tombstone. The checkpoint table is unique per identity, so the two overwrote each other on the way in, and the duplicate survived into the next action.
Carry-forward is now told every identity the run writes a row under, not only the records it reprocesses, and refuses any stored row standing under one of them. The inputs such a row answered for come back as `missing`, which the caller re-queues — dropping the row on its own would take a carried input's content with it, because the run does not re-invoke the tool. A `behavior: filter` record writes no row and is deliberately not counted, so a merge row keyed on one is still carried untouched.
One consequence is worth stating: a guard-skipped record's prior answer is replaced by a fresh tombstone rather than carried, and that now holds for a merge row as well as the 1:1 row where it already held. The inputs that row also answered for are re-queued and rebuilt, so nothing is lost, but the skipped record's own stored output does not survive the run that skips it.
Measured across four consecutive runs read back through `read_target_for_rewrite`: the duplicate was stable from the first skipping run rather than accumulating, so a single run's in-memory output could not distinguish the two states.
* A nested `context_scope.drop` reference now removes the field instead of silently keeping it. `parse_field_reference` splits on the first dot, so `upstream.body.text` arrived as the field part `body.text`, which is not a key of the namespace — the flat `pop` matched nothing, `pop(..., None)` swallowed the miss, and the field the author asked to withhold was sent to the provider. `observe` already traversed the same path, so nested references worked for one directive and were inert for the other, and the syntax is documented for all three. The traversal is now shared (`pop_nested_value`) across the RECORD-mode path, the FILE-mode path and the `seed` drop, which each carried their own flat pop, so the two run modes cannot disagree about what a drop removes. `passthrough` is cleared for the same reference in both of the shapes it stores — an explicit nested reference is held under its literal dotted key, a wildcard copies the nested dict — or a field would be withheld from the prompt and still written to the output. A drop that removes nothing now warns instead of logging at debug, and names the consequence, because an inert drop is a field the author believes is withheld and is not; an inner wildcard such as `a.*.c` is not a path the runtime can walk and now says so rather than passing silently. The docs Drops panel, which excluded nested references precisely because the runtime would not perform them, reports them again.
* Pre-flight now refuses a guard clause that names a field without its namespace, instead of letting the run discard every record and exit successfully. `n > 1` where the record holds `a1.n` resolves against nothing: the runtime filters or skips each record with a warning and the workflow finishes green, so an entire input can be lost with no failure anywhere. Nothing caught it before a run — the pre-flight guard check inspected only the right-hand side of a comparison, the static analyser skipped any path without a dot, and the reference extractor's pattern required one, so detection was editor-only. The refusal is deliberately narrow: a bare name legitimately resolves through a dependency's `output_field`, a promoted version key (`i`, `idx`, `base_name`, `param_name`) or a declared loop param, a record field such as `source_guid`, a runtime namespace, or an upstream's own name — and a first-stage action's staging columns, or the flat-spread output of a FILE-granularity version-merge tool, are not knowable from config at all. Only a reference that can be proved wrong is refused, and the message names the dotted spelling that would resolve. The rule lives in `agent_actions/guards/bare_reference.py` so the editor diagnostic and the pre-flight check cannot drift apart. Verified against every shipped workflow: 101 guards across 30 files, zero refused.
* A `conditional_clause` UDF now receives a read-only view of the guard's evaluation context instead of the record's own namespaces. Guard evaluation assembles that context by assigning namespaces from the record by reference, and when no context is supplied it hands over the record itself, so a UDF that wrote to what it was given rewrote the record mid-run — the action's input, the enricher and the skipped tombstones all saw the new value, with nothing logged. The view wraps nested containers on the way out, so a write lands on a copy and cannot reach the record at any depth, and it refuses mutation so a UDF that writes fails loudly instead of silently changing a copy it believes is the record. It stays a `dict`/`list` subclass, and a `Bus` on the guard-clause path, so `isinstance`, `json.dumps`, `**kwargs` and `Bus.require()` keep working for the UDFs that only read. The in-place operators are refused explicitly: measured, `|=` and `+=` are implemented at C level and do not route through the `update`/`extend` overrides.
* A backend walk that loses every record now fails the action instead of completing as though the input had never existed. `process_from_storage_backend` computed its found-count from what it managed to read, so an entry lost to a failed `list_target_files` or `read_target` was absent from that count and from the collected errors both. With nothing found, the `files_found > 0` gate in `process_files` never fired: the walk returned `(0, 0)`, fell through to a filesystem holding nothing real, and the run reported success having produced nothing — a caller reading the exit status could not tell "there was no input" from "none of the input could be read". Lost entries are now counted towards `files_found` and recorded, so the existing gate raises and the message names every entry that went missing. A failed listing counts as one loss, since how many files it held is unknowable once the listing itself failed. This is the third walker of the three; #1026 fixed the same defect for the two filesystem walks, which count per entry rather than from what survived.
* A FILE-granularity action that only names `source` in `drop` no longer discards records whose source cannot be resolved. The skip was gated on `has_source_refs`, the same flag that decides whether to build the source index — but resolving and requiring are different questions. `drop` names a field to withhold, so an unresolvable source means there is nothing to withhold and the record is complete without it; a record carrying no source cannot leak one. Only `observe` and `passthrough` need the content to exist, and those still skip with `source_unresolved`, unchanged. RECORD mode already kept such a record, so the two granularities disagreed about whether it survives; they now agree for every combination.
* A record's ancestry no longer depends on which duplicate came last in the list. Three places index records by `source_guid`; two take the first on a repeat, while the lineage index took the last, so a record's `source` namespace could come from one row and its lineage from another. It now takes the first, matching the other two. That alone is not enough among parent records, where a repeated guid is ordinary — `correlation.py` keys a versioned 1:1 id on `(version_base_name, source_guid)`, so two versioned actions over one source record produce two rows sharing a guid with different correlation ids, and either end of the list is the wrong ancestor for one of them. The parent lookup now keeps every candidate and picks the one whose `version_correlation_id` matches the item's, which is what distinguishes the branches; with no correlation on either side it falls back to the first, agreeing with the source resolvers. Measured before the fix, an item correlated to one branch was given the other branch's root and parent target ids.
* An `expect:` block written in `default_agent_config:` is now validated against `ExpectConfig`, as the identical block already is on an action. `DefaultAgentConfig` is `extra="allow"`, so the block reached `ExpectationService` unchecked: `max_iterations: 99` ran 99 generate-validate-repair iterations per record against a declared bound of 1-10, `repair: none` silently dropped the iteration keys it cannot use, and a scalar `expect: "auto"` was coerced to `None`. That matters more since #1066, whose refusal message sends a migrating author to this very block — landing them back in the silence the refusal exists to end. Validated beside `chunk_config:`, which the same function already checks, and dumped with `exclude_unset` so the merge still sees only what the author wrote. No shipped project declares a block this refuses.
* A field observed through a wildcard is now enumerated, so `Outputs` reports it and a `drop` aimed at it can be named. `context_scope.observe: [upstream.*]` recorded only the source name — the fields it forwards never reached the action's output schema, so they were missing from `available_outputs`, and a `drop` naming one had no entry to mark and came back empty while the run withheld the field. Spelling the same observe out explicitly made both work, which is the asymmetry this closes. The wildcard is expanded once the graph is built and the upstream's fields are known, mirroring the `passthrough_wildcard_sources` set that already existed for the passthrough case. An upstream whose fields are unknowable — schemaless or template-based — expands to nothing and keeps its source name recorded, so a reader can still tell "brings in nothing" from "brings in something unlistable". Measured on the sample project: `qana_quiz.generate_answer_from_source` went from 5 reported outputs to 9, and its two drops (`filter`, `vote_summary`) are named where they were previously invisible.
* Two framework fields — `_delta_mode` and `version_correlation_id` — no longer render to a human as business data. `RECORD_FRAMEWORK_FIELDS` counts both as envelope metadata and the data card's own `METADATA_KEYS` did not list them, so anything reading that list treated them as the record's content. The HITL approval screen reads it: `hitl/server.py` serialises `METADATA_KEYS` into `approval.html`, which filters those keys out of what a reviewer is shown. A test now pins the card's list against `RECORD_FRAMEWORK_FIELDS`, so a field added to the envelope cannot quietly start rendering as content — three hand-kept lists answer this one question and nothing compared them before.
* A `udf:` guard can now be written. No spelling of it loaded before. The parser required at least one dot, so a bare name was refused outright; a dotted name passed the parser and became a `conditional_clause`, which the preflight static checker reads for `action.field` references and rejected as naming a missing action. Had it got that far, `UDF_REGISTRY` is keyed on the bare lowercased function name, so the lookup would have raised `FunctionNotFoundError` — and silently, since `conditional_clause` passes records through on error. The form was documented in `agent_actions/guards/ARCHITECTURE.md`.
The name is now the registered function's own, with no module prefix — the same form `impl:` uses, and the only form `UDF_REGISTRY` holds. A dotted path is refused rather than resolved by its last segment: two spellings answering to one function would make the module half decorative. Nothing that worked changes, because nothing worked; a config carrying the documented dotted form now gets an error naming the form to use instead of one about a missing action.
The identifier blocklist is unaffected — it already matched on word boundaries, so `udf:exec` and `udf:__import__` are still refused while `udf:eval_something` is not. Separately, an `expression` expectation now reports a `udf:` condition with its pointer to `@expectation_check` before validating the name's shape; it previously decided that on a successful parse, so the answer depended on whether the name happened to be well-formed.
* `agac validate-udfs` now checks a guard's UDF, not only `impl:`. The command is documented as validating all UDF references in a config without running the workflow, and its walk collected one key, so a config naming a guard UDF that does not exist passed validation cleanly and failed later when the action ran — which is the outcome the command exists to avoid.
Both guard spellings are covered: `guard: "udf:name"` and `guard: {condition: "udf:name"}`. The prefix is matched case-sensitively, as `GuardParser` matches it, so an uppercase `UDF:` stays the SQL guard the runtime reads it as rather than being refused as a missing function. A SQL guard, a guard naming no condition, and a non-string guard are all left alone.
The summary reports guard UDFs on their own line rather than folding them into the tool count, since a guard UDF is not a tool and one number covering both would overstate what it says.
* A `context_scope` that is not a mapping — `context_scope:` written with nothing under it, or as a scalar or list — no longer crashes the static analyser with an unhandled `AttributeError`. `agac docs` and anything else reading a workflow's catalog or schemas went down on a traceback instead of reporting the problem.
The cause was that `analyze()` normalizes `context_scope` before the graph is built, and the five lazy entry points that reach graph building directly — which the docs catalog and the schema service use — did not. Every reader below them received the raw YAML, so the first one to index it raised: the schema extractor, then dependency inference, then the docs parser. Coercing the shape once where the graph is built fixes all of them, rather than each in turn. The diagnostics are unaffected: `analyze()` still inspects the raw value first and still reports "action has no context_scope" with its null-specific hint, so a bad value is reported rather than silently read as empty.
`agac inspect` and `agac run` were never affected, because both go through `analyze()`.
* `agac validate-udfs` now scans a guard's UDF for reads of an unknown bus namespace, the warning it already emitted for `impl:` UDFs. The same typo in a guard UDF was silent, which matters more now that a guard UDF can be referenced at all.
The valid set is wider for a guard than for a tool, and that is why this is two scans rather than one merged list. A tool UDF receives the action-keyed bus; a guard receives the evaluation context, onto which the record's envelope fields are also copied — so `data["source_guid"]` is a correct read in a guard and would have been reported as an unknown namespace. Merging the two reference lists into a single scan would have avoided those false warnings by widening the tool set too, silencing real findings there. `content` stays excluded from the guard set, because the context flattens it rather than exposing it, so reading it is genuinely a mistake.
The FILE return-contract scan is unchanged and still covers `impl:` only: a guard UDF returns a boolean and declares no granularity, so that contract does not apply to it.
* `agac validate-udfs` no longer reports a guard UDF as fine when it reads a version name the runtime does not supply. Deciding which names a versioned action's context promotes was done twice — once by `VersionNamespaceBuilder.build`, which does the promoting, and once by a copy inside the command — and the copy claimed `i` and `idx` wherever a `_version_context` existed. `build` promotes them only when the context carries them, so a UDF reading `data["i"]` on a context without it resolved to nothing and was reported clean. The command now asks `VersionNamespaceBuilder.promoted_names`, so what the checker believes cannot drift from what the runtime does.
* A record the scope pass refuses now records which field was missing, or how many pooled records its source_guid was searched against. The stored disposition carried only `observe_field_missing` or `source_unresolved` — that something was missing, never what. The diagnosis does reach `logs/events.json` at debug level, but a log is not joined to the record; the disposition row is where "why did this row vanish" can be queried alongside it. It now travels to the `detail` column of the disposition row, which already existed for "extended error message or context" and was being passed `None`. The text is built from the error's structured context rather than its message, so only config-derived names reach a durable column. Nothing about which disposition is written changes: FILE mode still skips before the guard, RECORD mode still reaches the guard and then fails at prompt preparation. No command displays a record-level detail yet — `agac status --quarantined` shows failed and exhausted rows only — so for now it is readable by querying the store.
* A guard UDF can no longer rewrite the record through a copy of its input. The read-only bus a `conditional_clause` UDF receives held the record's own nested containers, so `dict(data)`, `{**data}`, `data | {}`, `Bus(data)`, `{}.update(data)` and the unbound `dict` methods handed them out writable, and a write through any of them changed the record mid-run with the guard returning normally and nothing logged. The bus now stores read-only wrappers, the rule the read-only view already applies one level down. `data.copy()`, `copy.copy(data)` and `copy.deepcopy(data)` return a plain, deep, writable dict (the last two used to raise), and `data |= {...}` is refused. A UDF that only reads is unaffected, except that a copy taken with `dict(data)` or `{**data}` now holds read-only containers rather than plain ones; use `data.copy()` where a plain structure is needed.
* A batch re-run no longer keeps answers for records that have left the input, and no longer loses answers for records that are still in it. Online writes an action's output for the run's inputs only; batch carried every stored row it had not answered again. Below a step that splits one record into several, whose rows are given new identities on each run, that kept the previous run's answers beside the new ones, so the output doubled, then tripled (#1155). Batch now carries a stored row only where the input it answered for is one of the run's, counting inputs the run left unanswered because they were already done, held by a record limit, or failed. As online does, an input marked done whose stored row is missing is sent again rather than skipped, so a record that leaves the input and later returns is answered again (#1206).
Three ways a re-run could empty or shrink a batch output are closed with it. When every record left to send was turned away by the guard, the output file was replaced by the guard's result alone, deleting every earlier answer while their records still read as done, so they were never answered again; that write now carries the stored rows as an ordinary one does. `agac retry` keeps every row it did not name, including the rows of a record absent from that run, as online does. And a run in which everything sent fails keeps the stored answers of the records it did not send, where online leaves the file as it is; after a reset, which takes those answers back, both write the failures. A record the guard filtered is now judged by the guard again on each run, as online judges it, instead of being called done for good. A run in which nothing is sent because the one record that passed the guard failed prompt preparation counts as a run in which everything failed.
Batch and online still differ in places. Where they do batch keeps more, with one exception: an online run that stopped on an error wrote nothing, so it can still hold answers for records that were not part of that run, which the batch run does not keep. A run with nothing to send leaves the file as it stands, so it can still hold rows for records that have left. Rows of records a record limit holds back are kept, where online drops them and answers them again. A run in which everything fails writes the failed rows; online, outside a reset, writes nothing. An answered record that now fails the guard keeps its answer in batch. A row merged from several inputs is always kept. One consequence to know: an answer for a record that is no longer in the input, because it was filtered upstream or the file now holds different records, is dropped by the next batch run that produces an output. That is what the online path already did.
This replaces the rule two earlier unreleased entries describe. Rows are no longer inferred away by generation, the reports of that inference are gone (one INFO line now says how many rows a write left out), and a repair reaching a batch submission without its pre-narrowing input is no longer refused, because a repair no longer records its inputs.
* A batch action that is reset now submits again. When a completed action's record limit, prompt, schema, guard or model changes, the next run resets it and runs it again; for a batch action the reset left the finished batch job on record, and since a finished job for a file is what stops that file being submitted twice, the action was skipped with "Found completed batch job ... skipping resubmission". The run reported it complete with 0 records and its output stayed whatever the earlier configuration had produced. Trying a workflow under `--record-limit 1` and then running it in full, without `--fresh`, was enough: the full run answered nothing. The reset now clears the action's batch state as `--fresh` does, so the action submits for the inputs it has now, as the same action does online. A failed batch action run again with a plain `agac run` was skipped the same way, and the run reported it complete with nothing sent, where online sends the failed records again. A finished batch job now stops its file being submitted again only until its results have been collected. So that this does not cost a second submission, a run killed while collecting a batch now keeps the done records of the files it had already collected, as an interrupted run keeps its checkpoints; before, they were wiped and only the finished job kept those files from being sent again. A collect pass that ends in an error keeps them too.
* Changing an upstream step now re-runs the steps below it. When a completed action's prompt, schema, guard, model or record limit changed, the next run reset that action and ran it again, but the actions depending on it were left as they were. They kept output computed from the upstream output that had just been replaced, holding answers for records that no longer existed and none for the new ones, and the workflow was reported complete. Every action that reads the reset action's output, directly or through other actions, is now reset with it and runs again, whatever state it was left in. One that names the action only in its context scope counts as reading it, and one with a batch still out gives that batch up, since it was sent the old output. The same holds when an action is run again because its stored output has gone missing. Be aware of the cost: a prompt change at the top of a long workflow now re-answers everything below it, which is the correct result and not a cheap one. A limit counts as a change too, so a run with a different `--record-limit` gives up a batch still out below it. `agac retry`, when it has records to re-run, no longer resets an action whose config changed, and no longer records the actions it completes as answered under the new config. A retry answers only the records it names; the reset cleared the failure records of every other record, and the new stamp hid the edit from every later run. It now warns that the action was edited and the next `agac run` applies the edit to everything.
* A batch run with nothing to send now stores each record as what it is. When the guard turned away the records of a run and the rest could not be sent, the output was written with every one of them marked `guard_skipped`. A record that had passed the guard and then failed prompt preparation, for example because the prompt names a field it does not have, was stored that way, and so was a record an action above had already failed. The output said the guard had turned away a record it had passed, or one it had never judged, and because a guard skip is passed on, the action below took them as input: a failed record could be processed again two actions later. A preparation failure is now stored as `failed`, with the error in its history, and a record blocked upstream as `cascade_skipped`, as online and a batch run that does send something already store them. The failed disposition and the action's status were already right and do not change.
* A batch collect pass that ends in an error no longer sends the files it had already collected a second time. An error while collecting marks the action failed, and a failed action is reset by forgetting every record it had finished, so on the next run each file already collected and written was submitted, and paid for, again. A run killed while collecting already kept those records; one stopped by an error now does too, unless its batch was submitted before this release.
* `agac retry` no longer loses a batch that finished but was not collected. When a batch collect pass was stopped part-way (an error, a kill), a file whose batch had finished at the provider but had not been collected yet was still waiting. Retry treated only a batch still running as owed, so it went ahead, cleared the record of that batch, and nothing could collect it afterwards: its records were never answered and the action was reported complete. Retry now refuses in that case, as it does for a batch still in flight, and says to run the workflow again to collect it first (where the action already reads completed that run does not collect it, see #1234, and `--abandon-in-flight` is the way through). `--abandon-in-flight` still lets the retry through, and now marks as failed every record the abandoned batch was still holding, including records whose waiting mark an earlier run had cleared, so a later retry can reach them. Whether a finished batch is still owed is decided from its records, so a batch collected before this release whose records hold their dispositions, or one whose records all failed, does not hold a retry up.
* Batch runs now honour `on_empty`. When the model returned an empty answer for a record, a batch run counted the record as done and stored nothing for it, whatever `on_empty` said: no failed row, no tombstone, no halt, and nothing to show the answer had been empty. Online runs applied `on_empty` all along. A batch now does the same: `warn` (the default) stores the record as failed with the reason, so `agac retry` can reach it, `skip` stores a tombstone, and `error` stores the record as failed and fails the action. Under `error` a batch fails after writing its file, because a batch writes once and the other records' answers are in that write; an online run stops at the record. If your batch workflows had records that silently came back empty, they will now show as failed records on the next run.
* A skipped action whose input holds nothing now holds nothing either. A skip never rewrites stored output, so an action skipped because an upstream filtered every record, or a version merge skipped because every version came back empty, kept the rows it stored before, made from output that no longer exists, and `agac preview` showed them. Those rows are now deleted along with the dispositions and checkpoints that called them done. Rows stand while every dependency still holds rows, so a reader of an upstream that failed but kept its answers keeps its own, and a retry of named records never deletes rows.
* A batch collect pass no longer writes a file again from a batch it has already collected. Each pass re-read every finished batch of the action, collected or not, and wrote its file from those old results. So whenever one file of an action had a batch out, every other file was put back to what its last batch said: a later run that had sent nothing for a file, because the guard turned away what was left, saw its write undone, and rows came back for records that were no longer inputs. A provider that no longer returned an old batch had the file's answers rewritten as `batch_not_returned`. A collect pass now skips a batch whose results it has written, without asking the provider about it. A batch recorded before collection was stamped is read, and its file written, once more, then skipped.
* A batch input file in a subdirectory now has one name. A batch keyed every input file by its basename alone, so two files of one name in two directories (`a/page.json`, `b/page.json`), or one beside a top-level `page.json`, shared one batch: the second found the first's batch out and was never sent, with nothing reported, and on later runs each file's batch dropped the other's answers, so they were paid for again. A batch version merge over such files did the same. A file in a subdirectory was also stored under two names, its answers as `page.json` and the write made when the guard left nothing to send as `sub/page.json`, so an action below could read a record twice; an input of a later action not named `.json`, such as `page.txt`, was split the same way between `page.json` and `page.txt`. A batch now keys a file by its path and stores it there with a `.json` suffix, `sub/page.json`, the write made when nothing is sent included. A store that already holds a nested file under its basename keeps it there, since the actions below hold it there too, until `agac run --fresh` or until a top-level input of that name needs it; of two files that shared that name, the first walked keeps it and the other is sent again under its own. A store already split across two names stays split until `--fresh`: the actions below go on reading the stale `sub/page.json` beside `page.json`, so they answer its records twice and a record limit counts them twice. An earlier version runs a store this one wrote without error, but sends a nested file's records again and stores a second copy under its basename, and never stores the answers of a batch this version left out; run it with `--fresh`, and run `--fresh` again on coming back.
* A batch run with nothing left to send now records its records as a run that sends does. When the guard, the action above or a prompt that could not be prepared left nothing to send, the run built its rows by hand: each row lost the parent, version correlation and history the action above gave it, a guard skip carried the old `skipped_by_where_clause` flag in place of its reason, and no record got a disposition. So a record the guard filtered was not recorded as filtered, an answer whose record came back skipped kept its `success`, so the record was never sent again once the guard passed it. Such a run now collects its file as finalize does: a skip or an upstream block is `unprocessed` (as in a batch run that sends; online records a guard skip as `passthrough`), a filtered record is `filtered`, and a failure is `failed`. A record whose prompt could not be prepared is now recorded with the error itself on every batch run, as online records it, where a run that sent something recorded only `prep_failed`.
* An action that runs and finds no input file now holds nothing. When an action was reset (its config changed, or an upstream it reads ran again) after its input was removed, the re-run found no file, reported `0 records` and completed without writing, so the rows it stored before stood, its readers ran again on them, and `agac preview` showed them as current. Such an action is now skipped with "No input file found", the rows it stored before are deleted, and its readers are skipped under it and lose theirs. On a first run with nothing to read, a reader used to fail looking for output its upstream never wrote; it is now skipped too, and the run succeeds. A retry of named records whose files are gone still keeps every row.
* An online action now finds the rows it stored for a file in a subdirectory, and for a staged file that is not `.json`. It stored `staging/sub/page.json` as `sub/page.json`, and a staged `page.csv` as `page.json`, but looked its own rows up as `page.json` and `page.csv`. Mostly nothing was stored under that name, so `agac retry` rewrote the file with only the records it named: every other record's answer was deleted while its disposition still said success, and nothing answered it again. Where a top-level file of that name was stored as well, the rewrite filled the nested file with that file's answers instead of its own. And a run that picked an interrupted action back up sent records of a file it had already finished to the model again. Every lookup now uses the name the file is stored under. A top-level `.json` file was not affected. This does not repair what is already stored: an action rewritten this way keeps what it holds, and a plain re-run skips it as complete, so run the workflow again with `agac run --fresh`. For one of these files, a checkpoint left by a run interrupted before this release sits under the old name and is not found: the resumed run sends those records once more, and nothing is lost.
* A project that lives under a directory with `staging` in its name (such as `staging-env/`), or under one named `batch`, now reads its input. Where a run read from was decided by looking for those words anywhere in the path, so under `staging-env/` every action that reads another action's output found nothing and reported `0 records`, and under `batch/` no staged file was read at all. Only the directories inside the project decide it now.
* A batch action no longer keeps the rows of records its guard filters. Its write merged back every stored row whose record was one of the run's inputs and was not answered again, and a record the guard filters is never answered. So a completed batch action given a guard that filters a record kept that record's old answer, where online holds no row for it; given one that filters every record, it kept all of them, ended `completed` instead of `skipped`, and its readers ran on and kept their own rows, where online skips and empties them. A batch action now holds no row for a record its guard filtered in that run, as online, and one whose guard filters every record holds nothing and is skipped. A run in which everything sent failed still keeps what it held for such a record, as online, which writes nothing then. An action already holding such rows drops them the next time its records reach the guard again: after an edit resets it, or with `agac run --fresh`.
* What a run finished before it stopped partway through an action is now kept only while the action's config is unchanged. The next run resets such an action, and what the reset kept depended on how the run stopped. Killed, interrupted or stopped while collecting a batch, the action kept the records it had finished even when its prompt, schema, guard or model had been edited since: the next run asked only for the rest, a batch collected the jobs the old model had answered instead of sending anything under the new one, and the action was then recorded as complete under the new config, so nothing re-ran it. Stopped by an error, it kept nothing even when nothing had changed, so every record it had finished was asked again and paid for twice, as was a batch file already collected once a resumed collect failed before it was collecting again. An action now records the config and model it works under when it starts, and the reset compares them with the config in force. Unchanged, it keeps what was finished however the run stopped. Edited, the action and every action that reads it answer everything again, and a batch still out under the old config is given up with a warning. Only the prompt, schema, guard and model count: a change to a tool's code, to seed data or to the context scope is not seen, and `agac run --fresh` answers everything again after one. A record the stopped run answered in a file it had not written yet is asked again when an earlier run had stored that file: the next run used to carry the stored row, which held what was answered before an edit to the action or to what it reads. An `agac retry` of an edited action, stopped or finished, leaves the edit to the next run, which applies it to every record; for an action that had never completed, a finished retry recorded it as complete under the edit and the records the retry did not name kept the old answers. Records the reset keeps now keep their prompt traces as well. An action stopped before this release, or a batch submitted before it, has nothing recorded and is reset as before: kept if it was interrupted or killed, wiped if it failed, so a collect pass stopped by an error sends what it had collected again.
* A record an online run answered after an edit to the action or to what it reads is no longer served with its answer from before the edit when the run was stopped as that answer was being checkpointed. The run marked the record answered before checkpointing its answer, so a run interrupted between the two, or a checkpoint write that failed, left the record marked answered with no checkpoint: the next run carried the answer stored before the edit and recorded the action as complete. The answer is now checkpointed first, and a record whose checkpoint write fails is not marked answered then, so it is asked again when the run is stopped while still answering its file.
* A batch run whose every record is already done now writes its file for that run's inputs, as online does every run. Such a run sent nothing and collected nothing, so the file kept rows for records that had left it: a record removed from a file kept its row there, a record moved to another file was answered there and still held in the old one, so the actions below read it twice, and a staged file emptied before an edit kept every old answer. This is met on resuming a run that died, and on running again after an edit that resets the action. The run now drops the rows of records that are no longer inputs, writes an emptied input's file empty, and keeps the rows of records a record limit holds back, since they are still inputs. A file nothing left is not written again, unless it holds two rows under one `source_guid`: it is then written with one of them, as online writes it. `agac retry` writes nothing over a file it names no record of. A record that leaves a file while that file's batch is out still keeps its row.
* A guard written as a Python function (`guard: "udf:name"`) is now applied to every record. The function is handed a read-only view of the record, and building that view failed for a record nested a few hundred levels deep, which JSON allows, and for one that refers back to itself. The failure was taken for the function's own error, and a guard whose function raises passes its record, so such a record went to the action with the guard never run. The view is now built without recursion: depth, cycles and a value held in two places no longer matter, and an ordinary record's view costs about half what it did. If a view cannot be built at all, the record is never passed unjudged, as it was before: an online action fails with an error naming the guard and the record, and a batch marks that one record failed, or fails the action if the record is among the rows it checks before submitting. Four things a guard function can observe have changed. A copy taken with `.copy()` has the record's shape, so a value the record holds in two places is one value in the copy, as `copy.deepcopy` gives. A dict or list subclass inside a record is read from what it stores and in the order it stores it, not through methods it overrides. A named tuple that holds no dict, list or set keeps its type, where it used to become a plain tuple. And a value that only claims to be a dict or a list (a weak-reference proxy, a test mock) cannot be viewed, so its guard stops with an error where it used to run.
* `agac retry` no longer completes an action that holds no answer for some of its records on the records it names alone. A retry answers the records it names at every action it runs and carries what each already holds for the rest, so an action put back to pending by an edit to what it reads and then stopped while running again, stopped partway by an error, added since the last run, or completed with its stored output gone ended up complete holding old rows, or none, for every record that run had not reached, and the next `agac run` found nothing to do. That held for any such action the retry's run reached, including one that runs before the action the retry starts from. A retry that names records now refuses, before it clears anything, while any action in the workflow is pending, running, interrupted, stopped while collecting a batch, completed without its output, or failed by anything but reaching every record it was given, and says to run the workflow first; `--dry-run` reports the refusal instead. A failure that reached every record is still retried, unless the action holds a row for a record that run did not reach, as one reset by an edit keeps for a record its input no longer has. An action left unfinished by a retry that was itself interrupted is resumed by running `retry` again, as before, unless a run has reset it since. An action holding a batch that has not been collected, and one reading it, are left to the batch's own refusal, so `--abandon-in-flight` still gets past a batch the provider has forgotten. An action halted by `on_exhausted: raise` has a refusal and a remedy of its own, given in the entry on resuming a halt. A failure recorded before this release cannot say whether every record failed, and a retry interrupted before it left nothing to say which actions it put back, so a retry over either is refused until the workflow has run.
* A file-granularity action that reads an edited action no longer serves rows made from the answers the edit replaced when its run stops as it stores a file: interrupted, killed, or failed by an error such as a full disk on every file, now that an action stopped by an error keeps what it finished. Collecting a file marked every record in it answered before the file was stored, and a file tool leaves no checkpoint row to say the stored file is older, so the next run carried every row of the file stored before the edit and recorded the action as complete. A record whose checkpoint write had failed was left marked answered the same way. Collection now marks a record answered or passed through only once its file is stored, while a failure or a guard's filter is still recorded as it is collected; at record granularity an answer is also marked as its checkpoint row is stored. A file stored before the run stopped keeps its records, and the next run does not ask for them again. A reader left this way by an earlier version keeps those rows until the workflow is run with `--fresh`.
* A batch the provider refuses for one file now fails the action, as it already did when that file was the only one. When another file of the action had a batch out, the refusal was logged and the run paused as if the file had been sent; once the other batches were collected the action read completed, was not run again, and the refused file's records were never answered. A record sent again after a failure kept its failed row under a completed action, and a file sent for the first time was never written at all. The run now fails. The next run sends the refused file's unanswered records again, and the run after collects every file; a batch still out for another file is kept and collected, not sent again, and while the action's config is unchanged, records it had already answered, in any file, are kept rather than paid for again. While the provider refuses a file, the run names the files whose batches are out and wait to be collected. A refused batch also no longer replaces the file's record of what its last batch was sent: that record now changes only for a batch the provider has taken. If it cannot be stored, the error now names the batch the provider took, which nothing else names; the next run sends its records again. A project an earlier version left with a refused file's failed row under a completed action is not repaired by `agac run` or `agac retry`, which find nothing to do; `agac run --fresh` sends every record of the workflow again.
* A batch action no longer records a record that reached it without a `source_guid` under its target id. Every record is stamped where it is staged or by the action that produces it, so such a record comes from data edited outside the framework. When it failed, `agac retry` named the failure by that target id and cleared it, but a retry selects records by `source_guid`, so it sent nothing, and the action then read complete over the failed row it still held; `--abandon-in-flight` marked it failed under that id too. When it was answered, its row went downstream with the target id as its identity. A batch run now does what an online run does: the record is refused and stored as a failed row that keeps its target id and the content it arrived with but has no `source_guid`, and nothing is recorded for it under any other id, so a batch run no longer hands `agac retry` a failure it cannot repair. A line of the provider's results that could not be read, failed until now under the placeholder id the parser gave it, which names no record, is refused the same way. Where the action's other records succeeded it now reads complete, as online, where a failure of such a record made it read completed with failures; the failed row and the run log say what was refused. Where nothing in the file succeeded the action now fails, as online, where it could read complete and let the actions below it run. A batch run that sends nothing at all refuses such a record the same way, and since nothing in such a run succeeds, the action fails. To process the record, give it back its `source_guid` upstream. A failure an earlier release recorded under a target id stays in the store; a `deferred` mark it left for a batch still out is cleared when that batch is collected.
* A batch action no longer completes past a finished batch that its collect pass could not ask the provider about. A collect pass checks each batch with the provider before reading it, and when that call failed (a connection error, a provider out of reach) the file was passed over. If another file was read in the same pass, or had been in an earlier one, the action was recorded complete with that file's records still waiting: the next run found the action complete and never read the batch. If no file could be read at all, the run failed the action, and the run after that only paused, so collecting took a failure and two more runs. Both now pause, as a run does while a batch is still out, and say which file could not be read; the next run reads it, without sending anything again. A file a retry round hands back during the pass, when the round is dropped for want of its saved state, is waited for the same way. A finished batch the provider now reports failed or expired was passed over too, though no later run can read it; its records are now marked failed for `agac retry` to find, as are those of a file whose reading fails, which still costs only its own records. An action an earlier version completed this way is not repaired by `agac run` or `agac retry`, which find nothing to do; `agac run --fresh` sends every record of the workflow again.
* A completed action is no longer run again because its stored output could not be read. Before skipping a completed action, a run checks that it still holds its output, and a read of the store that failed there put the action back to pending. Run again, it answered the records it had failed, which a plain run of a completed action never does, and a record that now succeeded gained a row nothing reading the action ever saw: each reader stayed completed, holding the record as one its upstream never answered, and neither `agac run` nor `agac retry` reached it again. A store that cannot be read at that check now leaves the action completed, with a warning naming it, and its failed records are left for `agac retry`.
* A run in which the store fails to write one of an action's files, on a full disk or a database error, now fails the action instead of recording it complete. The failure was taken as that file's own, like an unreadable input: the run logged it, wrote the other files, recorded the action complete and exited 0, and a batch collect pass recorded it partly complete the same way. After an edit, that file still held the rows answered before it, so the action's readers ran on them and no later run asked for them again; on a first run the file was never stored, and never asked for again either. The run now fails the action with the store's error and exits 1, and the next run stores that file without asking again for the files it stored. An online run writes the other files first; a batch collect pass stops at that file, and a later run collects it and the files after it without sending any of them again. Anything else that keeps one file from being stored, such as a file name the store rejects, still costs only that file. An action an earlier version recorded complete this way keeps those rows until the workflow is run with `--fresh`.
* A batch action whose `retry` with `on_exhausted: raise` gives up on a record now halts once that record's file is written, as an online action does. The collect pass took the halt for that file's own failure: it logged the error and went on, recorded the action complete and exited 0 with the record unanswered, as `on_exhausted: return_last` would, and no later run asked for it again. The run now ends `failed` with exit 1, and later runs leave the action to `agac retry` or `agac run --fresh`.
* `agac retry --dry-run` no longer changes anything after a retry that was interrupted. It put that retry's failures back and deleted its manifest, though it said no changes were made. And any retry put them back on every action the interrupted one covered: on one it had completed, its answers were replaced by the failures it had already repaired, and when the action it started from had failed every record, that action's node-level failure went back too, so the next `agac run` answered every record of it again while the actions reading it kept what they had built from the replaced rows. A dry run now puts nothing back and keeps the manifest, and the plan it shows counts what a retry would put back. A retry puts nothing back once every action the interrupted retry put back to pending has completed, or on an action a run has reset since, and never a node-level failure on an action that has completed. Retrying again still resumes an interrupted retry from where it started.
* An online action whose guard filters every record of one input file is no longer skipped while another of its files holds rows. The file whose records were all filtered marked the whole action skipped, so the run reported it "skipped — All records guard-filtered — no output produced" over the rows its other files had just written, every later run ran it again, and its readers were skipped and kept the rows they built before, those from the filtered records included. Batch completed in the same project. Such an action now completes, as in batch, and its readers run on what it holds. A project left this way is put right by its next run. An action left holding no record because its guard filtered them all is still skipped, and so are its readers. Records it keeps from a file the run did not read, such as one beyond `--file-limit`, count as held in either run mode, and so do records stored by a version of agent-actions too old to note how many a file holds, which batch had read as none. The warning for a file whose records are all filtered now says none of them reaches downstream actions, rather than that downstream actions receive no input.
* A batch run that cannot reach OpenAI, Anthropic, Groq or Gemini while checking on its batches now pauses, and the next run asks again. Each SDK raises its own error for a connection that fails, a request that times out or a server error, and none of them was taken for a provider out of reach: the run failed the action, whether it was waiting on a batch still out or collecting finished ones, when the files after it in that pass were not read either. A provider that answers it does not know the batch still fails the action.
* The run-modes reference told readers to retry the failed records of a batch action with `agac batch retry --batch-id ...`, a command agac does not have: it answered `No such command 'retry'` and exited 2. The page now shows `agac retry -a <workflow>`, which retries a batch action's failed records as it does an online action's, and says that a batch still out at the provider must be collected first, with `--abandon-in-flight` only for one the provider no longer has. A test now resolves the command path of each docs code-block line that runs `agac` directly through the CLI's own command groups, so a page cannot name a command group or subcommand agac lacks; the options and arguments after the command are not checked yet. Separately noted, not fixed: the inspect reference still documents `agac inspect field-flow` and `agac inspect conflicts`, which were removed from the CLI; the test holds them as known gaps until that page is rewritten or retired.
* `agac retry` no longer erases a failure it does not repair. A retry clears the failures it names, at the action it starts from and at every action after it, then re-runs them on the records whose `source_guid` it named. A failure the re-run never reached — one an earlier release recorded under a batch record's target id, one set by hand, one whose record's input file is gone, one in a file the action then failed to process, or any of them when the action failed before it finished — was cleared and never decided again: the retry said it had cleared it and was complete, the failure was gone, and the action read complete over the failed row it still held, so neither `agac status` nor a later retry showed anything left to do. Each action now gets back what was cleared there for such a record unless it decided the record again itself, an action the re-run left complete is read again as a run reads it, and the retry names the records (the first ten, and how many more) with what to do: where a file or the action failed, fix that and run the retry again; where a record's input is gone, restore it; an id no input carries is cleared only by `agac run --fresh`. Records the re-run repairs are repaired as before, including one a file tool rolls into rows no single record produced. A retry stopped while putting back the failures it did not repair has the next retry put them back, even where every action it ran completed. A retry that puts back an interrupted one's failures now keeps each one's `relative_path` as well, as the put-back does; nothing in agac sets that field today, so only a value set through the storage API was lost.
* Pre-flight now refuses an action that names, in its `context_scope` or prompt, an action that is not upstream of it through `dependencies`, instead of running it on nulls. A record carries the namespaces of the actions it passed through, so an action that ran beside or after the reader was never on the records it read: every field of it read null, on every run, with no error. The run could also start the reader before the action it named, because it orders by `dependencies` while the run order counted the name, and when that action failed and ran again the reader stayed completed with what it had read. Running the reader later would not have helped: its input was stored before that action ran. A name on a parallel branch is refused as well. It was read only while that branch happened to finish at an earlier step than the reader's input, and its reader was left completed the same way when it failed and ran again. A reader with no dependencies, which failed at run time on such a name, is now refused before the run starts. The message names the reader and the action, or the base of a version merge none of whose versions is upstream, and says to add that action to its dependencies (the fan-in pattern) or to depend on one downstream of it. An action named upstream of the reader's dependencies is read as before, and none of the example workflows is refused.
* An online action that answers a record with several rows no longer keeps only the last of them when a run stopped on its first pass is resumed. The checkpoint saved a record's rows under the identity they share until they are stored, so each replaced the one before it, and the next run stored one row for every such record it carried from the checkpoint and recorded the action complete, with exit 0. The checkpoint now keeps every row of a record, and the next run asks again for a record answered with several rows rather than carry them under one identity. A record answered with one row is carried as before. A run an earlier version stopped is resumed without that loss too: its checkpoint holds one row of each record, so the next run asks again for every record it holds. An action an earlier version recorded complete this way keeps those rows until the workflow is run with `--fresh`. An earlier version cannot resume a run this one stopped, and fails the action; resume it with this version, or run the workflow with `--fresh`.
* A target file the run fails to store, on a full disk or a database error, is now reported as a failed write. Before the line saying the write failed, the run printed `Failed to load data from <target file>`, an error-level `D002` `DataLoadingErrorEvent` also recorded in `events.json` and `errors.json`, for a load that never ran. It now fires `FileWriteFailedEvent` (`FIO007`), `Failed to write <target file>: <error>`, online and in a batch collect pass alike. A filter on `D002` no longer sees write failures; one on `FIO007` does.
* A batch action below another one now sends the retry its `retry:` block asks for, and so does a versioned action whose prompt or guard reads `version.*`. When a collect pass found records the provider had not returned, preparing their retry batch for an action with `dependencies` failed with "has dependencies [...] but agent_indices was not provided", logged as a failed retry submission. Nothing was sent, the lost records were stored `cascade_skipped` with the disposition `unprocessed` (`batch_not_returned`), and the action reported itself complete, so only actions with no dependencies were ever retried. A versioned action whose prompt read `version.*` lost its records the same way; one with no dependencies whose guard read `version.*` failed its collect run instead. A retry is now prepared with the workflow's action positions and configs and with the action's version: it reads the same upstream answers, a guard on an upstream's `output_field` or on `version.*` lets it through as it let the first submission through, and a retry of a retry goes out the same way. A retry still cannot be prepared for an action whose prompt or guard reads `workflow.*`.
* A batch action now stores a file that took no input empty on its first run, as online stores it: one the action above holds nothing for, one whose every record a guard upstream filtered, or a staged file that is empty. With nothing stored for that file yet, the run stored nothing for it, so the actions reading it found no such file where online hands them an empty one, and the readers of an action whose every staged file was empty were skipped for finding no input file; they now complete over the empty files, as they do online. A file the action stored before was already written empty in that case, and a repair still writes nothing over it.
* Pre-flight now refuses a guard that names an action not upstream of its own action through `dependencies`. A guard is evaluated on the records its action reads, and those carry only the actions they passed through, so a guard on one that ran beside or after it found nothing there: under `on_false: filter` it filtered every record, and the action was skipped with exit 0. The message names the action and the one its guard names, and says to add that one to its dependencies or to depend on an action downstream of it. A guard naming an action upstream of it is evaluated as before, and none of the example workflows is refused.
* A guard written as a Python function (`guard: "udf:name"`) that writes to its input, for instance to tidy a field before deciding, is no longer skipped over. The function is handed a read-only view of the record, which refuses the write by raising, and a guard whose function raises passes its record, so such a guard filtered nothing: every record went to the action, the ones it would reject included, with a warning in the log and exit 0. The refused write now stops the action with an error naming the function and saying to copy what it needs and return a value, and no record reaches the action unjudged. Under `run_mode: batch` the rows checked before anything is submitted stop it the same way, and a write on a later row fails that record alone. * A guard written `NOT x == 1` now negates the comparison, not the field. `NOT` was the tightest-binding level in the guard grammar, above every comparison operator, so an unparenthesized `NOT x == 1` read as `(NOT x) == 1`: the comparison was decided by `x`'s truthiness, never its value, and was false for every record whose field was truthy. Under `on_false: filter` this filtered every record and the run exited 0 with no error; only `NOT (x == 1)` gave the intended result. `NOT` now binds looser than every comparison operator (including `IS NULL`/`BETWEEN`) and tighter than `AND`/`OR`, matching the guards page.
* A guard that compares a field to a string containing and, or, not, in, is, like, between, null or contains now parses. A naive pre-check split the raw clause on those words with no regard for quotes or parentheses, refusing valid guards such as `source.title == "rock and roll"`, `(s.x == 5 OR s.done)`, and every function call (`LENGTH(extract.items) > 2`) with a misleading "Invalid field names detected" that named no field. The check is removed; the real grammar already enforces the same field-name shape. `LENGTH`, `UPPER`, `LOWER` and `TRIM` can now take a field argument, not only a literal, and are documented on the guards page; they are not available in an `expression` expectation's condition. A guard naming an unregistered function, or the wrong number of arguments, is now refused before any run starts, rather than silently becoming a no-op at the first record.
* The terminal keeps the action name at the start of a log line. Many lines name their action in brackets, as in `[fragile] Error executing UDF ...`, and the console read that bracket as Rich markup and printed the line without it, which for an LLM action's error is often the only place the action is named. A closing tag that matched no open one, which an error quoting record content or a provider reply can hold, replaced the line with a traceback of about twenty lines and lost the error and its record detail. Text an event carries is now printed as text; the formatter's own colour is unchanged. `agac dispositions --quarantined` and the plan `agac retry` prints before repairing had the same flaw in their reason column, where a failure reason holding a closing tag raised instead of printing the table, and `agac retry` exited before any repair began; both print it as text now. The log files already kept the full message and are unaffected.
* Under batch, a guard UDF's write to its input now fails the whole action wherever it happens -- on a later prepared row, or during a retry round's preparation -- not only within the pre-submit preflight's first few rows. Online already failed the action the same way for the same data; batch now matches it instead of silently completing with just that one record failed.
* Three example tools read input they were not handed, so every read fell to its default and the run still reported success. The `contract_reviewer` FILE tool read each clause under its action's name: its report named the contract "unknown", rated every clause low and numbered every obligation clause 0. It now reads the flat keys a FILE tool is handed, and the action observes the clause number and title it reports. It also writes one report per contract: a file of several contracts was reported as one, under the first one's name. The `incident_triage` record tools read their fields as bare keys, so every incident was routed as SEV3 against an empty roster and formatted as "Unknown Incident", SEV5, with no teams; each field is now read under its action, and the seeds under `seed`. The examples' READMEs are corrected where a block named an action it did not depend on, guarded on a field with no action name, or showed a FILE tool returning a plain list of new rows. The docs-block test now reads the examples' pages too, checks `drop` and `passthrough` names, and no longer excuses those docs blocks.

Both the per-file summing and the guard-skip count now also work for batch, which previously had no file identity to key its events by at all.
* A record a guard could not be evaluated for (an unregistered UDF name, say) now fails alone instead of failing the whole action. The per-record guard pre-filter used to let any exception other than one specific type escape and kill the whole pass, so every other record, including ones the guard would judge cleanly, went unprocessed with no outcome recorded for it.
* Online now carries a guard-skipped record's content and target_id into the failed row enrichment refuses it with when the record has no source_guid, the same as batch already did. The guard-skip tombstone carried neither before, so the stored row kept nothing of what the record arrived with.
* A prompt field named items, keys, values or get now reads its value instead of the dict's own method of the same name, in both the per-record and load-time renderers. Dot access on such a field used to silently send the model a string like '<built-in method items of dict object at ...>', and a for-loop or length filter over it raised a TypeError the error handler couldn't name, both with no indication anything was wrong.
* `agac inspect action` and `agac inspect context` print a prompt, a guard clause, a model name, action names and schema field names as written. They were printed through Rich markup, so a prompt holding `[INST]` and `[/INST]`, as a Llama-style prompt does, lost the tags or raised `MarkupError` and showed a traceback in place of the action. The helper that escapes field names in the same command also put a backslash before every `]`, which printed as a stray `\`; it now escapes only what Rich reads as a tag.
* `agac preview` prints a record key that holds brackets as its column header. The cell values were escaped and the headers, which are the record's own keys, were read as markup: a key holding a closing tag raised `MarkupError` and a key such as `[note]` printed a blank header.
* The starter templates no longer name vendors that do not exist. `agent_actions.yml.template` listed `deepseek` and `perplexity` as supported vendors with examples, and `workflows/multi-vendor-workflow.yml` used both on live actions, but no provider exists for either and the load refuses both names, so a project begun from that workflow failed to load. They now use `cohere` and `ollama_cloud`, and a test loads every vendor the templates name.
* What a `templates/` file reads from another no longer depends on what the files are called. The folder was loaded in the order the filesystem listed it, and each file saw only the names of the files loaded before it, so a macro calling another file's macro failed the load (`'house_length' is undefined`) or worked depending on the file names, and a file included or imported without context rendered another file's variable as nothing. Every file now reads the macros and variables of the whole folder: each file's top level runs once, after the files whose names it reads. Where two files define the same name, the one from the file that ran later is used everywhere, as the warning says.
* `{% include 'p.j2' without context %}` now yields the file's text wherever it is written. Inside a macro, calling the macro printed `<generator object root.<locals>.macro at 0x...>` into the prompt, and inside a `{% set %}...{% endset %}` block, a `{% call %}` body or a `{% filter %}` block the text was lost, with the load exiting 0 either way. This is how Jinja compiles the tag; the load now compiles it so the text reaches whatever collects it.
* `agac inspect action` now lists every dependency of a fan-in as an input, e.g. `left, right  (merge of 2)`, instead of naming the first one the input and the rest context. A run has always read every dependency and merged their records by source record whatever the order; the docs that said the first dependency drives the execution count now describe that. `agac inspect action --json` reports the same: a fan-in's `input_sources` hold every dependency, its `context_sources` only actions named in `context_scope` or the prompt, and its `type` is `Merge` rather than `Transform + Context`.
* A fan-in over a branch that returns several records per input now pairs each of them with the other branches' record for the same source, so the action runs once per split record with every branch's fields. It ran once per record of each branch instead, each run holding one branch with the others' fields empty, and the run reported success. A source a guard filters out of one branch drops the other branch's records split from it too. Two branches that both split the same source record now fail the fan-in with a message naming them, rather than run on records that hold one branch alone.
* A record that runs out of expectation iterations under `on_exhausted: fail` now reads the same in both run modes. Online stores it `exhausted` and left the action reading `completed`; batch stored it `failed` and read `completed_with_failures`, so whether a run reported a failure at all depended on its mode. Batch now stores the record `exhausted` with the same `expectations_exhausted` tombstone online writes, and an action's status counts every failure `agac retry` selects, so an action holding an exhausted record reads `completed_with_failures` (`failed` when no record succeeds) in either mode. This also applies to records exhausted by retry, which an action used to ignore when reading itself complete. (#1282)
* A batch action that splits records into several rows no longer keeps a failed record's earlier rows. After a reset, a record sent again that failed beside an answered record of its file was stored as its failure plus the rows it split into before the reset, and the actions reading it answered those old rows again, for a record whose disposition read `failed`. Batch now writes the failure alone, as online does, for an exhausted record too.
* An expectation's `on_exhausted: raise` is now recorded as a halt in both run modes. Online, the node-level failure was written without the halt marker, so the next plain `agac run` reset the action and called the model again, only to reach the same deterministic halt. Under batch the error was not recognised as a halt at all: no node-level failure was written, the record that broke its rule was stored as a success beside the others, and the next plain run completed with nothing sent and handed that record to the action below. The error now carries the `on_exhausted: raise` tag wherever it is built, so the run holds the halt and points at `agac retry` or `--fresh`; and batch stores the records the policy stopped at as `exhausted`, so a resumed `agac retry` asks for them again. (#1280)
* A batch file whose input is now empty no longer keeps what its last batch left behind. The file was stored empty, but its failed or cancelled registry entry, context map, recorded inputs and recovery state stayed, so the action went on reading as owed a batch for records that no longer exist. They are removed when the file is stored empty, as a reset removes them for the whole action.
* Under batch, a FILE tool or HITL action now quarantines a record that an action above it failed, as online does. The row batch stored for a record the provider failed (an error row, a processing error, an empty answer under `on_empty: warn`) had no `content`, where online's failed row keeps the record's content and nulls the failed action's namespace. A FILE tool's or HITL action's `context_scope` pass runs before the cascade filter, found no namespace for the failed action in that row, and dropped the record as `observe_field_missing`, which points the author at their own `context_scope`; the action below it stored nothing for the record. Batch's failed row is now online's tombstone, with the provider's message, the raw answer and the recovery metadata kept on it, so the record is `cascade_skipped` with an `unprocessed upstream_unprocessed` disposition at every action below, and `agac retry` answers it at each. (#1363)
* A guard or WHERE clause that compares a field to a string containing a blocked word, such as `status == "open"` or `type == "file"`, now loads. The blocked-word check read the clause's raw text, quoted values included, so these were refused as a "potentially dangerous pattern". A quoted string is a value and is no longer checked; the same word outside quotes, as in `open(x)`, is still refused.
* A batch retry or repair round is now prepared the way the first submission was. The first submission gave its task preparator the action's version and the run's `workflow` metadata. A retry round had the version but no workflow metadata, and a repair round had neither, so a prompt reading `workflow.*` (or `version.*` on a repair round) could not render and a guard reading them could not be evaluated. A retried record whose prompt read `workflow.*` was dropped as unrendered while the action read complete; on a repair round the collect pass failed the action, and every later run paused on the same finished batch and failed again. The prompt traces of those rounds were written with a NULL `run_id`. One builder now serves both rounds, and the collecting run's metadata is carried from the executor through the collect pass to every round, so `workflow.run_id` is the id of the run that collects the batch.
* A record that leaves a file while its batch is out is no longer written into that file when the batch is collected. A run that finds the file's batch in flight, or finished and not yet collected, does not send it again, and the collect wrote the inputs recorded when it was sent, so a record removed from staging in between was still stored. Such a run now records the file's current inputs, and the collect leaves out the answers to records no longer among them, as an online run holds only the records its file has. A run that only collects does not read staging again, so this covers a run that resumes after a collect pass stopped or a status check was interrupted. A file that every record has left while its batch is out still holds the batch's answers.
* A first-stage batch action no longer leaves a placeholder file on disk. Submitting a staged file wrote one at the action's folder joined with the file's relative path again, so a file in a subdirectory left `target/<action>/sub/sub/page.json` behind after its batch was collected, which a reader of the target folder took for a batch still out. The batch registry already marks a batch in flight, as it does for every later action, so the placeholder is no longer written.
* Under batch, a halt raised during the collect pass no longer leaves another file's finished batch uncollected. `on_exhausted: raise` (a retry that spent its attempts, or a repair loop that did) stops the run, but the collect loop stopped at the entry that raised, so a sibling file's finished batch stayed in the registry with its records deferred and its file unstored. A plain `agac run` refuses a halted action, and `agac retry` refuses while a finished batch is uncollected, so the only way on was `--abandon-in-flight`, which marks the sibling's records failed so a later retry sends them again, paying again for answers the provider had already returned. The pass now collects every file, then raises the first halt and logs any other.
* After a batch collect pass stopped on an ordinary error, `agac retry` printed a green "Nothing to retry" and exited 0 while the action read `failed` and a file stayed unanswered. The error left the action failed with no failed record: the executor re-raised it without the node-level failed row every other action failure writes, and `retry` looks for failures only in the disposition table, so it returned before it checked for the finished, uncollected batch the failed pass left behind. The executor now writes the row, and `retry` settles an owed batch, or names a failed action, before it reports nothing to retry. Stores written before this hold the failure with no row, and retry now refuses those too, with the existing remedy: run the workflow again to collect the batch, then retry.
* A record nested hundreds of levels deep no longer fails a batch run. The run failed with "maximum recursion depth exceeded" for a record about 600 levels deep, and every later run submitted again and failed again. `copy.deepcopy` recurses once per level and breaks at about 500 levels, and a batch run copies the record while it prepares the task (applying the action's `context_scope`), and again for the snapshot kept with each result built for a record a guard turned away, an empty answer, or a record the provider did not answer; a FILE tool that returns nothing snapshots its input records the same way. Those copies now use the non-recursive copy that guard evaluation already uses. So do the other copies of record content that a deep record reaches: the storage read cache, which a downstream action hits when it reads the rows above it, passthrough merging, `update_schema_objects`, and the envelope an action's output is wrapped in. A record's identity was derived by a check for string field names that also recursed once per level and failed at about 800 levels in every run mode; it now walks the record on a stack. A record is identified, copied and collected at any depth the standard library's JSON encoder accepts, about a thousand levels on Python 3.11.
* A batch file that every record leaves while its batch is out is now stored empty when the batch is collected, as online stores it. The run that finds the batch out records that the file takes no input, so the collect writes the file empty instead of with the batch's answers to records it no longer has. The run still waits for the batch, as before.
* A batch collect pass no longer fails, and the action no longer never finishes, when a lost record's first retry admits no task. When a batch result lacks a record and retry is on, the collect pass rebuilds that record's task; if preparation admits none (a guard decides differently when the record is prepared again), `RetrySubmissionImpossible` was raised. Later retry rounds treat it as exhaustion and finalize the file, but the first round let it out of the pass, which failed the action. The next run reset it, found the same finished batch still owed, and paused, and the run after that failed again, so none of the file's records were stored. The first round now gives those records up as later rounds do, under the action's `on_exhausted`, and finalizes the file. A repair round had the same gap from the other side: `submit_repair_batch` sent whatever preparation admitted, even nothing, so an empty batch went to the provider and the next pass failed every record of the round. It now submits nothing when no task is admitted, and the records are given up under `on_exhausted`.
* Three batch fixes. A repair round reports as sent only the records preparation admitted: a record a guard turns away at preparation is given up under the action's `on_exhausted` in the same pass, instead of being failed as one the provider dropped when the round comes back (1465). The `on_empty: error` and `terminal_failure` halts are raised once the collect pass has read every finished batch, as `on_exhausted: raise` already was, so a sibling file's results are stored in the same run (1464). `agac retry --abandon-in-flight` abandons an owed batch once, and prints its message once, when no failed record is recorded (1469).

A record carried from its checkpoint is stored with the `_recovery` it earned, where before it was stored with `_recovery: null` (1320). A retry resuming a halt in full notes what the run found and answered for the records it cleared, so one in a file that fails during the resume is reported by that failure, and one a FILE tool answered with invented rows is not put back as failed (1329). Load-time pruning did not count a version base's branches, or the actions above them, as upstream, so it removed every such drop without a word and the dropped fields reached the tool or the prompt, online, in batch and under `agac retry` (1293).

The repair rewrote the file with only the rows it could match by `source_guid`, so the row, the only record of the refusal besides the run log, was deleted while the action read complete (1299).

* A prompt-store prompt that calls `load_prompt`, as the prompt-store page shows it, sends each record the loaded prompt filled from that record, online and batch. Before, a `$` reference to such a prompt failed every record with "'load_prompt' is undefined". Each `{{ load_prompt("file.Prompt") }}` tag in a store prompt is now replaced by that prompt when the workflow loads, recursively, so the same holds for a prompt loaded by another, whether from the store or from an inline prompt. Prompts that load each other in a cycle, and a call written other than as a tag of its own with a quoted name, fail the load naming them instead of failing every record (1371).

Batch's pre-flight renders the first prompts of an action before anything is sent, and stopped the whole action when the first record it tried lacked a field it observes, held a value nested too deep to print, or lacked a variable the template names; `agac retry` of such a record, which hands the action that record alone, could never finish. Pre-flight now passes over such a record to the next, and the run fails it with its reason and answers the rest. The ollama SDK raises every HTTP error as `ollama.ResponseError`, which was taken for a non-retriable API error, so such a record was failed at its first attempt. The batch id is in the batch events' `data.batch_id`, as before (1482).
* An LLM action that observes a field nested about 1000 levels deep or more now runs on Python 3.11, online and in batch, and a prompt can render such a field with `| tojson`. Building the request used the recursive JSON codec and a recursive JSON-safety pass, which raised `RecursionError` at that depth and failed the action; each now handles any depth and gives ordinary records the same request text as before. A prompt that prints such a field with a bare `{{ }}` (Python's `str()`, which has its own recursion limit) fails that record with a reason naming the field, its depth and the limit, instead of failing the action with an empty "references undefined variables" message (1483).
* A prompt that reads a field of an upstream namespace the record has no data for still fails that record, but the error now says what the record shows instead of "Namespace 'X' is null (likely guard-filtered or guard-skipped)" in every case: a guard on 'X' skipped the record (named only when the record's state history shows that skip), 'X' wrote null without one (or only that it is null, when the record's history cannot rule a skip out), no output of 'X' reached the record, or the output of 'X' holds none of the fields the action observes from it (naming the observed fields and the ones it has). The field is no longer also logged as a namespace that "nothing supplies" (1489).
* A fan-in whose branches each split the same source record now fails whatever number of records each branch keeps. It failed only while every branch held two or more records of the split, so a branch that kept one (a guard filtering the rest below the split), or a branch splitting a source beside branches that read an earlier expansion of it, ran the fan-in once per record with the other branches' fields empty, and the run reported success. So did a branch whose split a granularity: File tool gathered back into one record, which keeps a split record's identity rather than the source's. The error names the branches and the source record, and advises splitting the source once upstream of every branch; it no longer advises the File tool, which does not pair. Branches below one earlier split that share no record of a source at all (each lacks every record the other holds) fail the same way now, rather than run each record with the other branch's fields empty. (#1439)
* The dag-fit pre-flight warning no longer reports a tool's required output fields as having no upstream guarantee, and as rejected at runtime, when it cannot read what the tool returns. A tool whose output is built by a helper, appended in a loop, spread from another dict, returned as a list, or whose UDF cannot be found is no longer checked, and the fields inside a key the tool writes are the tool's own. An annotated initialiser such as `out: dict[str, Any] = {...}` is now read like `out = {...}`. A tool whose output the check can read and which leaves out a required field, such as a FILE tool with a literal `FileUDFResult`, is still reported. Four shipped examples lose a warning they printed on every `inspect` and `run` (1436).
* A HITL action over a record nested about 1000 levels deep or more now opens its review and stores the reviewer's decisions, online and in batch. The HITL provider decoded its context, fingerprinted it for saved reviews, redacted secret keys and served it to the review page with the recursive JSON codec and recursive walks, so the action failed with a bare `RecursionError` before anyone saw it; each now handles any depth, and an ordinary record is served and fingerprinted as before, so saved partial reviews still resume. The review page shows a value too deep for the browser's `JSON.stringify` as compact JSON instead of breaking the page (1487).
* `agac retry` naming a row that an expansion made no longer duplicates the rows an expansion below it made of that row. Those rows name the staged record as their parent, which is no input of the action below, so the retry carried them and wrote two new rows beside them: 24 rows became 26, exit 0, with only a "cannot be attributed" warning. The same happened where an action reads both a record and an expansion over it. A row minted from records the retry named, and from no other, is now placed by the inputs it lists as its producers and replaced. A row keeping an input's own identity is never placed this way. Rows that list no producer, or were made from a named record together with others, are still carried and reported. (#1505)
* Pre-flight no longer refuses a prompt that calls a dictionary method on an upstream action. The prompt-store docs' `{% for key, value in merge_alternatives.items() %}` example, and `ns.keys()` or `ns.values()`, were refused with "Field 'items' not found in action ... output schema" when the schema had no field of that name. Such a call now names no field. `ns.get('field', default)` is checked against the action's schema as `field`, as `ns.field` is, so a misspelt field is still refused before the run. A bare `ns.items` is still read as the field `items` (1506).
* The HITL review page shows a value nested more than 50 levels deep as compact JSON in its JSON view. It indented every value, and indented text grows with the square of the depth: a record nested 2,000 levels made about 8 MB of text and took seconds to render, enough to freeze the tab. An ordinary record is shown indented as before (1497).
* The dag-fit pre-flight warning now names every required output field a tool's code does not return, even when an upstream action's schema requires a field of the same name. A tool's output is validated exactly as its UDF returns it: upstream fields reach the tool as input, and `context_scope.passthrough` fields are added beside its output after it is checked, so neither supplies the field. A FILE tool returning a literal `FileUDFResult` without `id` below an action that requires `id` used to pass pre-flight in silence and then fail every record; `agac inspect`, `run` and `retry` now warn, naming the action, the field and the tool. A store error while it read its versions, or version records it could not align, ended a sequential run at once with every other branch left pending, and in a parallel run left the merge marked running, so the action that reads it ran against nothing and failed instead of being skipped (1478).
* Pre-flight reads a tool's output dict the same way however it is first written. A RECORD tool that set a required output field only inside an `if` was refused when its dict started as `out = {...}`, but passed when it started as `out: dict = {...}` or `out = dict(...)`, and then failed every record that did not take the branch while the run exited successfully. (#1491)
* A parallel run ends failed, as a sequential run does, when an error keeps an action from starting its work, such as the store failing while the action is set running or while its rows are counted before it runs. In a step of several actions the error was logged and the run went on: the action was left `running` (or `pending`), the actions reading it ran against output it never wrote and failed on that, and the run ended "paused … Run again to continue" with exit 0. The actions already running beside it now finish, then the run stops with a non-zero exit and the error; the action is recorded failed (or left pending, when it was never set running) and nothing below it runs. Run again once the store answers. Failures inside an action's own work are unchanged: the action fails, its readers are skipped and independent branches carry on. (#1508)
* A fan-in that reads a splitting action and an action that splits that action's records again now pairs each record of the second split with the first split's record it came from and with the other branches' record for their source. With the second split listed before the first in the fan-in's dependencies, it ran once per record of the first split with the second split's fields empty and every record of the second split dropped, and the run reported success; listed after, it failed saying the two branches each split the source on their own. * Pre-flight no longer refuses a RECORD tool that sets a required output field on every path that returns. Such tools used to be refused although every record they return has the field. A tool whose dict is filled in a way pre-flight cannot follow, such as `out.update(build(data))` or `for field in FIELDS: out[field] = ...`, is no longer refused either; its records are checked at run time. dag-fit reads a tool's output the same way. * An action with no `dependencies` that names an upstream in its `context_scope` is no longer told its guard reads a staged row. `prep IS NOT NULL` is again refused for `prep` not being upstream through its dependencies, and a bare `score > 0` suggests `prep.score`, not `source.score`. A first action's own name is not suggested under `source` (#1535).
* The `logging:` block in `agent_actions.yml` is loaded. `level`, `module_levels`, `file.max_bytes` and `file.backup_count` configure every command run in the project, with a set `AGENT_ACTIONS_*` variable overriding its own key and the `--debug` / `--verbose` / `--quiet` flags overriding both; before, the block was accepted and configured nothing. A key under it that nothing reads (`file.path`, `file.enabled`, `file.level`, `file.format`) is reported on stderr at boot instead of being parsed into a field no handler looks at. A run's re-initialisation of the logger factory keeps the resolved config instead of rebuilding it from the environment, which would have dropped the project block again. A project file the CLI cannot read at boot is reported on stderr and the default logging config stands, so `--help`, `--version` and `agac init` still run; the commands that read the project fail on it as before. A project file whose top level is not a mapping is now refused by the loader with its type named, instead of every reader failing on an AttributeError. (#1553)
* Preflight refuses `base_url` on an `anthropic`, `gemini`, `groq` or `cohere` action. Those clients always call their vendor's own endpoint, so the field was accepted and ignored, and a request meant for a local server went to the cloud vendor (#1564).
* A retry that reaches a `granularity: File` tool hands it the whole file, and every action below it answered every record of the file again, whether or not the tool wrote the record's row differently: below a flatten or a merge, a few failed records made every action reprocess the whole dataset. A row the tool writes again exactly as it was is now the row it was, identifiers and all, and the actions below keep their answers for it; only the records whose rows changed are answered again. The retry plan names each FILE tool in its range, and the actions reading it that answer again what the tool writes differently, before anything is cleared. (#1551)
* `agac run --verify-keys` reads `api_key` as the name of an environment variable, as a run does, and probes with that variable's value. It no longer probes with the name itself, or with `**********` when the value comes from configuration, and it reports an unset variable as missing (#1563).
* A retry reaching a `granularity: File` tool that writes several rows per record, or a roll-up, answered every record of the file again below it, because each such row is minted a new identity every run and none matched the row stored before. Such a row is now matched to the stored row holding the same, the records it was made from included, and takes back that row's identity, so the actions below answer again only the rows that changed. (#1566)
* `AGENT_ACTIONS_LOG_FILE`, `AGENT_ACTIONS_LOG_DIR`, `AGENT_ACTIONS_NO_LOG_FILE`, `AGENT_ACTIONS_FILE_LOG_LEVEL` and `AGENT_ACTIONS_LOG_FORMAT` were accepted and changed nothing: the run log is always `<output_dir>/logs/events.json` at DEBUG. The CLI now names each one that is set on stderr at boot and ignores it. `LoggingConfig` loses the fields they filled (`include_timestamps`, `include_source_location`, and `enabled`, `path`, `level` and `format` on `FileHandlerSettings`), which nothing read. (#1569)
* When `agac retry` resumes an interrupted retry, it now lists each live disposition row the restore will replace with a different value, live value first, and names the manifest to edit to keep the live value. This holds for `--dry-run` too. Before, a row changed by hand after the interruption was overwritten with no sign of it (#1549).
* An invalid `logging.module_levels` entry in `agent_actions.yml` (e.g. `httpx: LOUD`) was reported on every logger init: twice on `agac inspect` and three times on `agac run`. It is now checked when the CLI resolves the `logging:` block, reported there once and dropped; the logger factory still reports a bad entry in a `LoggingConfig` built in code. (#1568)
* `llamafile` now appears in the generated docs vendor list and in the `model_vendor` help text. Both lists, and the expander's list of valid vendors, now come from one `vendor_names()` (#1577). `run_mode: batch` on a vendor that cannot batch (`llamafile`, `cohere`) is now an error in the action entry check too, with the same text as preflight: "vendor 'V' does not support run_mode: batch. Set run_mode: online." Previously that check only warned that the vendor "may not support" batch. Both checks read the client's `supports_batch`, and the hard-coded batch vendor set is gone (#1578).
* A `llamafile` action's request, response and error events now name `llamafile`, not `openai`, so run stats and the docs catalog report the right provider. Token usage is still read with the OpenAI usage shape (#1584).
* A `tool` or `hitl` action no longer gets a batch error or warning when its workflow defaults to `run_mode: batch`. The pipeline always runs these actions online, so `kind: tool`, `kind: hitl`, `model_vendor: tool` and `model_vendor: hitl` now pass the entry check and preflight under batch. Their clients now report `supports_batch: false` (#1585).
* A `tool` action that sets `run_mode: batch` itself now loads instead of being refused, and a `tool` or `hitl` action under batch now runs as an online action on every path: a first action is staged online, its completion and execution time are recorded, its events and progress are not labelled batch, and a judged `context:` rule on it is no longer refused (#1585).
