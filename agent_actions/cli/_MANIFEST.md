# Cli Manifest

**[> Architecture Deep Dive (ARCHITECTURE.md)](ARCHITECTURE.md)** -- bootstrap flow, decorator stack, error propagation, command execution flows, caveats.

## Conventions

- **Read-only commands** (inspect, schema, status, preview, traces) must pass `auto_create=False` to `ProjectPathsFactory.create_project_paths()` and omit `output_dir` from `ConfigRenderingService().render_and_load_config()` to avoid filesystem mutations.
- **Write commands** (run, init, compile) use the defaults (`auto_create=True`, explicit `output_dir`).

| `run.py` | Module | Run command for the Agent Actions CLI. It holds the workflow's run lock (`storage.run_lock.hold_run_lock`) from right after the project paths are built to the end of the command, before `load_workflow` (which `--fresh` clears the store in) and the prompt check after it, so a second run is refused before it loads, clears or submits anything. `execute(holding_the_lock=...)` runs the command inside that context manager, entered once the lock is held and exited before it is released, however the run ends; it is not entered when the lock is refused (`sandbox check` notes the status file on entry and reads its result on exit). `--record-limit` and `--file-limit` bound every action for the run — records per input file and input files per action — carried on the runtime config and stamped onto each action config so the per-action limit resolver reads them. `--rerun` may be given more than once; every action it names, and each action reading one, is answered again in the one run. It classifies the finished workflow with `exit_codes.classify_outcome`, prints the sentence for that outcome and exits with its code (0, 1, 3 or 4), never reading the code from the sentence. `--wait` (`RunCommand._wait_for_batches`) repeats the pass a second `agac run` makes while the outcome is `PAUSED_FOR_BATCH`, sleeping `--poll` seconds between passes through the `sleep` the command was built with (`_poll_seconds`: `--poll` when given, else 60 in a real run and `config.sandbox.wait_between_passes()` in a sandbox run, which is no wait, or up to 1 second while the scenario holds a batch for `complete_after_seconds`; a pass after no wait prints `Checking the batch job(s) again...`), and stops at `--wait-timeout`, counted from before the first pass, with exit 4 and the time it waited; a `PAUSED` outcome with no open batch is not waited on and says so; `--poll` is a whole number of seconds, at least 1; the last sleep is cut to the time left, the printed wait is the time slept, and no pass starts once the timeout has passed; the later passes drop `--fresh`, `--rerun` and `--verify-keys`, and the run lock is held from the first pass to the last. | `retry.py` | Module | Retry failed/exhausted records from a specific action forward. Unless `--dry-run`, it holds the workflow's run lock for the whole command, taken before the store is opened; `--filter` (`retry_filter.py`) takes it the same way. A workflow with no store (`config.sandbox.store_file`, so `<workflow>.sandbox.db` under `--sandbox`) is refused first with exit 1 (`refuse_without_a_store`, "No store for workflow ..."), with or without `--dry-run`, `--all` and `--filter`, so no empty store is created. Its plan counts and lists records only: an action's `__node__` failure is shown on its own "Action status" line, not as a record. Below the plan it names each FILE tool in its range (`replaces_its_file_whole`): the retry hands such a tool every record of each file holding a listed record, and the actions in its range below it in the stored dependency graph (`repair_lineage.actions_below`, what the run clears by) answer again every record whose row the tool writes differently (`_note_file_tools`). Names the records it is re-running on the run, so a record limit admits them rather than cutting them loose and no file limit stops the walk before it reaches one. Classifies the finished workflow with the classifier `run.py` uses (`exit_codes.classify_outcome`) and exits with the same codes: 1 on a failed action, 3 while an action holds a failed or exhausted record, 4 when it submitted a batch, 5 when a provider's quota stopped its re-run (`ProviderQuotaStop`; its manifest stays, as after an interrupt, so the next retry resumes it). A failed action holding no failure row and owing no batch failed where the store could not record it: the retry writes the node-level failure it would have stored (reason: its status's `error_message`; a dry run writes nothing) and re-runs it in full. Refuses, before it clears anything, while an action in its range holds a batch nobody has collected: one still out, or one that finished and still holds a record nothing has answered (the repair clears the registry entry, which is all that names it). That is asked of the batch's records, read from its context map: one whose disposition is `deferred`, or which has none. `--abandon-in-flight` goes ahead and marks those records failed, so a later retry can still reach them. A record the batch holds without a `source_guid` is neither waited on nor marked: under its custom_id it would be a failure a later retry clears and cannot select. Refuses too, before the batch refusal, to narrow any action in the workflow (the run executes whatever is not complete, before its starting point as well) that holds no answer for some record — pending, running, interrupted, stopped while collecting, completed with its output gone, or failed by anything but reaching all of its input — since a plain run finishes it. A failure that reached all of its input (`EVERY_INPUT_FAILED`, or a batch action whose batches hold an answer or a failure for every record sent with a `source_guid`) is still refused while the action holds a row for a record that run did not reach (`target_row_identities` against its dispositions). Not refused: an action an interrupted retry put back to pending, which had finished before it — read from the `REPAIRED_BY` stamp that retry wrote beside the status, matched to its manifest's `created_at`, which a reset removes; an action holding an uncollected batch, and its readers, which the batch refusal decides; and a halt by `on_exhausted: raise` the retry does not clear, which stays halted. A halt it would clear is refused even then, naming a retry from the halted action: one starting at a halt without `--record` names no record and runs that action, and every one after it, in full (halts read from the failures it plans over, `_halted_among`). An interrupted retry's snapshot goes back only on the actions it stamped, and only while one of them has not completed or its manifest is a finished re-run's `put_back`; its starting action's record failures go back even where it completed, since the next retry starts from them, but a node-level failure never goes back on a completed action, which a plain run would run again over its readers. Before it looks for failures, it writes, at each completed action, the dispositions a collect pass stored rows for but left `deferred` because the store refused them (`managers.batch.lost_dispositions`), so a failure among them is found; nothing is submitted again, and a dry run plans over them unwritten. `--dry-run` restores nothing and keeps the manifest, planning over the snapshot as if restored. A retry that restores keeps the manifest and its notes until it writes its own, so one refused or finding nothing to do leaves the interrupted retry resumable. A `--from` below the interrupted retry's starting action, while an action it put back to pending has not completed, is refused before anything is restored (`_refused_below_a_stopped_retry`; a dry run reports it). After the re-run, a record the starting action never answered (`answered_by_repair`: found in a file processed to the end) and wrote nothing for gets back what was cleared for it at each action that did not decide it again, those actions are read again, and the record is named with a remedy that depends on whether it was in the input (`found_by_repair`), whether the action finished, and whether it was skipped below a halt the retry does not clear (then the retry from the halted action is named). Clears checkpoint rows only for the records whose dispositions it clears (`_clear_for_the_rerun`): a record keeping its `success` keeps the answer the row is, so a resume carries it and a `--rerun`'s replacement is answered again. Keeps what its re-run notes below each split it re-runs in `_retry_repair_notes.json` beside the manifest (`repair_lineage.keep_notes_at`), deleted with it; resuming an interrupted retry, it notes them again for the actions that retry put back to pending and never completed (`_not_run_since_an_interrupted_retry`), so their rows built on what the stopped retry's split replaced are taken out. A retry whose re-run ends in success or record failures writes the declared `outputs:` tables with `run.write_declared_outputs`. Given a `RecordFilter` (by `run.rerun_selected_records`), the plan is the selection alone: the records the filter matches at `--from`, failed or not, over that action and what reads it (`actions_below`), not every later action. Unless `--dry-run`, it holds a `knowledge_run` for all its passes. | `cli`, `storage`, `validation`, `llm`, `processing` |

Refuses an id that names no record, an expression no record can evaluate, and a row that traces to no input record. `read_record_ids`, `refuse_an_expression_that_does_not_parse`.
