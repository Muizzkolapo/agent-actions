# Workflow Parallel Manifest

## Overview

Helpers for parallel action execution, dependency tracking, and action-level
scheduling.

## Modules

| Name | Type | Description | Signals |
|------|------|-------------|---------|
| `action_executor.py` | Module | Executes actions concurrently while honoring dependencies. `compute_execution_levels` and `upstream_actions` read the same `dependencies`, a version base expanded to its versions, without writing the expansion back to `action_configs`. `upstream_actions(levels)` gives each action its ancestors through `dependencies` in the order the levels run them, which the coordinator stores as `dependency_graph`: not every action of an earlier level, since one beside an action or under another start node never reaches its records. Step boundaries are fired as events, not printed. Each action runs inside `EventManager.context(action_name=..., action_index=...)`, entered within its own gather task, so every event it fires, from `asyncio.to_thread` workers too, names it while the step's other actions run; nothing sets the action with the shared `set_context`. An action's failed result is logged and left to the circuit breaker; an exception that escaped an action's run (a store error setting it running or counting its rows) is re-raised by `_end_level_on` once the step's other actions finish, an interrupt before an error, so it ends the run as it does in sequential mode. A `ProviderQuotaStop` an action raised is re-raised the same way and is not logged as a failed action. `in_flight` holds the actions of the level last started, narrowed to the actions that raised when a step ends on one, which the coordinator names as the failed action when a parallel run dies. Its `ActionCompleteEvent` carries `guard_skipped` from the result's metrics, as the sequential path does. And `checks_failed`. `ActionCompleteEvent.cases` carries a built-in router's rows per case. `LevelExecutionParams.batch_preparation_concurrency` (the workflow key, None when unset) limits the batch actions of a step that prepare at once with a second semaphore, taken before the step's `--concurrency-limit` semaphore so a batch action waiting its turn holds no slot an online action could use; a batch action whose status is `batch_submitted` collects and is not limited, nor is any online, tool or hitl action. The slot is held for one `execute_action_async` call, and for a batch action that prepares, that call prepares and sends the batch and returns `batch_submitted` without waiting for results (`ActionExecutor._execute_action_run_async` reads the registry, it does not poll the provider); `--wait` waits between whole passes, outside every call. Its `ActionCompleteEvent` carries `stubbed` (`config.sandbox.stubs(action)`), as the sequential path's does. | `asyncio`, `workflow`, `llm.config` |
