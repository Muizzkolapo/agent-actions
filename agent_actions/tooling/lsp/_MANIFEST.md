# LSP Manifest

## Overview

Language Server Protocol helpers that index agent workflows/prompts/tools, resolve
references, and expose hover/definition/navigation for editors.

## Modules

| Name | Type | Description | Signals |
|------|------|-------------|---------|
| `models.py` | Module | Data models (`ProjectIndex`, `ActionMetadata`, `PromptDefinition`, `ReferenceType`, `Location`, `ParseError`) describing references, workflows, prompts, schemas, and tools. `ReferenceType.CONNECTION` names a connection; `ProjectIndex.connections` maps each name in the project file's `connections:` block to its line, or is None while that file does not parse. | `lsprotocol`, `pygls` |
| `indexer.py` | Module | Scans workflows/prompts/tools/schemas, builds `ProjectIndex`, and reads each workflow from its render (`jinja_source`), so a workflow that imports macros keeps its actions; a workflow that does not render goes into `ProjectIndex.parse_errors` with no actions. The line pass skips the lines the render dropped, takes a `- name:` line as an action only where the render defines one, gives a line to the action above it only when the render puts its text there (`line_owners`; a `call` or `include` tag can output another action), closes each nested block (`dependencies`, `context_scope`) at a skipped line that can output text, takes a reference only where the render puts its line under the key its type reads (`line_paths`), sets no `impl`, `schema` or `prompt` value from a line that holds a Jinja tag, records no reference on a line that holds a Jinja tag, and takes no action whose parsed name is not a string (`name: yes` is True in PyYAML). Builds and records metadata used by navigation and hover. Provides `find_all_project_roots()` for multi-project workspace discovery. Action values (`guard`, `context_scope`, `output_field`, `versions`) come from the PARSED document; the line pass supplies only positions and reference ranges. `output_field` defaults resolve workflow `defaults:` then `agent_actions.yml`'s `default_agent_config`. Guard-language keywords come from the operator registry. Uses `get_tool_dirs` from `path_config`. A `schema: dispatch_task('fn')` value is told from a schema file name by `schema_dispatch_function`, the test `agac inspect` and `agac run` use, so it records no schema reference. The outputs of each branch a workflow includes (`branches/<name>.yml`) are indexed as actions of that workflow (as `<as>__<name>` for an include with `as:`), located in the branch file, so a read of one resolves; a branch action that is not an output stays undefined. A `- loop:` entry indexes no branch output: `_index_entry_actions` indexes the name of each `- route:`, `- join:` and `- loop:` entry as an action of the workflow, located at its entry line, with the actions it reads (the `on:` action, `of:`, the loop's `inputs:` targets) as its dependencies. In a mapped Jinja file, an entry line is found only among the lines the render output as written. An optional observe entry is indexed by the reference it names: the `?` suffix is left out of the value and its range, and a mapping entry is read from its `field:` key. `_index_connections` reads the project file's `connections:` block (`project_config_file`), and `_index_database_references` indexes each `outputs:` entry's `action:` as an action reference and each `connection:` under `outputs:` or a `data_source` as a connection reference, only where `line_paths` puts the line under that key. Each `context_scope.retrieve` entry is indexed as the action `<action>__<entry>` at its entry line, reading the actions of its `query` and `where` refs (the parsed lists are not changed); the action's metadata keeps its entry names (`retrieve_entries`). | `ruamel.yaml`, `yaml`, `logging`, `config.schema`, `config.includes`, `input.preprocessing.parsing.operators`, `output.response.dispatch_injection` |
| `jinja_source.py` | Module | `render_workflow_source` renders a workflow file with the Jinja load step of `agac` only (`new_load_render`; no prompt fill, no versions, no file written) and maps each action to the file and line that define it, a template macro line included. The rendered text is read with `yaml.SafeLoader`, the loader `agac` uses. In the data, a value that the load leaves for a version or a record (a guard or `output_field` that reads `i`, a prompt that reads `source`) shows as the file writes it (`LoadRender.written`), never as its private-use token, and the rendered text holds it as one JSON line (`written_text`), so the tree reads the same value; versions are not expanded. `MarkingLoadRender` tags each `name:` line, and each other workflow line outside a tag, with a YAML comment; a name tag is read on the rendered line of each parsed action, and a workflow line whose tag is missing from the output is one the render dropped (`live_lines`). The body of a `set` or `filter` block gets no tag, because a tag would change the text it holds or outputs, and it is not read. A `macro` body keeps its `name:` tags but gets no line tag, because it is output where it is called. A line of a plain scalar that goes on past one line gets no tag, because a comment would end the scalar. A `{% raw %}` line is tagged, because raw text is output as written. A name written as a multi-line `{{ }}` tag gets its tag on the line where the tag ends. A workflow line is live, and has an owner (`line_owners`: the action whose text it is in the render) and a key path (`line_paths`), only where its rendered line, with each left value's first line put back (`written_line`) and tags removed, equals the line as written; a filter, a `caller()` filter or a tag on the line makes it not live. A name tag counts only when it names the workflow file, or a template that exists, at a `name:` line whose written name (if it has no tag) is the parsed name, and when no text follows it on the rendered line. The marked render, with its tags removed, must equal the plain render line for line (lines split where PyYAML splits them); when a tag changed the render, no action gets a source line, and in a file that holds any Jinja tag, no line is read (`action_lines` and `live_lines` are empty). A repeated top-level `actions:` key is read as PyYAML reads it: the last one, and an action's own `name` is read after any `<<:` merge. A YAML error line counts `\n` only, as the editor does. A workflow file that is a `$file.key` prompt reference loads as `agac` loads it (`_load_yaml_content`) and gets no source lines. When the templates/ load fails (a templates/ path that is not a folder included), a workflow file with no Jinja tag (no `{{`, `{%` or `{#`) is read as plain YAML, each action at the `name:` line that writes its name; any other render failure raises `WorkflowRenderError` with a 0-indexed workflow line. | `jinja2`, `yaml`, `errors`, `prompt.render_workflow`, `prompt.deferred_values` |
| `diagnostics.py` | Module | Collects LSP diagnostics: unresolved references, duplicate actions, guard clause validation. A guard reads the record as stored, so a clause is reported only where the file can prove it resolves nowhere: a bare name with no promotion available (suggesting the dotted spelling; at a first action, which names no upstream, `source.<name>`, since its record holds the staged row there), or a dotted reference whose namespace no action in the workflow writes. Which fields a namespace holds is never judged. A versioned action produces `base_1`, `base_2`, ... and not its own name. A workflow in `parse_errors` gets one Error, `Workflow does not render: <message>`. A diagnostic about an action that a template macro defines sits at line 0 of the workflow file and names the template line. A connection reference is reported unresolved only when the project file parsed. A `retrieve.<entry>` reference names the action's own retrieve step and is not reported when the action it is written in (by line, `_reads_own_entry`; in a guard, the action) has that entry; elsewhere it is reported as any unknown action. | `lsprotocol`, `models`, `resolver`, `utils.constants`, `record.envelope` |
| `completions.py` | Module | LSP completion providers for context_scope blocks, guard conditions and `versions:` blocks. `build_guard_completions` delegates to `collect_available_guard_variables` for variable list; `build_versions_completions` reads `VersionConfig.model_fields`, so the editor cannot offer a key the loader refuses. | `lsprotocol`, `diagnostics`, `config.schema` |
| `resolver.py` | Module | Detects references at cursor positions (`get_reference_at_position`) and resolves them to file `Location`s (`resolve_reference`). Finds the reference of an observe entry written as a mapping (`- field: a.b`). An `action:` under the top-level `outputs:` is an action reference, and any `connection:` a connection reference, which resolves to its `connections:` line in the project file. | `lsprotocol`, `pathlib`, `utils` |
| `server.py` | Module | `AgentActionsLanguageServer` setup plus LSP handlers for initialize/definition/hover using the indexer/resolver/navigator. The custom request `agentActions/renderedWorkflow` returns a workflow's rendered text and action source lines to the VS Code extension, which cannot run Jinja. It watches the prompt files in `prompt_store/` and each `agent_workflow/*/prompt_store/`, subfolders included, and `templates/**/*.jinja2` and `*.j2`, so a macro edit reindexes. | `pygls`, `lsprotocol`, `utils` |
| `utils.py` | Module | Shared LSP utilities: `uri_to_path()` for URI conversion, `is_in_dependencies_context()` and `is_in_context_scope_list()` for YAML block detection. `is_in_top_level_block()` tells whether a line sits under a top-level key. | `pathlib` |
| `__main__.py` | Entry | Enables `python -m agent_actions.tooling.lsp` invocation. Delegates to `server.main()`. | — |
