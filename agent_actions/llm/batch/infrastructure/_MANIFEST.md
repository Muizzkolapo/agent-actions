# Batch Infrastructure Manifest

## Overview

Infrastructure modules resolve context, job management, and file handling for
batch services that orchestrate runs outside online mode.

## Modules

| Name | Type | Description | Signals |
|------|------|-------------|---------|
| `batch_client_resolver.py` | Module | Returns the appropriate provider/batch client per agent config; with no configured key it falls back to the vendor's own variable from `llm.config.vendor.api_key_env_var`. Forwards the action's `base_url`, `batch_max_workers`, `request_timeout` and `enable_prompt_caching` to the factory, and each set value is part of the client cache key, so two actions that differ in one never share a client. `get_for_batch_id` (retry and repair rounds) forwards the same values and, given the action's config, reuses only the client cached under that exact key, so a round goes to the host and worker count of the first submission. | `llm.providers`, `llm.config` |
| `batch_data_loader.py` | Module | Loads and prepares batched input payloads for processors. | `input`, `preprocessing` |
| `context.py` | Module | Batch context builders and metadata propagation helpers. Persists two things per (action, batch) under storage metadata: the context map (`batch_context:…`), holding the rows that were submitted (encoded with `utils.deep_json`, so a row's nesting depth does not limit it), and the run's input identities (`batch_inputs:…`), holding the input above every narrowing — the record limit and the disposition gate both sit between the two. The context map is stored in parts of about 4 MB (`batch_context:{action}:{file}#{generation}:{index}`, each part a JSON object of whole entries) that the key `batch_context:{action}:{file}#parts` names, so neither a save nor a load builds one string of the map. The parts are written first; one store transaction (`save_and_delete_metadata`) then writes that key and deletes a map saved whole under `batch_context:{action}:{file}`; the earlier parts are deleted last. A save that fails deletes what it wrote and leaves the earlier map as it stood. A load that starts after the switch reads the new map. A load that a save overtakes finds a part gone, reads the parts key again and loads the parts it names now, up to 3 tries; when the parts key is unchanged it names the missing part. Thus a load returns one map whole, or raises. A map an earlier version saved whole still loads, the next save or a delete removes it, and a save never reads it. The parts key and a map saved whole exist together only when an earlier version saved that map after this version saved parts (a downgrade, then an upgrade): the map saved whole wins, and the next save deletes the stale parts. `checked_batch_file_name` refuses a name with `#` (the store refuses it too), so no file's key is another file's part key or parts key. Carry-forward reads the second, because a record either drops still holds stored rows it must carry. A repair records none and removes any an earlier run left (`clear_batch_inputs`), so every row it did not answer is carried. A batch input file is keyed by its identity, its path under the action's input root (`sub/page.json`; a top-level file's is its name): registry entry, context map, recorded inputs and recovery state all keep the directory, and `checked_batch_file_name` refuses an absolute path, a `..` part (a `..` inside a part, `v1..2/page.json`, is a name, as the store reads it) or a `#`. `batch_output_name` is the one rule for the name a batch's output is stored under — the identity with a `.json` suffix, directories kept, which is what online stores a first-stage or `.json` input under — shared by finalize's write, submission's lookup of stored rows and the write made when nothing is sent. `batch_file_identity`, called by both batch callers (`workflow/pipeline.py`, first-stage `initial_pipeline.py`), decides it. A store written by an older version keyed a nested file by its basename, and holds its output, its batch state and every downstream join under that name; such a file keeps it while the store holds it there (its output under that name, or a registry entry), unless a top-level input of the action stores under it (`base_owner`: a file the walk processes directly under the staging root that stores under that name, or a dependency storing that name, a version base standing for each of its versions) or another nested file stored under that name claimed it first. A file given its own name over a basename the store holds is logged once, when the choice is made. The choice is recorded in one blob per action (`batch_file_names:{action}`, `{identity: chosen}`), rewritten per decision, so it follows the stored rows rather than the inputs of the day: `clear_batch_state` keeps it, `delete_target` (`--fresh`) removes it, and a walk that deletes the stored file of an input that is gone forgets that input's entry (`forget_batch_file_names`); `recorded_batch_file_names` reads it, so the walk keeps a file stored under a recorded name. A repair decides by the same evidence and records its choice too, so two files cannot claim one name within it. The caller hands over the registry manager its submission uses, so a decision costs no second registry read. `load_batch_inputs` reports an unrecorded input (`None`) apart from one recorded as empty, and a recording it cannot read or that is not a list of identities degrades to `None` with a warning rather than raising — the reader's fallback is to carry every row, and raising would abandon a batch the provider has already answered. Both cleared with the context map by `clear_batch_state`. `record_no_input` / `takes_no_input` keep a separate `batch_no_input:{action}:{file}` key for a file that took no input while its batch was out, so the collect stores it empty; recording inputs again, clearing them, or a reset removes it. | `logging`, `workflow`, `storage` |
| `job_manager.py` | Module | Job lifecycle controller that tracks active batch runs. | `logging`, `tooling.docs` |
| `recovery_state.py` | Module | `RecoveryState`: cross-pass retry/repair state persisted to storage metadata between runs (`recovery_state:{action}:{identity}`), so a deferred batch resumes where it stopped. Its `phase` goes through `coerce_recovery_phase`, so a row naming a phase this version does not run refuses rather than resuming into a handler that cannot act on it. `records_awaiting_recovery` maps each record a recovery batch not yet collected holds to its round and the error recorded for its last attempt, and each other record of that batch's file to the same round with `for_its_file` set. Side rounds (a step's side calls sent as a batch of their own, `llm_judge` calls being one kind) persist, with no field naming a kind: the rounds sent per kind (`side_attempts`), the kind and requests of the side batch out now (`side_kind`, `side_requests`: request id to call key), what every returned batch answered as its requester settled it (`side_results`: kind, then call key), and the results waiting on the batch with the step that resumes (`side_waiting`, `side_resumes`); `records_awaiting_recovery` reports those results as waiting on a batch of that kind (`AwaitingRecovery.side_kind`, read from the registry entry). `RecoveryState.side_model` is the model the side batch out now names (None: the action's own), which its usage is counted under when it returns. | `storage`, `llm.batch.core` |
| `registry.py` | Module | `BatchRegistryManager`: thread-safe CRUD over the batch job registry, persisted as storage-backend metadata keyed by action. `are_all_jobs_completed()` releases the lock before network I/O to prevent thread starvation. A malformed entry is skipped with a warning but written back on every save, because the stored blob is the only thing naming its batch and a reclaim has to be able to read the id; a save or a remove on that key retires it. `batch_ids()` reads those ids as stored, bypassing the model for the same reason. One naming a retired recovery type is not skipped at all, because dropping it makes its parent look unsubmitted. `uncollected_batch_ids()` names, read as stored like `batch_ids()`, the batches whose results nothing has written yet: what a reset gives up when it clears the registry of an action that had not completed. `get_registry_stats()` counts a settled entry (`BatchJobEntry.is_settled`) as `settled`, not as failed or cancelled, so it no longer reads `partial_failed`, and any entry not ended as `in_progress`, a status outside `BatchStatus` included. | `llm.providers`, `logging`, `storage` |
