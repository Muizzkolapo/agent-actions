# Batch Infrastructure Manifest

## Overview

Infrastructure modules resolve context, job management, and file handling for
batch services that orchestrate runs outside online mode.

## Modules

| Name | Type | Description | Signals |
|------|------|-------------|---------|
| `batch_client_resolver.py` | Module | Returns the appropriate provider/batch client per agent config. | `llm.providers`, `validation` |
| `batch_data_loader.py` | Module | Loads and prepares batched input payloads for processors. | `input`, `preprocessing` |
| `context.py` | Module | Batch context builders and metadata propagation helpers. Persists two things per (action, batch) under storage metadata: the context map (`batch_context:…`), holding the rows that were submitted, and the run's input identities (`batch_inputs:…`), holding the input above every narrowing — the record limit and the disposition gate both sit between the two. Carry-forward reads the second, because a record either drops still holds stored rows it must carry. A repair records none and removes any an earlier run left (`clear_batch_inputs`), so every row it did not answer is carried. A batch input file is keyed by its identity, its path under the action's input root (`sub/page.json`; a top-level file's is its name): registry entry, context map, recorded inputs and recovery state all keep the directory, and `checked_batch_file_name` refuses an absolute path or a `..` part (a `..` inside a part, `v1..2/page.json`, is a name, as the store reads it). `batch_output_name` is the one rule for the name a batch's output is stored under — the identity with a `.json` suffix, directories kept, which is what online stores a first-stage or `.json` input under — shared by finalize's write, submission's lookup of stored rows and the write made when nothing is sent. `batch_file_identity`, called by both batch callers (`workflow/pipeline.py`, first-stage `initial_pipeline.py`), decides it. A store written by an older version keyed a nested file by its basename, and holds its output, its batch state and every downstream join under that name; such a file keeps it while the store holds it there (its output under that name, or a registry entry), unless a top-level input of the action stores under it (`base_owner`: a file the walk processes directly under the staging root that stores under that name, or a dependency storing that name, a version base standing for each of its versions) or another nested file stored under that name claimed it first. A file given its own name over a basename the store holds is logged once, when the choice is made. The choice is recorded in one blob per action (`batch_file_names:{action}`, `{identity: chosen}`), rewritten per decision, so it follows the stored rows rather than the inputs of the day: `clear_batch_state` keeps it, `delete_target` (`--fresh`) removes it, and a walk that deletes the stored file of an input that is gone forgets that input's entry (`forget_batch_file_names`); `recorded_batch_file_names` reads it, so the walk keeps a file stored under a recorded name. A repair decides by the same evidence and records its choice too, so two files cannot claim one name within it. The caller hands over the registry manager its submission uses, so a decision costs no second registry read. `load_batch_inputs` reports an unrecorded input (`None`) apart from one recorded as empty, and a recording it cannot read or that is not a list of identities degrades to `None` with a warning rather than raising — the reader's fallback is to carry every row, and raising would abandon a batch the provider has already answered. Both cleared with the context map by `clear_batch_state`. | `logging`, `workflow`, `storage` |
| `job_manager.py` | Module | Job lifecycle controller that tracks active batch runs. | `logging`, `tooling.docs` |
| `recovery_state.py` | Module | `RecoveryState`: cross-pass retry/repair state persisted to storage metadata between runs (`recovery_state:{action}:{identity}`), so a deferred batch resumes where it stopped. Its `phase` goes through `coerce_recovery_phase`, so a row naming a phase this version does not run refuses rather than resuming into a handler that cannot act on it. | `storage`, `llm.batch.core` |
| `registry.py` | Module | `BatchRegistryManager`: thread-safe CRUD over the batch job registry, persisted as storage-backend metadata keyed by action. `are_all_jobs_completed()` releases the lock before network I/O to prevent thread starvation. A malformed entry is skipped with a warning but written back on every save, because the stored blob is the only thing naming its batch and a reclaim has to be able to read the id; a save or a remove on that key retires it. `batch_ids()` reads those ids as stored, bypassing the model for the same reason. One naming a retired recovery type is not skipped at all, because dropping it makes its parent look unsubmitted. `uncollected_batch_ids()` names, read as stored like `batch_ids()`, the batches whose results nothing has written yet: what a reset gives up when it clears the registry of an action that had not completed. `get_registry_stats()` counts a settled entry (`BatchJobEntry.is_settled`) as `settled`, not as failed or cancelled, so it no longer reads `partial_failed`. | `llm.providers`, `logging`, `storage` |
