# Batch Services Manifest

## Overview

Services that coordinate batch submission, retrieval, and processing updates.

## Modules

| Name | Type | Description | Signals |
|------|------|-------------|---------|
| `collect.py` | Module | The two steps finalize and a run with nothing to send share. `collect_batch_rows` runs results against the context map through `BatchResultStrategy` and the shared collector, then clears DEFERRED, writes FILTERED for the records the guard filtered and records answers on their prompt traces; every entry no result answers is collected as what preparation found it to be, so no results collects a run that sent nothing. One action name, passed in, names the rows, every disposition and the collector's context. A halt `on_exhausted: raise` or `on_empty: error` decided is returned, for the caller to raise once the file is written, and so is online's breaker (`terminal_failure`) for a file holding a record with no `source_guid` none of whose records succeeded: refused, such a record leaves no disposition to read the action failed by. It also clears the `deferred` an earlier release marked under such a record's custom_id. `write_batch_file` merges the stored rows the run does not replace (`with_stored_rows_not_reproduced`), none of them for an input the guard filtered (`filtered_inputs` of the context map, which each caller passes) unless the run failed and answered nothing, and stores the file under exactly the stored name it is given, building the path from it; `store_batch_file` is that store step alone, merging nothing. Also home to `halt_survives_failure`. Imports neither `processing.py` nor `processing_recovery.py`, so submission does not depend on the retrieval service. | `processing`, `output`, `storage` |
| `processing.py` | Module | Service that orchestrates batch processing pipelines (load, transform, execute). Delegates retry to `retry.py`, recovery/finalization to `processing_recovery.py`, and collecting and writing a file to `collect.py` (`_convert_batch_results_to_workflow_format`, `_write_batch_output`). A collect pass (`process_all_batch_results`) finalizes only the entries whose results are still owed: one already collected (`collected_at`) is neither polled nor read again, since a later run may have written its file since, and a pass that finds only those is not an error. A finished entry the provider cannot be asked about (its status check raises `OSError` or `ConnectionError`, which the batch clients raise for their SDK's transient errors) or reports running again is left unread and handed back in `CollectPass.unread`, beside the files the pass wrote (`CollectPass.written`), and so is the parent a recovery dropped during the pass hands back, which the pass has already skipped; leaving one is not an error either, and the caller waits for it rather than completing the action. A finished entry the provider reports ended any other way, or does not know, is not waited for: no later pass could read it, so the records of its file (its parent's, for a recovery round) are marked failed. So are those of a file whose batch the poll found failed or cancelled before it finished, naming the file and its batch, and its entry is then stamped `collected_at`: owed nothing, it no longer holds the action, and no later pass reads it. A dead recovery round is not settled this way: a retry's failure path continues it, and the pass over a repair's file puts its records back in play. A file whose reading fails is not left unread: its records are marked failed and it costs only itself, unless the failure is one the loop lets through (below). Returns the `EmptyOutputError` that `on_empty: error` asks for as a halt the finaliser raises once the file is written; the loop over the action's files lets it through, as it does an exhaustion halt and any error declared fatal to the action (`is_action_fatal`), such as a store that failed to write the file, and the executor records the action as failed. A file holding a record with no `source_guid`, none of whose records succeeded, halts the same way with online's breaker (`terminal_failure`), which the collect step returns. A retry does not send again a lost record with no `source_guid`, which preparation would refuse (`BatchResultReconciler.resendable_ids`); it is collected unanswered. | `processing`, `logging`, `errors` |
| `processing_recovery.py` | Module | Recovery and finalization functions extracted from `BatchProcessingService`: recovery batch handling, retry and repair recovery, repair submission, output finalization. Finalize collects and writes through `collect.py` under the one action name it resolves, and keeps what belongs to a batch: parking and raising the halt, the batch event, the registry status and `mark_collected`, recovery cleanup and the placeholder. `finalize_batch_output` reads the run's recorded input (`batch_inputs:{action}:{file}`) and hands it to the write, which is what lets carry-forward tell an input the run left unanswered, whose stored rows it keeps, from one that is not part of the run, whose rows it leaves out as the online path does; it also hands over the inputs the context map says the guard filtered, whose rows the write leaves out whether or not inputs were recorded, unless the run failed and answered nothing; a recovery round reads its parent's recording, since it finalizes under `parent_file_name`. A later retry round leaves out a record with no `source_guid` as the first does. | `processing`, `retry`, `logging` |
| `retrieval.py` | Module | Pulls completed batch results and cleans up state. | `output`, `workflow` |
| `retry.py` | Module | Facade for `BatchRetryService`. Delegates to `retry_ops` and `shared.retrieve_and_reconcile`, handing every retry it prepares the workflow's action positions and configs it was built with. | `retry_ops`, `shared` |
| `repair_ops.py` | Module | `repair_expectations`, `submit_repair_batch`, `pool_records`, `stamp_exhausted`, `apply_exhaustion_policy` | Drives the `expect:` repair loop in batch: splits graduated from still-failing, sends the failures back with their feedback, and applies `on_exhausted` once the rounds are spent. `pool_records` is the accumulator the loop and the recovery state machine share, keyed by record id so a resume cannot ship a record twice. `submit_repair_batch` sends neither a record with no context-map row nor one with no `source_guid`, which preparation would refuse, and counts neither as sent; with nothing left it sends no batch. |
| `retry_ops.py` | Module | Retry-specific operations: submit retry batches, resubmit missing records, process retry results, build exhausted recovery metadata. Both senders require the workflow's action positions and configs (`action_indices`, `dependency_configs`), as repair does, and prepare with the action's version context, built as the first submission builds it (`ProcessingPipeline._build_pipeline_context`). Preparation refuses an action with dependencies without the positions, a guard on an upstream's `output_field` reads nothing without the configs, and a versioned action's prompt and guard read nothing under `version.*` without its version, so a retry prepared without any of them is not sent. The run's `workflow.*` values are not handed to it, so a retry of an action whose prompt reads them is not sent, and one whose guard reads them fails the collect pass. | `retry_polling`, `llm.providers`, `processing`, `workflow.pipeline` |
| `retry_serialization.py` | Module | Serialize/deserialize `BatchResult` objects for JSON persistence. | `llm.providers`, `processing.types` |
| `retry_polling.py` | Module | Batch polling (`wait_for_batch_completion`) and validation module import (`import_validation_module`). | `llm.providers`, `logging.events` |
| `shared.py` | Module | Shared utilities (retrieve_and_reconcile) used by both processing and retrieval services. | `llm.providers`, `processing` |
| `submission.py` | Module | Submits batch jobs to the scheduler or provider. A file with a job in flight, or a finished one whose results are not collected yet (`collected_at`), is not submitted again; a collected job does not block, since the executor has already decided the action must run. What a batch was sent (its context map and recorded input, or a repair's clearing of the input) is stored only once the provider has taken the batch, and before the registry names it, so a refused batch leaves the record of the file's last batch as it stood. A run stopped between the two leaves the store describing a batch the registry does not name; the registry still names the file's earlier entry, or none, and an earlier entry the guard let a resend replace is collected, failed or cancelled, which no collect pass reads. A refused batch raises `ExternalServiceError` declared fatal to the action (`mark_action_fatal`), so the walk sends the action's other files and then fails it rather than completing on their batches without this one; the next run sends the file again, and the guard above keeps the other files' batches. It is declared refused as well (`mark_submission_refused`), so the executor names the other files' batches the failure leaves waiting. A batch the provider took but that cannot be recorded raises an error naming it, since nothing else does; the next run sends its records again. Records the run's input above every narrowing (`batch_inputs:{action}:{file}`, beside the context map) for carry-forward to read back at finalization — taken from the caller's pre-narrowing list, never from the `data` it submits, which the record limit and the disposition gate have narrowed. A repair records nothing, so finalize carries every stored row it did not answer, as online does. An input the disposition gate carries is submitted again when no stored row answers for it, as online re-queues it: the stored file is looked up under `batch_output_name`, the name finalize writes it under. One the guard filtered holds no row by design and is sent on to the guard again instead. A record sent without a `source_guid` is not marked `deferred`: it has no identity to mark. `batch_name` is the input file's identity (`batch_file_identity`), so every key and the stored name derive from one value. When preparation leaves nothing to send, submission collects and writes the file itself through `collect.py`, as finalize does with no results — rows keep their tracking, each record gets its disposition (`unprocessed`, `filtered`, `failed` with its error), and the file carries the stored rows a finalize would, under `batch_output_name(batch_name)` — then records the node-level `passthrough` and raises any halt the collect step returned. It returns `{"type": "written"}`, so the caller writes nothing. The registry, recovery state and batch events are left alone: no batch was sent. When no record is left to send at all -- every one already done, or the input empty -- nothing is collected, but the file is still written for this run's inputs, as online writes it every run: the merge over no answers keeps each stored row whose input is one of the run's, and a file whose input above every narrowing is empty -- the action above holds nothing for it, the runner dropped every record of it a guard filtered upstream, or its staged file is empty -- is stored empty without the merge, on a first run too, where nothing is stored for it yet. A repair, or a run that recorded no inputs, writes nothing, and a file the merge would leave as it stands, or one stored empty already, is not written; the merge keeps one row per identity, so a file holding two rows under one is written with one of them, as online and finalize write it. No disposition or node-level `passthrough` is recorded, as online records none, so the action is classified on its files and completes as before; it returns `{"carry_forward_only": True}`. | `llm.providers`, `logging`, `processing` |
