# Batch Services Manifest

## Overview

Services that coordinate batch submission, retrieval, and processing updates.

## Project Surface

| Symbol | File | Interaction | Config Key |
|--------|------|-------------|------------|

| `cleanup_recovery()` | `.agac/batch_state/{batch_id}.json` | Deletes | — |

## Modules

| Name | Type | Description | Signals |
|------|------|-------------|---------|
| `collect.py` | Module | The two steps finalize and a run with nothing to send share. `collect_batch_rows` runs results against the context map through `BatchResultStrategy` and the shared collector, which writes each terminal disposition, then clears DEFERRED, writes FILTERED for the records the guard filtered (again: submission wrote it first, as such a record waits under no DEFERRED a refused write could leave; each terminal disposition is written before its record's DEFERRED is cleared, so dying between the two leaves the outcome queryable; `_fail_abandoned_records` writes FAILED in the same order; a record whose terminal disposition the store refused keeps its DEFERRED, the collector naming it in the context's `dispositions_not_stored`, rather than hold nothing) and records answers on their prompt traces; every entry no result answers is collected as what preparation found it to be, so no results collects a run that sent nothing. One action name, passed in, names the rows, every disposition and the collector's context. A halt `on_exhausted: raise` or `on_empty: error` decided is returned, for the caller to raise once the file is written, and so is online's breaker (`terminal_failure`) for a file holding a record with no `source_guid` none of whose records succeeded: refused, such a record leaves no disposition to read the action failed by. It also clears the `deferred` an earlier release marked under such a record's custom_id. `write_batch_file` merges the stored rows the run does not replace (`with_stored_rows_not_reproduced`), none of them for an input the guard filtered (`filtered_inputs` of the context map, which each caller passes) unless the run failed and answered nothing, and stores the file under exactly the stored name it is given, building the path from it; `store_batch_file` is that store step alone, merging nothing. Also home to `halt_survives_failure`. Imports neither `processing.py` nor `processing_recovery.py`, so submission does not depend on the retrieval service. | `processing`, `output`, `storage` |
| `processing.py` | Module | Service that orchestrates batch processing pipelines (load, transform, execute). Delegates retry to `retry.py`, recovery/finalization to `processing_recovery.py`, and collecting and writing a file to `collect.py` (`_convert_batch_results_to_workflow_format`, `_write_batch_output`). A collect pass (`process_all_batch_results`) finalizes only the entries whose results are still owed: one already collected (`collected_at`) is neither polled nor read again, since a later run may have written its file since, and a pass that finds only those is not an error. A finished entry the provider cannot be asked about (its status check raises `OSError` or `ConnectionError`, which the batch clients raise for their SDK's transient errors) or reports running again is left unread and handed back in `CollectPass.unread`, beside the files the pass wrote (`CollectPass.written`), and so is the parent a recovery dropped during the pass hands back, which the pass has already skipped; leaving one is not an error either, and the caller waits for it rather than completing the action. A finished entry the provider reports ended any other way, or does not know, is not waited for: no later pass could read it, so the records of its file (its parent's, for a recovery round) are marked failed. So are those of a file whose batch the poll found failed or cancelled before it finished, naming the file and its batch, and its entry is then stamped `collected_at`: owed nothing, it no longer holds the action, and no later pass reads it. A pass that cannot read the context map of either kind of file (`_fail_abandoned_records` returns whether it did) leaves the file unread instead, unstamped, and claims nothing was marked, so the next pass marks them. A dead recovery round is not settled this way: a retry's failure path continues it, and the pass over a repair's file puts its records back in play. A file whose reading fails is not left unread: its records are marked failed and it costs only itself, unless the failure is one the loop lets through (below). Returns the `EmptyOutputError` that `on_empty: error` asks for as a halt the finaliser raises once the file is written; the loop over the action's files lets it through, as it does an exhaustion halt and any error declared fatal to the action (`is_action_fatal`), such as a store that failed to write the file, and the executor records the action as failed. A file holding a record with no `source_guid`, none of whose records succeeded, halts the same way with online's breaker (`terminal_failure`), which the collect step returns. A retry does not send again a lost record with no `source_guid`, which preparation would refuse (`BatchResultReconciler.resendable_ids`); it is collected unanswered. Nor does it send a record whose failure online would not retry (`BatchResultReconciler.retriable_ids`): a 400, a refusal or a safety block is failed with what the provider said, not exhausted. A dead judge round is processed as a dead retry is: each judgement it held fails. | `processing`, `logging`, `errors` |
| `processing_recovery.py` | Module | Recovery and finalization functions extracted from `BatchProcessingService`: recovery batch handling, retry and repair recovery, repair submission, output finalization. Finalize collects and writes through `collect.py` under the one action name it resolves, and keeps what belongs to a batch: parking and raising the halt, the batch event, the registry status and `mark_collected`, recovery cleanup and the placeholder. `finalize_batch_output` reads the run's recorded input (`batch_inputs:{action}:{file}`) and hands it to the write, which is what lets carry-forward tell an input the run left unanswered, whose stored rows it keeps, from one that is not part of the run, whose rows it leaves out as the online path does; it also hands over the inputs the context map says the guard filtered, whose rows the write leaves out whether or not inputs were recorded, unless the run failed and answered nothing; a recovery round reads its parent's recording, since it finalizes under `parent_file_name`. A later retry round leaves out a record with no `source_guid`, and one whose failure online would not retry, as the first does; a round that ends exhausted keeps only the exhausted records in `missing_ids`, from which the repair finaliser rebuilds exhaustion. `finalize_batch_output` reports the token usage of the results it writes, summed (`report_batch_usage`, through `run_counts.add_tokens`), keyed as an online call's. A step that would make side calls (`check_and_submit_repair` after the main or retry batch, `handle_repair_recovery` after a repair round) first sends them as a side batch and defers: `_send_side_batch` asks each registered requester (`side_batch.side_requesters`) what it would call over the step's results and sends the first kind that has calls (`RecoveryType.SIDE`, registered as `<file>_<kind>_<n>`); `handle_side_recovery` hands the returned replies to that kind's requester, keeps what it settles in the state, and runs the waiting step again, which sends the next kind's calls or goes on. Neither names a kind. A resume while that batch is unread defers to it. The two steps read the judge's results from the state through `judge_ops.judge_verdicts`. Every one of those steps, and the judge collection before it, reads each record's judge context from the stored context map. The retry handler leaves in `missing_ids` only what it exhausted. `report_batch_usage` reads each result's usage through `ResponseBuilder.batch_usage`, so an Anthropic result counts its cached prompt tokens as an online call does. | `processing`, `retry`, `logging`, `output` |
| `judge_ops.py` | Module | The `llm_judge` rules of a batch action as a requester of side batches (`JudgeRequester`, kind `judge`, registered with `side_batch.register_side_requester` at import). `collect` is `collect_judgements` unless `judge_mode: online` opts out (`judges_in_batch`): it runs the suite over a step's results as that step will (the repair strategy, or the result writer's items under `repair: none`) with a `HeldSideCalls` executor, so each judge call is held back, deduplicated by verdict key; each record is judged against the context its context-map row kept, so a held call's prompt carries the grounding context online's carries (the verdict key, like online's cache key, does not include the context). `sent` charges `judge_budget` one unit per call that went out (`JudgeBudget.at_start` less the calls sent, kept in `repair_judge_budget_remaining`). `settle` reads a call's replies with `expectations.judge.verdict_from_replies`, the function the online path calls. `judge_verdicts(state)` is every verdict the file's judge batches returned, and `with_judge_results` puts them and the unspent budget on the config under `BATCH_JUDGE_KEY` for a result writer that validates. | `expectations`, `llm.side_calls`, `processing.evaluation` |
| `side_batch.py` | Module | A batch run's side calls (`llm.side_calls`), sent as batches of their own, for any kind of requester. `SideRequester` is what a kind gives the round: `collect(step)` (the calls a step would make that no returned batch has answered, by key; `SideStep` holds the config, the results, the recovery state and the context map, and `settled(kind)` what that kind's batches answered), `sent(step, calls)` (told which went out) and `settle(key, replies)` (a call's result, in a form JSON stores). `register_side_requester` adds a kind (a name of lowercase letters and digits that is not `retry`, `repair` or `side`, since it names the batch); `side_requesters()` lists them, the built-in ones (`_BUILT_IN`, modules whose import registers one: `judge_ops`) first. `submit_side_batch` sends one request per copy of each call as `<file>_<kind>_<attempt>`, with the config `SideCall.request_config` gives the online executor; a batch takes one kind and one model, so the rest go out in a later round; each row is the call's prompt with empty content, as online passes them, and a request too large for the model is raised (`raise_unsent`) before anything is submitted. Request ids are the kind's first letter, a hash of the key and the copy (`j_<hash>_<n>` for a judge). `read_side_batch` gives each call its replies (`SideReplies`): a request that errored or that the batch did not return fails the whole call. | `llm.side_calls`, `llm.providers` |
| `retrieval.py` | Module | Pulls completed batch results and cleans up state. | `output`, `workflow` |
| `retry.py` | Module | Facade for `BatchRetryService`. Delegates to `retry_ops`, handing every retry it prepares the workflow's action positions and configs it was built with. | `retry_ops` |
| `repair_ops.py` | Module | `repair_expectations`, `submit_repair_batch`, `pool_records`, `stamp_exhausted`, `apply_exhaustion_policy` `build_repair_strategy` hands the strategy each record's kept judge context from the context map. | Drives the `expect:` repair loop in batch: splits graduated from still-failing, sends the failures back with their feedback, and applies `on_exhausted` once the rounds are spent. `pool_records` is the accumulator the loop and the recovery state machine share, keyed by record id so a resume cannot ship a record twice. `submit_repair_batch` sends neither a record with no context-map row nor one with no `source_guid`, which preparation would refuse, and counts neither as sent; with nothing left it sends no batch. |
| `retry_ops.py` | Module | Retry-specific operations: submit a retry batch, process its results, build exhausted recovery metadata. The sender requires the workflow's action positions and configs (`action_indices`, `dependency_configs`), as repair does, and prepare through `shared.recovery_preparator`, which builds the action's version context as the first submission builds it (`ProcessingPipeline._build_pipeline_context`). Preparation refuses an action with dependencies without the positions, a guard on an upstream's `output_field` reads nothing without the configs, and a versioned action's prompt and guard read nothing under `version.*` without its version, so a retry prepared without any of them is not sent. It also takes the collecting run's `workflow_metadata`, so a prompt or guard reading `workflow.*` renders and evaluates as it did for the first request. | `shared`, `llm.providers`, `processing`, `workflow.pipeline` |
| `retry_serialization.py` | Module | Serialize/deserialize `BatchResult` objects for JSON persistence, `error_status` and `retriable` included, so a deferred round still classifies a failure. `BatchResult.text` is not persisted: only the reading of a side batch uses it, in the pass that retrieved it. | `llm.providers`, `processing.types` |
| `retry_polling.py` | Module | Validation module import (`import_validation_module`). | `utils.module_loader` |
| `shared.py` | Module | Shared utilities used by both processing and retrieval services: `retrieve_and_reconcile`, and `recovery_preparator`, the one builder of the preparator a retry or repair round rebuilds its prompts with, so both carry the action's version like the first submission. `settle_unanswered` gives each returned line with no readable answer the content its mode's online call returns: in JSON mode a `_parse_error` record, stored failed or regenerated by `expect:`; in text mode the empty output `on_empty` decides for an answer the model left empty, while a refused or cut-off one keeps its error and no content. `retrieve_and_reconcile` applies it when handed the action's config, which a judge batch's retrieval does not pass. Handed the action's config, as the collect pass hands it for the main batch and each retry or repair round, `retrieve_and_reconcile` puts on every answered result of an `add_dispatch` action the schema its record's dispatch chose (`{function: chosen}` on each object of the answer, from the context-map row), as an online call returns it, so the rules, a repair prompt and the stored record read the answer online reads. `recovery_preparator` is the one builder of the preparator a retry or repair round rebuilds its prompts with, so both carry the action's version like the first submission. Given the action's config, `retrieve_and_reconcile` reads each reply of a text-mode action (`json_mode: false`) as the record an online call returns for it, its text under the output field (`ResponseBuilder.wrap_non_json` over `BatchResult.text`): a provider parses every reply as JSON, not knowing the action's mode. The main batch and a retry or repair batch pass the config; a judge batch and `agac batch retrieve` do not. | `llm.providers`, `processing`, `output` |
| `submission.py` | Module | Submits batch jobs to the scheduler or provider. Once the provider takes a batch it stamps DEFERRED on each record sent and FILTERED on each record the guard filtered (`_stamp_filtered`), whose outcome is known then. A file with a job in flight, or a finished one whose results are not collected yet (`collected_at`), is not submitted again; a collected job does not block, since the executor has already decided the action must run. What a batch was sent (its context map and recorded input, or a repair's clearing of the input) is stored only once the provider has taken the batch, and before the registry names it, so a refused batch leaves the record of the file's last batch as it stood. A run stopped between the two leaves the store describing a batch the registry does not name; the registry still names the file's earlier entry, or none, and an earlier entry the guard let a resend replace is collected, failed or cancelled, which no collect pass reads. A refused batch raises `ExternalServiceError` declared fatal to the action (`mark_action_fatal`), so the walk sends the action's other files and then fails it rather than completing on their batches without this one; the next run sends the file again, and the guard above keeps the other files' batches. It is declared refused as well (`mark_submission_refused`), so the executor names the other files' batches the failure leaves waiting. A batch the provider took but that cannot be recorded raises an error naming it, since nothing else does; the next run sends its records again. Records the run's input above every narrowing (`batch_inputs:{action}:{file}`, beside the context map) for carry-forward to read back at finalization — taken from the caller's pre-narrowing list, never from the `data` it submits, which the record limit and the disposition gate have narrowed. A repair records nothing, so finalize carries every stored row it did not answer, as online does. An input the disposition gate carries is submitted again when no stored row answers for it, as online re-queues it: the stored file is looked up under `batch_output_name`, the name finalize writes it under. One the guard filtered holds no row by design and is sent on to the guard again instead. So is one checkpointed online after its file was stored (`answered_since_stored`): its stored row is older than its answer, and finalize reads no checkpoint row. Every other input the gate carries is put to the guard (`BatchTaskPreparator.turned_away`), as online's guard above its gate judges it, other than one the action above blocked, which neither preparation nor online puts to the guard: one the guard now filters or skips is prepared again, so its row is left out or replaced by its tombstone at no model cost, and one it passes stays carried. An error while judging propagates, so a guard UDF's write to any carried input stops the action. A file whose batch is out, or finished and not collected, is not sent again, so none of its inputs is judged: the collect writes what the batch brings, as the guard judged it when the batch was sent, where online judges it in the run that resumes the action. A record sent without a `source_guid` is not marked `deferred`: it has no identity to mark. `batch_name` is the input file's identity (`batch_file_identity`), so every key and the stored name derive from one value. When preparation leaves nothing to send, submission collects and writes the file itself through `collect.py`, as finalize does with no results — rows keep their tracking, each record gets its disposition (`unprocessed`, `filtered`, `failed` with its error), and the file carries the stored rows a finalize would, under `batch_output_name(batch_name)` — then records the node-level `passthrough` and raises any halt the collect step returned. It returns `{"type": "written"}`, so the caller writes nothing. The registry, recovery state and batch events are left alone: no batch was sent. When no record is left to send at all -- every one already done, or the input empty -- nothing is collected, but the file is still written for this run's inputs, as online writes it every run: the merge over no answers keeps each stored row whose input is one of the run's, and a file whose input above every narrowing is empty -- the action above holds nothing for it, the runner dropped every record of it a guard filtered upstream, or its staged file is empty -- is stored empty without the merge, on a first run too, where nothing is stored for it yet; that file's registry entry, context map, recorded inputs and recovery state are removed then, since nothing is left to collect. A repair, or a run that recorded no inputs, writes nothing, and a file the merge would leave as it stands, or one stored empty already, is not written; the merge keeps one row per identity, so a file holding two rows under one is written with one of them, as online and finalize write it. No disposition or node-level `passthrough` is recorded, as online records none, so the action is classified on its files and completes as before; it returns `{"carry_forward_only": True}`. A sent batch is named in `BatchSubmittedEvent.data.batch_id`, never in the shared event context (`set_context`), which every later event of the process would carry, other actions' included. A config with no `model_vendor` is refused with the action as `action_name` and `missing_fields`. A file whose every record preparation sent to another branch (skip reason `sent_elsewhere`) records no node-level `passthrough`, so the action completes on no records, as online does. | `llm.providers`, `logging`, `processing` |
