# Batch Core Manifest

## Overview

Core batch helpers describe workflow batch metadata, constants, and embodied models
shared by the CLI, service layer, and infrastructure components.

## Modules

| Name | Type | Description | Signals |
|------|------|-------------|---------|
| `batch_constants.py` | Module | Batch enums (`BatchStatus`, `FilterStatus`, `RecoveryType`, `RecoveryPhase`, `OnExhaustedPolicy`) and `ContextMetaKeys`, the context-map keys a tool is never handed (`all_internal_keys`), among them the error that failed a record's preparation (`PREP_ERROR`) the schema a dispatch chose for the row (`OUTPUT_SCHEMA`) and the LLM context values the action's `llm_judge` rules reference (`JUDGE_CONTEXT`). `coerce_recovery_phase`/`coerce_recovery_type` are the only string-to-enum entry points for the two recovery enums: both refuse any value that is not a member of the enum with `UnknownRecoveryState`, which names the value and tells the user to re-run the action with `--fresh`, rather than letting a bare `ValueError` reach a caller that would skip the entry. The refusal is declared fatal to the action (`errors.mark_action_fatal`), since its remedy (`--fresh`) is the action's, so a collect pass that meets it in one file's recovery state stops rather than fail that file alone. `RecoveryType.SIDE` is a batch of a step's side calls; the kind it carries is not in the enum but on the registry entry (`BatchJobEntry.side_kind`), so a judge batch is `side` with kind `judge`, filed as `<file>_judge_<n>`. | `llm.batch`, `errors` |
| `batch_context_metadata.py` | Module | Metadata helpers for preserving context (session IDs, run IDs). `set_output_schema`/`get_output_schema` keep the schema a dispatch chose on the row, so a repair round, which reads its rows from the stored context map, compiles the same schema. `set_judge_context`/`get_judge_context` keep on the row the context a judged rule's `context:` refs resolve against, which every verdict pass reads once the answers are back (`judge_contexts` gives it for each record of a context map). | `logging`, `workflow` |
| `batch_models.py` | Module | Typed models (dataclasses) that represent batch run state and inputs. `BatchJobEntry.from_dict()` filters unknown keys via `dataclasses.fields()` to tolerate schema evolution. `BatchJobEntry.side_kind` is the kind of side call a `recovery_type: side` batch answers, and `recovery_name` what a recovery batch is called (that kind, else its type). `BatchJobEntry.is_settled` is an entry the provider failed or cancelled that a collect pass has stamped `collected_at` once it marked its records failed, and `BatchRegistryStats.overall_status` rolls `settled` entries up with completed ones, so one holds an action no more than a collected batch does. `BatchJobEntry.is_in_flight` is any entry not ended (`is_terminal`), one holding a status outside `BatchStatus` included, as a registry an earlier version wrote can: it warns naming the batch, and the provider is asked about it again. `overall_status` has no `error` bucket: an action whose batches have not all ended and none failed reads `in_progress`, so it is polled rather than failed unasked. `SubmissionResult.passthrough` says why no batch was sent: `{"type": "written"}` when submission wrote the file itself, `{"carry_forward_only": True}` when no record was left to send, every one already done or none there; submission then writes the file for this run's inputs if it holds a row of a record that left. `BatchJobEntry.usage_kind` is what the calls of the entry's batch are counted as: a side batch as its kind, a repair round as `repair`, the first batch and a retry of it as `main`. | `typing`, `validation` | `BatchTaskPreparationStats.sent_elsewhere_items` counts records sent to another branch, outside `total_filtered`.
