# Batch Processing Manifest

## Overview

Models that prepare batch inputs, reconcile outputs, and process results
before persisted results are written.

## Modules

| Name | Type | Description | Signals |
|------|------|-------------|---------|
| `preparator.py` | Module | Prepares batch workloads (chunking, formatting, batching). A cascade-blocked record is not sent; its skip reason is `quarantine_reason`'s, so a record a fan-in found folded into another's row is `consumed_into_another_record`, as online. A record whose prompt cannot be prepared is marked failed on its context-map entry, which keeps the error (`_batch_prep_error`, 500 characters) whether or not its state could move to failed; so is one refused for having no source_guid, which is never submitted. The preflight sample passes over a record that fails alone as it passes over a guard skip, so one at the head of the input, or the only one a retry hands it, does not stop the action: one refused for having no source_guid, one whose context is incomplete or too deep to render (`RecordContextError`), and one lacking a variable the template names (`TemplateVariableError` with `missing_variables`), the records online fails alone (`_fails_only_its_record`). Anything else stops it as before: a malformed template, a render error no variable explains, an error marked fatal to the action, an incomplete configuration. Behind the sample, the per-record loop stops the action on what online stops it for while preparing a record (`_stops_the_action`): an error marked fatal, a `ConfigurationError` other than `RecordContextError`, and a `TemplateVariableError` with no `missing_variables`, such as a render error this record's data provoked; it marks the error fatal to the action before re-raising, so a retry or repair round does not take it as transient, and nothing is sent. Any other error fails that record alone. `turned_away` names the records the guard filters or skips, judged as preparation judges them but stopping at the guard (`TaskPreparer.judge`), so no prompt is rendered and nothing is stored or marked. Unlike preparation, it fails no record alone: an error while judging, such as a guard UDF's write to its input, propagates on any record. An action whose schema is `dispatch_task(...)` has no action-wide schema: each row compiles its own and carries it on the task as `compiled_schema`. The dispatch function is called only for a row with no recorded choice; the chosen name is kept on the context-map row, so a repair round compiles the schema its first round chose. A row whose dispatch function fails or returns no schema fails alone (`SchemaDispatchError`); a row that compiles to no schema is sent with none, as an action with no schema is: in JSON mode each client asks for JSON as its online client does, and nothing refuses the action for having no schema. An action whose `llm_judge` rules declare `context:` refs (`expectations.service.judged_context_refs`, read once per call from the suite the run resolves) keeps on each sent record's context-map row the values those refs read from the record's LLM context (`narrow_context`), and nothing else of it: the verdict passes run once the answers are back, when that context is gone. A record whose prompt is too large for the model (`PromptTooLargeError`, raised by the message builder while the provider formats the row, which leaves it on the row as `UNSENT_ERROR_KEY`) is marked failed the same way and not sent, as online fails that record's call alone; the other rows go out. A repair round appends each row's feedback to its prompt (`_append_feedback`) and records on the row what an online repair call's config says of its prompt (`repair_call_scope`): the length of the prompt before the feedback (`_shared_prompt_len`), so the Anthropic client can mark the prompt and send the feedback unmarked after it, or `_request_varies_per_record` when the repair prompt does not begin with the round's prompt, so it gets no mark. Blank feedback (`repair: retry`, a repair template, a record with no verdict) leaves the prompt untouched. A repair round's feedback per record (`RepairFeedback`) is text appended to the prompt, or a function (a `repair: {prompt: ...}` template) that builds the prompt from it; `_append_feedback` keeps the shared prompt length only where the result still starts with the prompt. With `prompt_debug`, each row's prompt, context and schema are printed before the rows go to the provider (`_debug_print_prompts`, through `PromptService.debug_print_prompt`), as an online call prints its own: repair feedback included, the preflight sample not. A row carries its prompt's cache points (`_cache_points`). For a client that marks them (`marks_cache_points()`), the rows of one source (`parent_source_guid`, else `source_guid`) are sent side by side, sources in the order they first appear; the context map and every other batch keep the order of the records. A record the guard of an action marked `_sends_elsewhere` filters gets skip reason `sent_elsewhere`, which the `filtered` disposition then carries, and is counted in `sent_elsewhere_items`, not `filtered_items`. A task's `content` is the whole observed context (dispatch schemas and judges read it); `prompt_debug` prints the context block the line sends. | `preprocessing`, `input` |
| `reconciler.py` | Module | Reconciles batch outputs with context; uses string-normalized custom_id for JSON compatibility. A record the context map holds without a `source_guid` has none: its custom_id, a target_id, is never handed out as one, so enrichment refuses it, as it refuses whatever reaches it without one (a guard skip, or a record in a batch an earlier release sent). Nor is an id the map does not hold, such as a parser placeholder: it names no record. `resendable_ids` leaves a record with no `source_guid` out of what a retry sends again: preparation would refuse it, so it is collected unanswered and refused at enrichment. `was_sent` tells an entry preparation handed to the provider (`included`, or no status in a map saved without them) from one it held back; the expected ids are the entries sent. `is_retriable` decides whether an unanswered result is sent again as online's retry policy would (`is_retriable_error` over `error_for_status`): a rate limit, a 5xx or a transient 400 is; any other status is not; a result whose client classified the error online raises for it (`BatchResult.retriable`: an answer with no content, an Ollama failure with no HTTP answer) is taken at its word; else an answer with no content is only when cut off at the output limit, and a failure with no `error_status` is. `retriable_ids` leaves out the rest, which are failed with the provider's error. | `formatting`, `output` |
| `batch_result_strategy.py` | Module | Batch result processing strategy; converts raw BatchResult objects into enriched ProcessingResult records, and every context entry no result answers into the result preparation found it to be (none at all collects a run that sent nothing). An empty answer goes by the action's `on_empty`, as online: `warn` a failed record, `skip` a tombstone, `error` a failed record, on which the service raises `EmptyOutputError` once the file is written. A preparation failure's result carries the error preparation kept, which its disposition records as online's does; its row says `prep_failed`, and a context map saved before the error was kept gives `prep_failed` too. One with no source_guid carries no row: the collector builds it from the record, as it builds online's, where a tombstone without the identity would be refused again at enrichment. A record that was sent and that no result answers, reached only once no retry will send it (retry is off, or its retry batch did not go out), is failed the same way with the reason `batch_not_returned`, its row a tombstone: the action completes with failures and `agac retry` sends it again, where a cascade casualty would leave the action complete and `agac retry` with nothing to send. An answer item that is not an object (a list of strings) is stored as `{"value": item}` by `ensure_dict_output`, as online stores it. Each answer is read into the fields its action stores by online's passthrough strategies (`PassthroughTransformer.action_outputs`), handed what online hands them, so an answer item that itself holds `source_guid` and `content` is stored as its `content`, and a `context_scope.passthrough` that resolved to no field is read as online reads it. `dispatch_results` is what online's `add_dispatch` puts on a record's answer (the schema its dispatch chose, under the function's name, read from the context-map row) and `processing.helpers.with_dispatch_results`, the merge online's `run_dynamic_agent` calls, puts it on each object of an answer; retrieval applies them to every answer it reads, and the writer applies them again once a text answer has become an object. Under `repair: none` each item is validated against the judge context its context-map row kept, as online validates against the record's LLM context, and the service it validates with is seeded from the config's `BATCH_JUDGE_KEY` Under `repair: none` the service it validates with is seeded from the config's `BATCH_JUDGE_KEY` (the verdicts and unspent budget a judge batch left); `written_answer` is the writer's reading of one answered result (a string wrapped by mode, in JSON mode as `error_wrapper.unparsed_json_record`, the record online stores; the dispatch results merged; a schema echo replaced), and `validated_items` its items: `_process_successful_result` and any step ahead of the writer both call it, so the judge round sends the values the writer will validate. Each answered result is checked against the action's schema with `processing.helpers.warn_on_schema_mismatch`, the warning each online call logs; a record whose schema a dispatch chose is checked against that schema, loaded once per name for the batch (`_dispatched_schema`), and one that no longer loads is not checked. Of a provider's own metadata a row keeps `finish_reason` alone (`_response_metadata`); its `model` and `provider` are written from the config, as online. | `processing`, `output` |
