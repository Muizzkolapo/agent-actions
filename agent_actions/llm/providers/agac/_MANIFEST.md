# AGAC Provider Manifest

## Overview

Claude-branded provider adapter (AGAC) with non-blocking clients and test helpers.

## Project Surface

| Symbol | File | Interaction | Config Key |
|--------|------|-------------|------------|
| `AgacBatchClient._write_state()` | `.agac/batch_state/{batch_id}.json` | Writes | — |
| `AgacBatchClient._load_state()` | `.agac/batch_state/{batch_id}.json` | Reads | — |
| `AgacBatchClient.release_batch()` | `.agac/batch_state/{batch_id}.json` | Deletes | — |
| `AgacBatchClient.discard_partial_writes()` | `.agac/batch_state/*.tmp` | Deletes | — |
| `AgacBatchClient.reset()` | `.agac/batch_state/` | Deletes | — |
| `scenario.load` | `sandbox.<workflow>.yml` or `sandbox.yml`, or the file `--scenario` names | Reads (once per workflow load of `agac run --sandbox` or `agac retry --sandbox`) | — |
| `Scenario.next_attempt` | `agent_io/store/` (`<workflow>.sandbox.db`, `workflow_metadata` keys `sandbox_attempts:<action>:<record>`) | Reads and writes (each scenario call online, each task at a batch submit) | — |
| `rules_for` | `agent_config/{workflow}.yml`, `schema/{workflow}/{action}.yml` | Reads (through the expectation suite the run resolves, once per action in a run) | `actions[].expect` |
| `observed_refs` | `agent_config/{workflow}.yml` | Reads (less a loop's `feedback` inputs) | `actions[].context_scope.observe`, `- loop:` `feedback` |
| `Contract._report` | `agent_io/logs/` | Writes (one warning per run, action and field) | — |
| `tool_stub.stub_output` | `schema/{workflow}/{action}.yml`, `agent_config/{workflow}.yml` | Reads (the compiled output schema, the `expect` rules and the observe list of a tool action that the scenario stubs, for each record) | `actions[].schema`, `actions[].expect`, `actions[].context_scope.observe` |

## Modules

| Name | Type | Description | Signals |
|------|------|-------------|---------|
| `batch_client.py` | Module | Offline batch client for testing batch without a vendor. It seeds each answer with the action and what the record is asked (the task's prompt and `user_content`), as the online client does, never with the task id, so one record gets one answer in every run. It reads result lines with `OpenAICompatibleResponseMixin` (`_vendor_label` `agac-provider`), as the OpenAI batch client does, except that a line's top-level `error` reads as its `message`. A batch reports `in_progress` for its first `polls_until_complete` status checks and until `complete_after_seconds` have passed (both from the sandbox scenario's `batch` block, 0 by default; the constructor's arguments win), so with neither it completes at its first status check. Under a sandbox scenario `prepare_tasks` puts on each task its record's `source_guid` (`record`, read from the row's `RECORD_GUID_KEY`) and its whole input (`input`, the row's `content`), and at submit each such task is stamped with `Scenario.next_attempt` for its action and record (`attempt`), counted in the sandbox store, so a retry or repair batch that a later run submits counts on; any other task counts in memory per `custom_id` and nothing is written. A batch holding a task of an action the scenario's `batch.fail` names (or its version group's base name) is recorded `failed` and every status check reports it so. At collect, under a sandbox scenario, a task with a `record` is named by `Scenario.record_key(input)`, then left out when `drops` holds (counted `dropped`), becomes `faults.batch_line` for the kind `error_for` picks (counted `errors`) with the rules `rules_for` reads from its input, or else has its answer passed through `Contract.follow`. A text-mode task whose prompt ends by offering answer shapes (a judge's) gets one of them, seeded by the action and prompt as online, passing or failing by `judge_passes`. `prepare_tasks` adds the action's `Contract.to_task()` to each task, so collecting answers each one with the same rules as online. At submit, `_shared_contracts` keeps each distinct rule set once in the batch record (`contracts`, by key) and each task holds only its key; a task with no rules (or a record with no `contracts`) is answered by the plain generator. Imports `contract` inside the methods that use it. Records a submitted batch under `.agac/batch_state/` in the project so the run that collects it — a separate process, because submitting pauses and asks to be run again — can find it. Answers each task from the schema and prompt that task carries. A task's `model_config` holds only the settings the action sets, never a null. The record outlives the read: collecting hands bytes to a caller that has yet to write and evaluate them, and a re-run must find the same batch. It dies with the registry entry that names it. A batch with no readable record is reported `unknown` and taken as failed: nothing will come back for it. Nothing in it names a kind of side call. | `llm.batch`, `llm.providers` |
| `contract.py` | Module | What a mock answer must meet beyond its schema. `Contract.follow(scenario, rules, record, schema, record_id, attempt)` applies a sandbox scenario to an honest record: when `breaks` holds, `break_rules` makes rules fail (`all`: the one `pick_rule` chooses among the error-severity rules the mock can check; a list: every such rule of those types), trying values led by the rule's own params (a pattern's match, its phrases or values, a word or item count past a bound) in each field the rule reads (every declared field for a record rule) until the real check (`run_suite` over that rule) fails, a value the field's schema accepts first; an action with no error-severity rule is not changed and nothing is logged; a named rule type the action does not check, or a rule no value breaks, is logged once per run, action and rule. Then `pin` sets each pinned field and logs once per run, action and field a value its schema or a rule refuses; the value is kept. `Contract.for_request` reads the action's rules with `rules_for`, through the same suite resolution the run uses (`create_expectation_service_from_config`), less `llm_judge` rules and unregistered types, cached per run on the action and a hash of its `expect`, schema, schema name and project root; the record's context as the request sends it; and the action's `context_scope.observe`. `Contract.generate` builds each top-level field a rule names to meet its schema and rules (`enum` ∩ `accepted_values`, `matches_regex` and schema `pattern` through `regex_gen` on a string or untyped field, the number a pattern spells on an `integer`/`number` field, else a value of the field's type; a negated pattern, `word_count_between`, `item_count`, `not_null`/`no_null_fields`, `field[*]` element rules), checks each field with the real registered check, then checks the whole record with the real `run_suite` and builds it again up to `TRIES` (20) times. A rule no record can meet (`_unmeetable`: a pattern Python cannot compile, or a field the schema does not declare) gets no tries and adds no key. An output field that an observe reference names exactly (`ns.field`, never `ns.*`, never a loop's `feedback` input, which holds the previous iteration) copies that input when it meets the field's schema and rules. What still fails is logged once per run, action and field, naming the constraints; a run is `run_key`: the `workflow_session_id` and the event `correlation_id` each run sets at start (`reset_runs` forgets all runs; at most `_MAX_RUNS` are kept). The best attempt is returned, ranked first by fields the schema refuses, then by failed rules. `to_task`/`from_task` carry the rules, observe list and session id on a batch task; the task's `user_content` is the context. With no rules, the answer is the plain generator's, plus any copied inputs. | `llm.providers`, `expectations` |
| `scenario.py` | Module | The sandbox scenario. `load(source, project_root, groups, tally, tools, workflow)` reads a preset (`PRESETS`: `happy`, no faults; `chaos`, `seed: 0`, errors at 0.1 of `rate_limit`/`timeout`/`truncated`/`empty` healed at attempt 2, one rule broken at 0.2 healed at attempt 2, judge `pass_rate` 0.7, batch `polls_until_complete: 1` and `drop_rate: 0.1`), the file a path names, or with no source the project's file for *workflow* (`project_file`: `sandbox.<workflow>.yml` at the project root, else `SCENARIO_FILE`, `sandbox.yml`), else `happy`. A refusal of `sandbox.yml` in a project of more than one workflow (folders `agent_workflow/*/agent_config`) adds one line naming `sandbox.<workflow>.yml` (`_per_workflow_hint`, kept on the `Scenario` for `check_outputs` too); a refusal of any other file does not. Pydantic models with `extra="forbid"` refuse an unknown key; a rate outside [0, 1], a `heal_on_attempt` below 2, an unknown error kind (`ERROR_KINDS`), a `latency_ms` range with min above max, an action name that is neither an LLM action or tool action of the workflow nor the base name of one of its version groups (*groups* maps each LLM action to its group's base name from the expanded config, so `foo` is not a group of `foo_2`; *tools* maps each tool action to its `Tool`: its group and `cannot_stub`, the reason the mock cannot build its output, or None), `judge` in a `records` entry, and a `break_rules.rules` type the expectation registry does not know are refused too: one `ConfigurationError` naming the file and each key, with the file as `config_file` and a hint in its context. `check_outputs(declared)` refuses, the same way, a `pin` field an action's output schema does not declare and `pin`/`break_rules` under `actions` or `records` for an action with no JSON output schema. One resolver (`_named`: the exact name, else the version group's base name) reads `actions`, `records[].actions` and `batch.fail`. `Scenario.rules_for(action, record_input)` merges, each key whole, a `records` entry whose `match` (dotted paths into the record's whole input) the input meets and that names the action (`error: <kind>` is errors at rate 1 of that kind), over `actions.<name>`, over `defaults`. `record_key(input, fallback)` names a record by a SHA-256 of its input (the guid *fallback* only for a call with no input), alike in every run, also below an expansion or a FILE tool, whose rows get a new `source_guid` in each run. Each decision (`error_for`, `breaks`, `pick_rule`, `latency_ms`, `judge_passes`, `drops`) is `chance(action, record, attempt, decision)`: a SHA-256 of the seed and those values mapped to [0, 1), so no call order changes it. `drops` holds for a record's first submission only. `next_attempt(action, record)` counts a record's attempts at an action: with a store attached (`attach`), one `increment_metadata` of `sandbox_attempts:<action>:<record>` in the sandbox store, atomic across processes; else in memory. `count`/`summary` add to the command's `Tally`, which every load of the workflow in one command shares, for the one line the CLI prints (`Tally.counts()` is a copy of the counts). `next_attempt` also counts the call there (`Tally.calls`, not in the line), so a command that an error stopped knows whether the mock answered. `actions.<name>.stub` (`NamedActionRules`, under `actions` only) is for a tool action: `Scenario.stubs(action)` reads it through `_named`, so a version's own entry wins over its base name, and `stubbed()` lists the stubbed tools. A preset sets no stub of its own, but `load` keeps the `stub` entries of the project file under a preset (`_stub_entries`: each `actions` entry that sets `stub`, with only its `stub` and `pin`), recorded as `Scenario.stubs_from`; `Scenario.label` (`preset <name> with the stubs of <file>`) names it in a refusal. A `--scenario` path takes no project stubs. `tool_problems()`, part of the load's one refusal, refuses `stub` on an action that is not a tool action, `stub: true` on a tool whose `Tool.cannot_stub` is set (a FILE tool, a built-in tool, a tool with no output schema known at load), each key of `MODEL_CALL_KEYS` (`latency_ms`, `judge`, `errors`, `break_rules`, `error`) on a tool action, `pin` on a tool action that is not stubbed, and a tool action in `batch.fail`; `stub` under `defaults` or in a `records` entry is refused as a key that belongs under `actions.<tool action>`. `check_outputs` checks the `pin` fields of a stubbed tool as it checks an LLM action's. | `config.sandbox`, `llm.providers` |
| `tool_stub.py` | Module | `stub_output(scenario, agent_config, context_data)` is the record a tool action stores when the scenario stubs it (`actions.<tool>.stub: true`); `llm.providers.tools.client.ToolClient` calls it in place of the tool's function. It builds the record from the tool's `json_output_schema` with `Contract.for_request(...).generate(schema, 1)`, as the online client builds an LLM answer (schema keywords, the action's `expect` rules, an observed input field of the same name), then applies the `pin` that `Scenario.rules_for` reads for the record (`Contract.pin`). The generator is seeded with the action name and `Scenario.record_key` of the record's whole input (`RECORD_INPUT_KEY`, else the context the call was given), never with the scenario's seed, an attempt or a `source_guid`, so one input gets one record in every run and thread. It counts the call in the `Tally` (`calls`). | `llm.providers`, `tools` |
| `faults.py` | Module | Each scenario fault as a real OpenAI-style vendor shows it. Online: `rate_limit` and `server_error` (an `httpx.HTTPStatusError` of 429 or 503) and `timeout` (`httpx.ReadTimeout`) are raised through `error_wrapper.wrap_vendor_error` as `RateLimitError` / `NetworkError`, which the retry policy retries; in JSON mode (`json_answer`) a `refusal` and an `empty` answer are the `_parse_error` records `chat_no_answer` names, `truncated` is the first half of the honest answer with `cut_off_parse_error("length")`, and `invalid_json` is `unparsed_json_record` of text with no brace; in text mode (`text_answer`) `refusal` and `empty` raise `VendorAPIError` from `chat_no_answer`, `truncated` returns the first half of the honest answer as the answer, as a real client returns a text answer cut off partway (a cut before the first character raises `ResponseTruncatedError`, as there), and `invalid_json` returns that text. `batch_line` turns an honest result line into a 429/503 line with an error body, a line with a top-level `error` for a timeout, or a 200 line whose message holds a refusal, no content, cut-off content with `finish_reason: length`, or that text. | `llm.providers` |
| `regex_gen.py` | Module | `generate(pattern, rng)` builds a string from a bounded regex subset: literals and escapes, `.`, `\d \w \s` and negations, `[...]` with ranges and negation, `? * + {m} {m,} {m,n} {,n}` (an unbounded repeat adds at most `UNBOUNDED_EXTRA`, 3), groups `( )`, `(?: )`, `(?P<name> )`, `|`, `^ $`. Anything else raises `UnsupportedPattern`, as does a pattern `re.compile` refuses, one nested too deep (`RecursionError`), or a braced repeat count above `MAX_REPEAT` (1000). Each pattern's parse is cached. Written by hand, not on `re._parser`, which is private. The caller checks each result with `re`. | `llm.providers` |
| `client.py` | Module | Online client for Claude Code/AGAC interactions. Under a sandbox scenario (`config.sandbox.scenario()`), a call naming a record (`RECORD_GUID_KEY`, else `RECORD_ID_KEY`) counts its attempt with `Scenario.next_attempt` (in the sandbox store), reads its rules and its decision name from its whole input (`RECORD_INPUT_KEY`, else the context it was sent), sleeps its `latency_ms`, then answers the fault `error_for` picks as `faults` shows it (counted `errors`; a text-mode `truncated` is the honest text cut in half), or else passes its honest answer through `Contract.follow`; a call naming no record (a judge's side call) gets a passing or failing offered shape by `judge_passes`. In JSON mode the answer comes from `Contract.for_request(...).generate`; `contract` is imported there, not at module level, because the online client registry loads this module for every vendor. In text mode (`json_mode: false`) a prompt whose last non-empty line is only two or more JSON objects joined by ` or ` gets one of those objects back (seeded choice, string values replaced by generated sentences); that is how an `llm_judge` gets a verdict. Any other text prompt gets prose. `VENDOR_PARAMS` accepts any key and reads none, so a workflow switched to it keeps its `vendor_params`. The attempt it answers with is counted per action and record: the record is the `_record_id` on the call's config (`RECORD_ID_KEY`, set by `run_dynamic_agent`), else a `source_guid` in the context, else one counter for the action (a side call, such as a judge's). With no scenario the counts are kept per run (`contract.next_attempt`, under the same `run_key` as the unmet-constraint warnings), so each run starts each record at attempt 1, and the batch client counts per action and `custom_id` in memory. | `llm.realtime`, `llm.providers` |
| `fake_data.py` | Module | Test helpers that simulate Claude responses. `offered_answer_shapes` reads the answer shapes a prompt's last line offers; `generate_offered_answer` returns one of them, with `passing` set one whose `passed` is that value when one is. A string schema with a `pattern` is built by `from_pattern` (through `regex_gen`, kept only when `re.search` matches and it fits the length bound; None on an unsupported pattern, `re.error` or `RecursionError`), else as before. `sentence_of(n, rng)` is a sentence of exactly n words. `generate_openai_response` takes an optional `contract` that builds the record. A declared `minimum`/`maximum` (or `exclusiveMinimum`/`exclusiveMaximum`) wins over the field-name rules: the value is drawn uniformly inside the bound, on a `multipleOf` step when one is declared (a whole-number step for an integer); a one-sided bound is completed from 0 or 1000 away; name rules apply only to an unbounded field. A string outside its `minLength`/`maxLength` is padded with sentences or cut at a word boundary, a field-name value such as an email included; one of `KNOWN_FORMATS` keeps its format. | `tests`, `llm.providers` |

## Dependencies

| Package | Direction | Why |
|---------|-----------|-----|
| `expectations` | outbound | `contract.py` resolves the action's suite with `create_expectation_service_from_config`, runs single checks from `registry`, and checks the whole record with `runner.run_suite` |
| `utils` | outbound | `contract.py` checks a value against its field schema with `jsonschema_cache.checked_validator` |
| `logging` | outbound | `contract.run_key` reads the run's event `correlation_id` from `logging.core.manager` |
| `config` | outbound | `client.py` and `batch_client.py` read the loaded scenario with `config.sandbox.scenario()` |
| `storage` | outbound | `Scenario.next_attempt` counts attempts with the attached store's `increment_metadata` (typed only, under `TYPE_CHECKING`) |
| `config` | inbound | `config.sandbox.load_scenario` calls `scenario.load`; `config.sandbox.tool_actions` builds each `scenario.Tool` |
| `llm/providers/tools` | inbound | `ToolClient.invoke` calls `tool_stub.stub_output` for a tool action that `Scenario.stubs` names |
| `errors` | outbound | `scenario.load` raises `ConfigurationError`; `faults` raises the errors `error_wrapper` builds |
