# Processing Manifest

**[> Architecture Guide (ARCHITECTURE.md)](ARCHITECTURE.md)** — full data flow, record lifecycle, checkpoint/resume, ASCII diagrams.

## Overview

Shared processing utilities used by batch/online runners: enrichment, error handling,
lineage helpers, recovery flows, and transformation pipelines.

## Sub-Modules

| Sub-Module | Description |
|------------|-------------|
| [invocation](invocation/) | LLM invocation strategies (online/batch) for unified execution. `OnlineStrategy` accepts an optional `expectation_service: ExpectationService \| None` (from `agent_actions.expectations`), composed as the outermost recovery layer around the existing retry dispatch when an action's config sets `expect:`. `invoke()` threads `task.llm_context` into `ExpectationService.execute()` so a judged expectation's `context:` refs can resolve; `InvocationStrategyFactory` threads `agent_config` into the service factory so a judged expectation's LLM call can reuse the generating action's own model. |
| [strategies](strategies/) | Pipeline-level processing strategies for FILE-granularity modes (`FileToolStrategy`, `HITLStrategy`). |
| [recovery](recovery/_MANIFEST.md) | Retry, checkpoint, and recovery helpers for failed batches. |
| [evaluation](evaluation/) | Graduated-pool evaluation of batch results. `EvaluationLoop` is strategy-agnostic -- a concrete strategy implements the `EvaluationStrategy` protocol and is plugged in by the caller; `strategies/expectations.py` adapts an action's `expect:` suite to it. |

## Modules

| Name | Type | Description | Signals |
|------|------|-------------|---------|
| `batch_context_adapter.py` | Module | Adapts batch state to `ProcessingContext` + `ProcessingResult` for the shared `EnrichmentPipeline`. | `batch`, `enrichment` |
| `cascade_filter.py` | Module | `partition_cascade_records` splits records into processable and quarantined before any strategy-specific logic runs. A record whose `_state` is in `CASCADE_BLOCKING_VALUES` (`cascade_skipped`, `failed`, `exhausted`) becomes an `UNPROCESSED` result immediately -- no LLM call, no tool invocation. Called by `UnifiedProcessor` before `strategy.invoke()`, so a strategy never sees a cascade-blocked record. | `record`, `processing` |
| `disposition_gate.py` | Module | `DispositionGate` and `positions_named_by_repair`: the per-record idempotency gate that decides what a repair re-runs and what is carried forward from prior output. `positions_named_by_repair`, given the run's backend and the action, notes which named records it found there (`found_by_repair`); `note_answered_by_repair`, called by the pipelines once a file's processing returns, notes which of them were in a file processed to the end (`answered_by_repair`). `agac retry` reads both to tell a record it cleared and never re-decided. Partitions on terminal dispositions already in the storage backend, above the strategy layer -- the same architectural layer as `cascade_filter`. Instantiate once per run: the cache is instance-level on purpose, because `retry.py` calls `workflow.run()` again in the same process after clearing dispositions and a module-level cache would serve stale rows. `carried_past_repair` reports the case it cannot resolve rather than guessing (#1022). `with_stored_rows_not_reproduced` is the batch path's one merge of a run's output with the stored rows it does not replace, used by finalize, by the write made when the guard leaves nothing to send, and by the one made when every input is already done; `stored_rows_not_reproduced` decides which rows those are, never one answering for an input the guard filtered this run unless the run failed and answered nothing, and `build_carry_forward` fetches them. A run that failed and answered nothing keeps the stored answers only while `every_answer_vouched_for` finds each still holding `success`; `stored_answers_stand` asks that of a stored file for the online pipelines, which otherwise write the file with its failures before raising, so the answers a reset took back are not served as this run's. Otherwise the batch merge keeps no stored row, minted or not, of an input the run wrote a row for, as online writes only that row. `answered_since_stored` names the records of a file checkpointed after it was last stored: their stored rows are older than their answers and their checkpoint rows lack enrichment, so the online path answers them again instead of carrying either. With nothing stored, `build_carry_forward` carries checkpoint rows, except a record checkpointed with several rows: an expansion's rows share their input's identity until enrichment mints one each, so that record is reported missing and answered again, as is one an earlier version checkpointed (`checkpointed_without_row_count`), whose one row may be the last of several. | `storage`, `record` |
| `enrichment.py` | Module | Adds metadata (timestamps, run IDs) to processed items. | `logging`, `workflow` |
| `error_handling.py` | Module | `ProcessorErrorHandlerMixin` for wrapping file loading/processing logic. A failure fires the event `_failure_event` returns: a parse or load failure (D001/D002) unless the processor overrides it, as `FileWriter` does to report a write. | `logging` |
| `exhausted_builder.py` | Module | Builds reports once a workflow’s retries are exhausted. | `validation`, `logging` |
| `guard_context.py` | Module | Single source of truth for guard field context, so the online prefilter and batch prepare evaluate identical structures. Source resolution is delegated to `source_resolution.py` at both stages. Where the context resolved a `source` namespace and the record carries one under the same name, the resolved one decides the guard: the evaluator merges the record after the context but no longer lets a carried namespace override a resolved one. Both sides must be a namespace — a plain field spelled that way is somebody's data (a first-stage staging row, a version-merge tool's flat output field, a promoted `output_field`) and is left alone, since taking the key away would read as a missing field, which is *not matched* and so a silent filter. Two consequences: `context_scope.drop` does not hide a field from a guard clause — in this namespace or any other, since the FILE prefilter reads the pre-scope record — and a field only the carried copy had becomes unreadable once the resolved document replaces it. | `prompt`, `input` |
| `helpers.py` | Module | Shared helpers (UUID construction, tuple flattening) for processors. `bypasses_expectations()` names the routing that makes an `expect:` block inert — a tool or HITL action at file granularity is processed by a strategy that never evaluates expectations — so a caller can say so rather than implying the rules run. | `processing` |
| `record_helpers.py` | Module | Shared record assembly helpers: `build_tombstone`, `build_exhausted_tombstone`, `carry_framework_fields`, `apply_version_merge`. Used by all processing paths (online, batch, FILE). | `record`, `processing` |
| `source_resolution.py` | Module | Shared source content resolution for a record at either stage. `resolve_first_stage_source` returns the record enveloped, normalizing a record whose user fields sit at the top level so `RECORD_FRAMEWORK_FIELDS` separates them from the framework's own keys -- the boundary such a record does not carry, and without which a wildcard `observe` sends `source_guid`, `node_id` and `lineage` to the model as document fields. `resolve_source_content` handles every later stage, by identity: own guid → carried parent_source_guid → the `source` namespace the record carries, which must be a dict → None (no positional fallback). Same order as the FILE-mode resolver in `prompt/context/scope_application.py`. A pool row that matches must carry a `content` namespace dict: without the envelope there is no boundary between the user's keys and the framework's, and reading it means guessing which is which -- so it raises `DataValidationError` rather than guess. Only the row actually read is checked, so one unreadable row does not fail the records resolving elsewhere in the same pool. A workflow with no staging data of its own passes its input records as the pool, so a record resolves to itself at the first step by design. Used by `task_preparer.py` and `guard_context.py`. | `input`, `prompt` |
| `result_collector.py` | Module | Collects main vs side outputs, handles duplicates. Counts UNPROCESSED results separately from successes. Exports `write_node_level_disposition` (node-level skip/passthrough), `write_record_dispositions` (batch record dispositions) and `write_dispositions` (one transaction, logged on failure). Given a `ProcessingContext` with `defer_kept_dispositions`, it leaves what the gate carries a record from the stored file by (SUCCESS, PASSTHROUGH) in `kept_dispositions` for the caller to write once the file is stored, minus a row the store refuses as a schema echo, whose failure the store records as it writes the file. The rest (FAILED, EXHAUSTED, UNPROCESSED, DEFERRED, FILTERED) is written at once: a file whose records all failed is usually not stored, and a fan-in drops a record by its FILTERED alone. All `set_disposition` calls (except executor-level) are centralized here. `CollectionStats.terminal_failure` writes the node-level skip per input file, which the executor takes as the action's only while the action holds no record, and returns, rather than raises, a `terminal_failure` for a file in which nothing succeeded (which batch collection raises too for a file whose refused records leave no disposition to fail it by), marked with `mark_every_record_failed`, since every active record of the file failed: the record loop re-raises anything that would stop it partway, so reaching this check means every record was reached. Returned, so a caller can write the file first where the answers stored for it no longer stand; `raise_if_terminal_failure` raises it. Exhausted records take their lifecycle-stamp and disposition reason from the tombstone's own `_tombstone_reason`/`metadata.reason`, not a hardcoded `retry_exhausted`, so expectations-exhausted records are labelled honestly; the retry config's `on_exhausted: raise` policy skips expectations-exhausted results, whose policy already resolved inside `ExpectationService`. | `output` |
| `prepared_task.py` | Module | `GuardStatus` enum (PASSED, SKIPPED, FILTERED, UPSTREAM_UNPROCESSED), `PreparedTask` dataclass, and `PreparationContext` (carries `mode: RunMode` directly). `PreparedTask` carries only fields something reads: `source_content` and `prompt_context` were assigned on two of `prepare`'s three returns (the upstream-unprocessed short-circuit assigned neither) and `metadata` on none, and nothing read any of them. `PreparationContext` carries only fields something reads: `file_path`, `output_directory` and `record_index` were assigned by both builders and read by neither, and the same-named reads elsewhere are on `ProcessingContext` and `DataPreparationContext`. It is an input struct with two builders, `from_processing_context` here and `_build_preparation_context` in `llm/batch/processing/preparator.py`; the latter derived `file_path` from an `output_directory` and a `batch_name` it took for no other purpose, so both parameters went with the fields. Note it is not a straight copy of `ProcessingContext`: it omits `parent_records`, `defer_exhaustion`, `pending_exhaustion`, `defer_kept_dispositions` and `kept_dispositions`, and adds `tools_path`, which is derived rather than copied. It is also the wrong place to carry a resolved `source` namespace, because it is built after every surface that would read one -- `prefilter_by_guard` runs over raw records before any `PreparedTask` exists, and inside `TaskPreparer.prepare` the guard and the prompt already share one `field_context` from one resolution. That agreement is pinned by `tests/unit/processing/test_source_precedence_across_granularity.py` rather than by a carried field. | `typing` |
| `task_preparer.py` | Module | Unified task preparation (normalize, prompt, guard) for batch/online. Short-circuits upstream-unprocessed records before context loading. Source resolution is delegated to `source_resolution.py` at both stages, resolved once per record and threaded into `build_guard_context`, so the guard context and the prompt are built from one value. A record below the first stage with no source_guid is refused (`MissingSourceGuidError`) once the guard has passed it and before its prompt is rendered, traced or sent, for LLM and record-level tool actions in both modes; the guard decides it first, so one it filters or skips is decided as online's guard above the strategy decides it. | `input`, `prompt` |
| `types.py` | Module | `ProcessingStatus` enum (SUCCESS, SKIPPED, FILTERED, FAILED, EXHAUSTED, DEFERRED, UNPROCESSED), `ProcessingResult` factories, and `ProcessingContext` (uses `RunMode` for mode; `defer_kept_dispositions`/`kept_dispositions` hold back SUCCESS and PASSTHROUGH until online has stored the file; `target_relative_path` is the name the caller stores the file's output under, and every read of that output uses it). | `typing` |
| `unified.py` | Module | `UnifiedProcessor`, the shared skeleton every processing path (online LLM, FILE tool, HITL, batch result) passes through: guard filter, cascade quarantine, `strategy.invoke()`, enrich, collect -- in that order, for both RECORD and FILE granularity. Each path supplies a `ProcessingStrategy` that controls only the invocation; everything around it is uniform. It is the only caller of `prefilter_by_guard`, and the one place FILE mode's pre-scope `raw_records` are paired position-for-position with the scoped `records` -- a length mismatch is refused here rather than at the guard, because a repair narrows both lists and an already-mispaired caller would otherwise arrive the same length and be paired record-to-wrong-original. Rows the gate carries from a stored file are appended as they are, enriched and collected when it was written; with nothing stored for the file they are checkpoint rows, the strategy's output saved before either, in a run that stopped or whose store failed to write the file, and `_answered_from_checkpoint` puts them through both with the run's own. | `processing`, `workflow` |

`UnifiedProcessor.process()` reads the action's stored rows for one file (carry-forward, the
carry of a repair, `answered_since_stored`, and `has_target_file`, which tells a carry from
checkpoint rows from one from the stored file) and `OnlineLLMStrategy.invoke()` writes a
checkpoint row per record, both under `ProcessingContext.target_relative_path`: the name the
caller stores the file under, and by which it clears the file's checkpoint rows once written.

**Internal only**: `ProcessingStatus`, `ProcessingResult`, `ProcessingContext`, `GuardStatus`, `PreparedTask`, `PreparationContext`, `RetryState`, `RetryMetadata`, `EvaluationMetadata`, `ExpectationsMetadata`, `RecoveryMetadata`, `CollectionStats` -- no direct project surface.

`OnlineLLMStrategy.process_record`'s not-executed branch has two exhaustion arms, checked in
that order: expectations (they wrap the inner layers, so their exhaustion is the terminal cause
even when inner retry metadata is also present), then retry. The expectations arm
writes reason `expectations_exhausted` plus `expectations_failed`/`expectations_iterations` in the
tombstone metadata. `ExpectationsExhaustedError` joins `ConfigurationError`/`EmptyOutputError`/
`SchemaValidationError` in the action-fatal re-raise list — `on_exhausted: raise` halts the run
rather than degrading into a per-record failure.

## Dependencies

| Package | Direction | Why |
|---------|-----------|-----|
| `llm` | inbound | Batch and online runners delegate to UnifiedProcessor |
| `prompt` | inbound | DataGenerator uses OnlineLLMStrategy for subsequent-stage processing |
| `workflow` | inbound | Pipeline orchestrator calls processing for each action stage |
| `cli` | inbound | `agac retry` asks `answered_by_repair` and `found_by_repair` what its re-run reached; `agac expect` reads `bypasses_expectations` |
| `prompt` | outbound | TaskPreparer uses PromptPreparationService for context and prompt rendering |
| `input` | outbound | Uses guard evaluators and field resolution from preprocessing |
| `storage` | outbound | ResultCollector writes dispositions to StorageBackend; `disposition_gate` reads them beside the stored rows |
| `config` | outbound | Reads action configuration types and run mode from config |
| `expectations` | outbound | `OnlineStrategy`/`InvocationStrategyFactory` build and compose an `ExpectationService` from an action's `expect:` config |
| `record` | outbound | Envelope, state, reasons, disposition and tracking -- `cascade_filter` and `disposition_gate` both partition on `RecordState` |
| `errors` | outbound | `ProcessingError` and the structured error types raised across the package |
| `utils` | outbound | Constants, content-envelope helpers, `IDGenerator` (first-stage `source_guid`), `VersionIdGenerator`, `FieldManager`, `LineageBuilder` |
| `validation` | outbound | `schema_output_validator` for checking an action's output against its schema |
| `guards` | outbound | `GuardBehavior`, read by `task_preparer` to act on a guard verdict |
| `llm` | outbound | `helpers.run_dynamic_agent` imports `llm.realtime.builder` lazily, inside the function, because `llm` depends on `processing` -- the deferral is what keeps that cycle from closing at import time |
