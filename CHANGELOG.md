## 1.1.0 - 2026-09-13
### Enhancement or New Feature
* A workflow run now prints as a progress stream instead of a log: one line per action, grouped under the dependency step that produced it, with its record count, duration and model. Framework bookkeeping no longer interleaves with it, and the step structure is written to `events.json` for the first time — previously it existed only on the terminal, and was printed twice there. The post-run summary table is removed: it re-rendered every action the stream had already shown, so a run ended four separate times. Output for the bundled example workflow went from 127 lines to 58.
* Framework-internal log messages are kept off the console without being lost. Events carry a `diagnostic` flag: the terminal drops them unless the run is verbose, while the JSON log files keep them at full severity. The rule for what counts as internal is written down — whether the person running the workflow can change what the message describes — so classification is reviewable rather than a matter of taste.
* `AGAC_MAX_RECORDS` caps every action's record count for a run, regardless of what the project config asks for. A capped run says so, because a truncated run that stays silent looks like a complete one. An unusable value fails the run rather than being ignored.
### Under the Hood
* Release v1.0.0 — batch changie entries, bump version
* Faster project scans: the docs scanner no longer walks the project twice per workflow, each workflow event log is read once instead of twice, project-tree searches skip virtualenvs and VCS directories, and the schema-tree walk is reused across `load_schema` calls.
* Removed a superseded source resolver and two paths traced as unreachable, keeping the two that were load-bearing defensive guards — deleting those would have replaced a loud failure with a silent one.
* The lockfile is back in step with `pyproject.toml`; `uv lock --check` had been failing. Metadata only — no resolved dependency version changed.
### Bug Fix
* A failing record was reported twice on the console — once by the processing strategy, once by the result collector — and the action's own failure line described file processing rather than the fault, because the record's cause was flattened into a string two layers below. The collector is now the single reporter for both online and batch runs, and the cause travels intact to the action line, where it leads the message so it survives the 60-character truncation `agac dispositions` applies.
* Every version-merge consumer reported zero records while its output was on disk. The per-run record count is a delta measured across the action, and the correlated input is written into the consuming action's own target before it runs, so the snapshot already included it. Both run paths now measure from before input resolution.

## 1.0.0 - 2026-09-08
### Breaking Change
* `agac clean` no longer deletes generated output by default. The old default removed both `agent_io/source/` and `agent_io/target/` — the documented per-action output path — while the docs described the command as cache/temp cleanup, so a routine clean (or `clean -f` in a script) silently destroyed paid LLM output. The default scope is now `agent_io/source/` only, which is regenerated from `agent_io/staging/` on the next run. Removing `agent_io/target/` requires the new `--target` flag; `--all` is unchanged and still removes everything, including staging and the durable store. Callers that relied on plain `clean` to remove output must pass `--target`.
* Referencing a schema name that matches more than one file is now a hard error instead of a warning. Schema names must be globally unique (the loader's own contract), but a collision used to log a warning and silently pick the winner by alphabetical directory order — so an action could validate its output against an unrelated workflow's schema, the same class of risk as a duplicate action name, which already hard-fails. `SchemaLoader.load_schema` now raises `SchemaValidationError` naming every colliding path when the requested stem is ambiguous; `agac inspect` surfaces it as a preflight failure. Discovery itself stays lenient — the LSP indexer and docs scanner keep working, `agac docs` skips ambiguous names with a warning, and collisions among schemas nothing references warn without blocking. That warning now fires once per process instead of once per action. Projects with two same-named schema files that relied on the alphabetical pick must rename one of the files.
* `validate_and_raise_if_invalid` is removed from `agent_actions.validation`. It had no callers inside the framework — the `on_schema_mismatch: reject` path it served went with the `reprompt:` block — and it was not reachable as public API in practice, being absent from the docs site, the examples and the README. `validate_output_against_schema`, which does the validation and is what the framework itself calls, stays exported; the removed wrapper only added "and raise `SchemaValidationError`" on top of it, which a caller can do from the returned report.
* `reprompt:` and `on_schema_mismatch:` are no longer accepted, on either the action or defaults config surface — a config carrying either is refused at load, with the `expect:` replacement named in the error. A block that only checked the schema (`on_schema_mismatch: reprompt`) becomes `expect: {repair: auto}`; a block with a validation function (`reprompt: {validation: fn}`) becomes `expect: {expectations: [...]}` using a deterministic or `llm_judge` type. `skip_schema_validation` is removed with it — with no `expect:` block, schema conformance is now reported rather than enforced; enforcement belongs to the structural gate, which regenerates instead of raising. See the expectations reference's migration section for the full field-by-field mapping.
### Enhancement or New Feature
* Add `expect:`, a validation layer above schema and guards for checking what a value means, not just its shape: deterministic checks (`not_null`, `word_count_between`, `no_forbidden_phrases`, `item_count`, regex, allowed values, and more) plus `llm_judge`, which asks a model whether a value satisfies an arbitrary natural-language rule, optionally grounded against another action's output, with majority-vote sampling and a per-run judge budget. Rules can be inline, in a reusable `suite:` file, or declared directly on schema fields. `repair: none` makes the checks pure reporting; `repair: retry` re-sends the original prompt; `repair: auto` re-sends with the failure list composed into feedback; `repair: {prompt: ...}` uses an authored regeneration template — the same four modes apply separately to schema failures via `structural:`. Works the same way in both the online and batch paths.
### Under the Hood
* RELEASING.md said pushing a v* tag publishes to PyPI. It does not — publish.yml triggers on `release: published`, so a tag alone reaches nothing. Corrected, and documented the release-PR changelog entry the CI job requires, the pre-tag version check, and the manual VS Code extension publish.
* Release v0.3.0 — batch changie entries, bump version
### Bug Fix
* The documentation site builds again. Deploy Docs had failed on every run for over a week, so the published site was frozen and still advertised v0.2.6. Two partial dependabot bumps left version sets Docusaurus requires to match exactly: @docusaurus/core at 3.10.1 against preset-classic at 3.10.2, and react ^19.2.8 against react-dom ^19.2.7.
* FILE-granularity observed fields no longer overwrite each other or the namespaces they land beside. Each observed field is injected into a record as a bare top-level key, and that write was blind: a wildcard expansion could clobber an explicitly observed field (last writer wins, decided by ref order), and a field whose name matched a sibling namespace or a bus namespace (source/version/workflow/seed) replaced that namespace outright — which then stranded the namespace's own observed fields, since they no longer resolved against a dict. All of it was silent data loss on the bus handed to kind: tool and kind: hitl actions. Keys that could collide are now delivered namespace-qualified (ns.field) and announced. Qualification is decided from the observe refs alone, never the record values, so a given ref produces the same key on every record, batch and run: an explicit ref is qualified whenever a wildcard on another namespace could expand onto its name, and a field naming an observed or bus namespace is always qualified. Configs mixing a wildcard with a cross-namespace explicit ref will see that explicit ref arrive qualified — e.g. observe: [extract.*, classify.category] now delivers classify.category rather than category. The preflight check covers kind: hitl as well as kind: tool, resolves granularity the way the expander does (it compared against a lowercase literal the expander never emits, so it had never fired), and reports only what the action's payload will actually receive. Protecting a namespace that merely happens to be present but is not itself observed also no longer depends on which record is being enriched: that reservation is now decided once from the union of namespaces across the whole batch a FILE action receives in one call, so a guard reading the same bare field name can no longer see the namespace on one record and the observed value on the next.
* An action whose records are all removed by a guard now reports the same way in batch as in online: SKIPPED, with skip_reason 'All records guard-filtered — no output produced', a skip line in the run summary, and downstream actions cascade-skipping. Batch previously reported it as a successful completion, indistinguishable from a run that produced real output. The cause was a missing signal rather than a mishandled one. The completion classifier derives SKIPPED from a node-level 'skipped' disposition whose only writer sits past the batch fork in workflow/pipeline.py, so a run_mode: batch LLM action never produced it; batch records a node-level 'passthrough' for its empty tombstone instead. The classifier now also reads that, gated on the action having written zero records, so a passthrough carrying real data is unaffected. That row is read and never rewritten, because the node-level disposition is single-valued and the row is the batch resume path's only marker. Alongside this, both batch completion paths now route a SKIPPED classification through the same handler online uses, where previously one returned COMPLETED before classifying at all and the other set the status without a skip reason, without an ActionSkipEvent and without recording the completion. The passthrough path also now reports the classified status rather than a hardcoded COMPLETED, so an action with some failed records is no longer flattened to a clean completion and one with all records failed is no longer reported as success.
* When every input file of an action fails to process, the error now names why. It previously read only "Action 'X': Found N files but failed to process any. Check logs for details." — in the CLI summary, in the run status file, and in the node-level failed disposition that `agac dispositions` reports. The real causes were collected a few lines earlier and passed to the log summary, but never to the raised DependencyError, so a broken `impl:` reference or an undefined template variable was only discoverable by opening the log file. All three collectors (storage backend, merged upstreams, single directory) now return their per-file errors, and the raised error leads with them: the summary panel renders only the first 80 characters, so a cause appended after the counts would still not reach the reader. The full list is also attached to the exception context for the run tracker.
* An action that halted on `on_exhausted: raise` now stays halted. `raise` means "stop, a human needs to look at this", but every subsequent `agac run` reset the action to PENDING and re-ran it — the failure is deterministic, so it burned the same model calls and reached the identical halt, indefinitely. Leaving the status FAILED was not enough on its own: the executor has no FAILED branch, so the action ran again whatever the status said. The failure now carries a marker on its node-level disposition — set from the `on_exhausted` policy the raising code already attaches to the exception — the startup reset skips those actions and preserves their dispositions, and the executor refuses to re-run one, naming `agac dispositions`, `agac retry` and `agac run --fresh` as the ways forward. An ordinary failure is still reset and still retried on the next run, so nothing changes for a provider hiccup.
* `agac dispositions`, `agac schema` and `agac retry` no longer destroy the state they were opened to read. `AgentWorkflow.__init__` ran its startup reset unconditionally, so each of these commands returned every failed action to PENDING and wiped its dispositions before doing any work. `agac retry` was the worst affected: it reads the disposition table after constructing the workflow, so against any fresh failure it reported "No failed records ... Nothing to retry" about rows its own constructor had just deleted — in both dry-run and real mode. The constructor now takes a read_only flag that suppresses both the fresh clear and the retryable reset, and the three commands request it; `agac run` is unchanged, where reset-before-execute is the intent. `agac inspect`, `agac status`, `agac preview`, `agac validate-udfs` and `agac list-udfs` were never affected — they do not construct an AgentWorkflow.
* Every `on_exhausted: raise` site now tags its exception with the policy, so a deliberate halt is recognisable wherever it came from. Previously only the online retry-exhaustion site did; batch retry exhaustion, both reprompt exhaustion sites and batch reprompt exhaustion raised a bare RuntimeError that the next run read as an ordinary, resettable failure — including `reprompt.on_exhausted`, a first-class config field with the same semantics as `retry.on_exhausted`. The exception type is deliberately unchanged: batch's own handler re-raises RuntimeError ahead of a generic except that would otherwise swallow the halt. The online per-record loop, which re-raises a fixed list of action-fatal types and flattens the rest, now also lets a policy halt through — without that the reprompt tagging had no end-to-end effect. Separately, the halt now survives file processing: that layer collects each per-file failure and raises its own error afterwards, outside any except block, so nothing linked the two; it chained the first error, which lost the halt whenever another file failed first, and dropped it entirely past the tracked-error cap. It now chains the halting cause and captures it outside the cap. Batch mode remains unfixed and is filed separately: a batch action's deferred retries never reach exhaustion, so the policy never fires there at all.
* `agac dispositions` now shows action-level state. Both of its views filtered out the node-level record id, so an action halted by `on_exhausted: raise` was invisible in the very command its error message tells you to run — and when the halt was the action's only row, the action was missing from the table altogether, because the summary skips actions with no per-record dispositions. Both views now render node-level rows in their own section with halts labelled and the resume commands beside them. The per-record table is unchanged; node rows are not records and would distort its counts.
* A FILE-granularity tool that folds N inputs into fewer outputs no longer tombstones the contributors it kept. `FileUDFResult(outputs=[{"source_index": [0, 1, 2, ...]}])` is the documented shape for a many-to-one collapse, but the missing-record safety net decided which inputs were accounted for by reading the output records' source_guid — and a collapsed output inherits only its first contributor's guid, so the rest read as dropped and were tombstoned `tool_missing_record`. Those tombstones were emitted as real output records stamped `cascade_skipped`, which is a cascade-blocking state, so a collapse of ten records into one file produced one real result and nine synthetic records that every downstream action then quarantined as `upstream_unprocessed`; record_count reported ten. The check now also walks the source_mapping that reconcile_outputs already builds, which is the only place the remaining contributors survive. The change can retire a false tombstone but never create one: a contributor named by no output is still caught, and 1:1 tools are unaffected.
* A completed action now re-runs when its guard, prompt or schema changed. The config-hash mechanism that detects this was correct but unreachable: `execute_action_sync` consults it before checking for output, yet no run loop reaches that function for a completed action — the sequential and parallel loops both call `verify_completion_status(action_name)` first, which takes only a name and can therefore only ask whether output still exists. For a completed action that still has its output the answer was always "skip", so the hash was never compared and `--fresh` was the only way to honour a config edit, with nothing telling the user so. The check now lives inside `verify_completion_status`, reading the config through the action runner rather than from its callers, because that function is the only thing a run loop calls for a completed action and a caller that checked output first would make it unreachable again. An action whose config is unknown falls back to the output check, and a status written before config hashing existed is left alone, so existing state does not invalidate en masse. Changing the model is detected too, by a separate route: the hash reads a `model` key that no config writes (configs declare `model_vendor`/`model_name`), and adding those to the hash input would change every stored digest at once and re-run every workflow on the first upgrade. They are stamped at completion and compared from the stamp instead, the way the record and file limits already are, and only when a stamp was written, so state predating it is grandfathered rather than mass-invalidated.
* `agac validate-udfs` now runs the structural preflight as well as the UDF checks, so it is a complete gate rather than half of one. It is the only preflight surface with "validate" in its name, and therefore the one a CI job tends to reach for, but it and `agac inspect`/`schema`/`run` checked disjoint things: a broken `impl:` reference failed `validate-udfs` and passed `inspect`, while a missing `context_scope:` passed `validate-udfs` and failed `inspect`. Either command alone let a real breakage reach runtime. The structural pass runs through the same WorkflowInspector façade `inspect` uses rather than assembling the config locally, because those checks read the fully expanded action shape while this command otherwise runs only two of the config pipeline's seven stages. A structural failure is now also reported: previously an added check would have exited non-zero while printing nothing, which is no more usable than not checking at all — the command names the failing fields and points at `agac inspect` for the full report.
* Structured fields passed to a logger via `extra=` now reach the persisted event. The logging bridge copied exactly three of them — `operation`, `action_name`, `workflow_name` — and dropped everything else, so a failure named the action but never the record. Call sites that pass `custom_id`, `record_id` or `batch_id` this way produced entries reading `"data": {"operation": "process_batch_item"}` with the identifier missing, which is precisely the field needed to trace the failure. On a real project, an identical failing run went from 9 distinct persisted data keys to 18. Naming the three missing keys would have left the same gap for the next call site, so the bridge now copies whatever the caller supplied, excluding attributes derived from a real LogRecord rather than a hand-kept list — the redaction filter's own list shows why that matters, since it names `batch_id` and `item_id` as reserved even though they are caller fields. Widening the copy does not widen exposure: the redaction filter already covered `extra` fields, and a secret passed that way is still written as `[REDACTED]`.
* Batch lifecycle events report the real batch. BatchSubmittedEvent and BatchCompleteEvent were fired a second time from the executor using a batch_id key nothing writes and a hardcoded count of one, so a three-record batch logged 'Batch  submitted: 0 requests to ' next to the correct line, and completed as 'total: 1'. The duplicates are gone, the failure path reads the batch registry and reports each job by its own id and record count, and both surviving events now name the action rather than the input file.
* A batch action's retries now reach exhaustion, so retry: {on_exhausted: raise} halts instead of resubmitting forever. When a batch comes back with records missing, the framework submits a recovery batch and leaves the parent job at COMPLETED. Nothing skipped that parent afterwards, so every subsequent agac run re-read it and started a second recovery from attempt 1: retry_attempt never climbed to max_attempts, the exhaustion policy had nothing to fire on, and the action cycled batch_submitted -> failed -> reset -> batch_submitted indefinitely, submitting a new batch job — and paying for it — on each pass. A parent that a recovery batch has taken over is now skipped, and the recovery entry it spawned is processed in its own right, which is where the attempt counter advances. The same re-read also overwrote the recovery registry entry; because replacing an entry evicts the old batch id from the registry's id index, the processing loop then asked for a client for an id the registry no longer knew and the whole run died with 'Cannot determine client for batch_id'. The loop now re-reads each entry from the registry as it reaches it rather than trusting the snapshot it took up front, since processing one entry registers the next attempt and removes finished siblings while the loop is still running.
* A retry recovery batch that reaches a terminal failure at the provider (FAILED or CANCELLED) now counts as a spent attempt instead of resetting the counter. Previously such a batch superseded nothing, so the next pass re-read the parent from scratch, wrote a fresh recovery state with `retry_attempt: 1`, and submitted another paid provider batch — every pass, forever, with `on_exhausted: raise` never firing. The dead recovery is now processed in its own right: it delivered no results, so the existing recovery handler advances the attempt counter and either resubmits the missing records as the next attempt or, at `max_attempts`, applies the `on_exhausted` policy — `raise` halts the action with a node-level failure disposition, `return_last` finalizes with exhausted tombstones. The same applies to a recovery batch cancelled at the provider. For local testing, the Ollama failure-injection seam gained `OLLAMA_FAIL_BATCH_NAMES`, which makes matching batches die terminally at the provider.
* Every contributor to a many-to-one collapse now gets a disposition row. A FILE tool folding N inputs into one output wrote a single `success` row keyed on the carrier (the first contributor's guid), so `agac dispositions` showed one row for an action that consumed nine records and the other contributors were unaccounted at the consuming action. Contributors whose guid is not carried on any output now get `success` with `reason=collapsed_into_output`, distinguishing "produced a record" from "was folded into one". The carrier keeps its bare success row, a record no output accounts for is still tombstoned `tool_missing_record`, and 1:1 tools are unaffected.
* Prompt traces can now be correlated with the records they belong to. `prompt_trace` held only the prepare-time `target_id`, an identifier minted afresh on every run, so it shared no key with `record_disposition` — the join between a record's outcome and the prompt that produced it returned nothing on every store measured. Traces now also record `source_guid`, the durable identity the disposition table keys on, and `run_id`, the run that wrote the row; existing stores gain both columns on open, and rows written earlier keep them `NULL`. Separately, a record produced by a 1-to-many expansion had its identifier re-minted after its prompt had already run, so the batch response update and the Data Explorer's trace attachment both matched nothing for it: every expansion trace kept a `NULL` response and showed no prompt. Both now reach the trace through the record's `parent_target_id`, and a record prompted in its own right always resolves to its own trace first. A response that finds no row to land on is logged instead of passing silently. Reprompt rounds now record which round they were, so a round no longer overwrites its predecessor — this was previously threaded through only one of the two reprompt paths. First actions also carry the run's `{{ workflow.name }}` and `{{ workflow.run_id }}`, which were unavailable to their prompts and left `run_id` empty on the traces they wrote. One known gap remains: an expansion's trace records the last child's output as its response, since children are written back individually.
* An action-fatal error raised while processing one input file is no longer discarded because another file succeeded. Previously the file collector escalated only when *every* file failed, so an `on_exhausted: raise` halt, a broken configuration, or an empty output under `on_empty: error` hit on one file of many was demoted to a log line: the action resolved COMPLETED, no node-level failure disposition was written, the halt marker never survived, and both resume paths were dead — a plain re-run skipped the action and `agac retry` had nothing to clear. Which errors are fatal is now declared by the layer that knows — the record, file-tool and HITL processing loops, and the template renderer, which alone can tell a malformed template from a render that one record's data provoked — and read back through the exception chain, so a wrapper added on the way up cannot hide it. An error nobody declared stays a per-file failure whatever its type, which keeps a per-item schema violation, an unreadable file, an incomplete record context, and staging data that must be corrected scoped to the input that caused them. Each collector branch finishes its walk before raising, and the executor then records status FAILED, the node-level failure disposition and the halt marker as it does for a total failure. A halt keeps everything: its dispositions are preserved, the action refuses to re-run, and `agac retry` resumes without re-billing the records that succeeded. Any other action-fatal error is an ordinary failure the next run resets, so its files keep the output they wrote but are processed again.
* `agac dispositions` now shows what each action wrote beside what it consumed. A disposition is one row per input record per action, so an action that expands or collapses records has a disposition count that legitimately differs from the number of records it produced — a workflow step that fans one record out to five showed a single row, which read as four missing records. The summary gained a `Records` column carrying the number of records stored under the action, with a note naming the reasons the two differ, and the contract is now written down in the storage architecture reference and the `dispositions` command page: the children an action creates are accounted at the actions that consume them, not at the one that produced them, which is also why `retry` targets inputs.
* Documentation that still described `reprompt:` has been brought back to what the code does. Two of the corrections would have cost a reader real time: the shipped `agac` agent skill taught a `reprompt:` block that a project carrying it is refused for at config load, and eight `expect:` snippets across the context-scope and output-validation reference pages used `max_attempts:`, which `ExpectConfig` forbids. The event catalogue listed three recovery events that do not exist, the batch-recovery page documented a metadata shape that was replaced, and eight example READMEs listed a `tools/shared/reprompt_validations.py` that is not shipped with any example. Also removed: three uncollected test scripts that fail on import because the mechanism they exercised is gone, and `llm/batch/services/resubmission.py`, whose only reason to exist was keeping the reprompt and repair rounds in step.
* A batch registry written before the reprompt phase was removed no longer loses its recovery entries on load. `RecoveryType('reprompt')` raised a bare `ValueError`, which the registry loader caught and skipped with a warning — so the parent batch those entries accounted for looked unsubmitted, and the next run resubmitted a batch that had already completed. Both halves of the retired mechanism, the `RecoveryState` phase and the registry entry's `recovery_type`, now refuse by name with a message that says which action to re-run with `--fresh`. Separately, the events reference (`docs/reference/execution/artifacts.md`) named eight event classes that do not exist and showed a JSON shape that is not written — a flat object keyed on `type`, where a real line is an envelope with `event_type`, `code`, `meta` and `data`. The sample is now generated from the real classes, the prefix table covers all 21 prefixes, and a test keeps both honest.

## 0.3.0 - 2026-08-08
### Enhancement or New Feature
* Add a top-level required_by_default key to agent_actions.yml to set required-by-default flat-field schema validation project-wide, instead of per schema file. A schema may still override it with its own required_by_default, and explicit per-field required/optional markers win over both.
* Preflight warnings now print as one grouped, tree-formatted block per check (dag-fit, prompt-contract, tool-passthrough, resolution) with counts in the header, fields grouped per action, and the remedy stated once — instead of one full paragraph per field. A run that previously emitted 30+ near-identical warning paragraphs now shows a dozen scannable lines.
* The run manifest now records the pid and hostname of the process executing the workflow. A run killed outright -- SIGKILL, OOM, power loss -- never gets to write a terminal status, so `.agent_status.json` kept claiming `running` forever and the VS Code sidebar spun indefinitely. Readers can now ask the OS whether that process still exists and report the actions as interrupted instead. The check is skipped when the manifest predates this field or was written on another host, so nothing is relabelled on a guess.
### Under the Hood
* Remove dead code from the logging module: 22 never-fired event classes, the unused stdlib JSONFormatter module, the unreachable ContextDebugHandler (built for a --debug-context flag that never shipped), the unused EventManager global-filter machinery, and two unused LoggerFactory accessors. No behavior change — none of the removed code was reachable in production.
* Remove the ActionExpander delegate façade: 13 static pass-through wrappers (9 with no callers at all) and an empty __init__, self-described as 'thin wrappers, no logic'. Tests now call the real module functions directly. No behavior change.
* Remove verified-dead definitions across nine modules: four unused PathManager methods, the unused RenderCommandArgs module, unused content-namespace helpers (wrap_content, read_namespace, has_namespace, get_all_namespaces — content is written via RecordEnvelope.build_content), and dead methods in FileHandler, LineageBuilder, MetadataExtractor, FieldAnalyzer/FieldChunker, BatchContextManager, DataFlowGraph, and path_utils. No behavior change.
* Move the six CLI argument models (RunCommandArgs, RetryCommandArgs, InitCommandArgs, CleanCommandArgs, StatusCommandArgs, BatchCommandArgs) from misnamed validation/*_validator.py files into one cli/args.py, and drop the unused BatchModeCompatibilityValidator alias. No behavior change.
* Remove the ActionRunner file-processing facade: nine pure-delegation methods over the runner_file_processing module functions, including two the module itself called back through. Callers and tests now use the module functions directly. No behavior change.
* Flatten four single-class utils packages (lineage, id_generation, field_management, correlation) into plain modules — package-level imports are unchanged; only inner-module paths moved. No behavior change.
* Remove backward-compat re-export shims: retry.py no longer re-exports retry_polling/retry_serialization names (callers import the real modules; the serialize/deserialize static-method facade is gone) and disposition_gate no longer aliases the storage TERMINAL_DISPOSITIONS set. No behavior change.
* Deduplicate the byte-identical retry/reprompt field validators shared by ActionConfig and DefaultsConfig into one private validator mixin. No behavior change; API surface byte-identical.
* Inline the five identical per-vendor error-wrapping helpers — each was a one-line pass-through to the shared wrap_vendor_error with the module's own error mapping. No behavior change.
* Remove the unused dependency-injection layer (config/di + config/factory, ~700 LOC): its container bindings were never resolved, its config profiles never read, the ProcessorFactory it threaded through the runner/strategies/pipeline was null-checked but never invoked, and its component registry was write-only. ActionRunner is now constructed directly. The workflow package barrel resolves its exports lazily, which fixes a circular import that broke standalone test collection. No behavior change.
* Final dead-code sweep across errors, record, tooling, cli, prompt, and input: remove the never-instantiated field-chunking machinery and its strategies subpackage, the orphaned DataProcessor subpackage, five zero-importer barrel modules, the unused TextLoader and ContextPreprocessor, and two dozen verified-dead or test-only definitions. No behavior change.
### Bug Fix
* Preflight's dag-fit check no longer reports output fields the consuming tool synthesizes itself — no upstream producer can guarantee a value the tool computes, so those were gaps that did not exist. Fields whose UDF provably emits them are excluded; unreadable shapes still warn. The UDF source scanner also now reads the FileUDFResult envelope, so FILE-granularity tools are no longer invisible to it.
* A run killed by Ctrl-C or SIGTERM no longer leaves its in-flight action reading `running` forever. The coordinator caught only `Exception`, but the CLI signal handler raises `SystemExit`, so the terminal-status sweep never ran and `agac status` and the VS Code extension kept reporting a live run after the process was gone. Interrupted actions now get a distinct `interrupted` status, which also preserves their checkpointed dispositions on resume -- routing them through `failed` would have bulk-wiped the checkpoint and forced a full reprocess.
